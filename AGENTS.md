## Hard rules

1. **The API is the trust boundary.** Only `apps/api` reaches the database. `apps/web`, `apps/mcp-admin` and `apps/ai-service` talk to the API over HTTP; `apps/mcp-public` uses the AI service's read interface. `web`, both MCP apps, `ai-service` and `packages/llm-agent` never import `@sebela/db` or `@sebela/services`. Python has no database access.
2. **Every write to content is an authenticated, private API route.** Public routes are read-only, with one named exception from phase 7: a visitor may create, continue and delete their own chat conversation. The API key is used by server-side callers only and never reaches client-side code.
3. **No real personal data in the repository.** Only the fictional demo seed and fictional test fixtures. Never copy anything from `.context/` into tracked files. Everything stored in the database is public content — there is no private flag.
4. **Nothing is hard-coded about the environment.** Ports, hosts and database names come from environment variables. Each worktree has its own values.
5. **Work in a worktree.** App and package code is never edited in the main checkout.
6. **Only the owner merges into `master`.** Never push to `master`, never force-push a shared branch. The orchestrator — and no other agent — may squash-merge a reviewed issue pull request into its phase branch.
7. **Environment files:** agents may read and edit `.env.example` (placeholders only) and `.env.local` inside their assigned worktree. Run the session from that worktree. Other environment files, other worktrees and the main checkout's environment files are off limits. Production credentials never belong in a development worktree. A worktree's `.env.local` holds its own database role (`DATABASE_USER`, `DATABASE_PASSWORD`), generated by the worktree script; the Postgres superuser password stays in the main checkout's `.env`. Never commit environment files or copy their values into public output.
8. **Do not add a top-level folder, app or package** that is not in `docs/repository-structure.md` without the owner's approval.
9. **Do not weaken a check to make it pass.** No disabled lint rules, skipped tests or lowered thresholds without the owner's approval.

## Deep modules

Expose a small, documented interface that hides a complete responsibility. Put handwritten backend modules in `src/modules/<name>/` with an explicit `index.ts`; other modules use that entry and other packages use declared exports. Keep dependencies acyclic and preserve the API trust boundary. Hide SQL, storage drivers and internal workflows behind their owning interfaces. Follow [code standards](docs/code-standards.md#deep-modules), [module placement/import rules](docs/repository-structure.md#backend-module-layout) and [architecture](docs/architecture.md#module-responsibilities-and-composition); maintain the module map in each relevant app/package `AGENTS.md`.

Project-local references: read [codebase-design](.claude/skills/codebase-design/SKILL.md) when shaping an interface and [tdd](.claude/skills/tdd/SKILL.md) for test-first implementation. They supplement the binding docs and do not reopen approved issue scope. These skills live only in this repository; no global installation is required.

Use [`GLOSSARY.md`](GLOSSARY.md) for canonical domain language. Read it when naming or changing domain concepts; update it only when a term or meaning is actually settled, and keep detailed behaviour in the owning domain document or specification.

## Testing

- **Test-first is mandatory** for security, API contracts, services and domain logic, and bug fixes. The test is written first and must fail without the implementation.
- **UI layout, typography and responsive polish** are accepted on acceptance criteria, Playwright checks and screenshots at 360, 768 and 1280 px in light and dark mode. A test before the markup is not required.
- **MCP and AI features are evals-first.** Evals with a stated pass threshold are written before the implementation.

Details: `docs/testing.md`.

## Git

- One issue → one branch → one worktree → one pull request into the phase branch `phase/<phase-folder>`.
- One phase → one pull request into `master`, reviewed and merged by the owner.
- Commits follow Conventional Commits. One squashed commit per issue.
- The pull request description names who implemented, who reviewed and who approved.

Details: `docs/git-workflow.md`.

## Hooks and handoff

Your edits are formatted as you make them. Commits format and lint the staged files and check the message against Conventional Commits. A developer agent's handoff is refused while lint or typecheck of what it changed fail; fix the failures, do not bypass them (no `--no-verify`). Details: `docs/permissions.md` (Hooks) and `docs/git-workflow.md` (Local hooks).

## Language

Code, comments, docs, commit messages, pull requests and PRDs are written in English. The owner converses in Czech.

Stop and ask the orchestrator or the owner rather than guessing about scope, structure or anything that touches secrets or the owner's personal data.
