# Phase 5 — Security acceptance scenarios

Status: approved planning specification, 2026-11-18. Source: [PRD](prd.md). This is an acceptance specification, not a report that MCP security has already been implemented or tested. Implementation slices and owners are in [the published breakdown](issues.md); model behaviour is specified separately in [evals](evals.md).

## Boundaries

```text
owner client -> authenticated SSH tunnel/internal network -> MCP Admin
MCP Admin -> fixed first-party HTTP API -> backend services -> database
```

- MCP receives no database/migration/storage credentials and cannot reach Postgres. Its only data capability is the allowlisted API client. No model runs inside MCP Admin.
- API authentication/validation remain authoritative, including requests that bypass MCP. The MCP gate validates a named caller through a private API authentication-check operation before protocol discovery and on subsequent operations. No second key store or expiring-auth workaround is introduced.
- Use the existing first-party administrative API-key mechanism. Do not present it as an OAuth proxy or blindly accept/forward unrelated OAuth access tokens. Verify the pinned SDK/protocol and authentication flow with an automated SDK test client in S01. Verify the actual supported owner-client connection and approval configuration in S05.
- Forward the caller credential only to configured first-party private API operations, through the transport context; existing generated public-read operations do not carry it. Never use tool arguments as an authentication source, API address or path.
- The only supported initial paths are internal server access and an authenticated SSH tunnel. Public API exposure must not provide an alternate path to private writes. Production reverse-proxy implementation remains phase 10; phase 5 supplies and tests the route/network policy locally.
- A trusted owner's client must request approval for deletion. An annotation alone is not enforcement, and an authenticated custom client can still exercise the content rights its key grants. A stolen administrative key/compromised owner host is not made harmless by MCP; revocation, constrained API operations, audit and backups limit/recover damage.

## Fixed safety rules for every slice

1. Reject before discovery/tool dispatch when authentication fails; revalidate on every operation, including existing connections. Do not interpret an MCP session/connection identifier as authorization.
2. Validate a fixed operation registry and strict API schemas. SQL-like text is never executed: reject invalid identifiers/operators; valid free text may remain literal data. Do not build a keyword-based SQL firewall.
3. Unknown outcomes are not success. Do not automatically replay a write after a timeout/disconnect whose commit status is unknown. Reconcile through reads/audit, or return an explicit uncertain outcome for the owner. MCP transport request IDs are not a promise of business idempotency.
4. The API verifies actor identity; a client cannot supply an audit key ID/name as authority. A tool label is bounded provenance, not proof of human intent. No credential, hash, authorization header or raw request dump enters audit/model context/reports.
5. Record committed content changes and audit atomically in the owning backend operation. The current post-success `onWrite` attachment point is a best-effort notification and is insufficient for authoritative before/after audit. If audit persistence fails, the content mutation fails too; media cleanup follows its documented compensation contract.
6. A complete learning-session operation (day records, local-midnight split, time records and note additions) commits atomically in the API. MCP does not orchestrate a pretend transaction over HTTP. Separate actions such as creating a missing resource can have a confirmed partial result; report it accurately, never delete it as hidden compensation.
7. Preserve the canonical roadmap rules: statuses `planned`, `in-progress`, `completed`, `paused`, `skipped`; Prague calendar days; absolute time endpoints with offsets; no overlap. Book status is derived from dates, and book study time belongs to its linked resource.

## Evidence and gates

- **100% of applicable deterministic cases pass in ordinary CI.** Missing cases, skipped safety assertions or unsupported protocol paths are not passes. Each functional slice adds its own tests; S05 checks completeness rather than introducing security at the end.
- API route coverage walks all registered content mutations. Each new route must either participate in audited mutation handling or have an explicit reviewed non-content classification; an arbitrary new private write cannot silently skip audit.
- Capture state before/after, side-effect counts, called operation IDs and redacted audit records. Test fixtures may inspect their disposable database from the test harness, never through an MCP database tool.
- Verify container/private-edge policy with disposable configuration and probes, not just comments. Final production wiring and runtime role provisioning are verified again in phase 10; no live production network is changed by this plan.
- Model evals measure restraint and correct tool use separately. Finite passing suites are release gates, not proof against every attack.
