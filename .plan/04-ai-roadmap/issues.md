## Execution and collision notes

- Every functional slice owns its necessary schema/migrations, cohesive domain operations, authenticated API writes/public reads, generated client, rendered UI, fictional seed/loader extension, cache invalidation, tests and documentation. There are no separate database-only, API-only or test-only issues.
- [#109](https://github.com/sebelapetr/sebela.dev/issues/109) introduces the area/module/resource hierarchy and canonical progress calculation; [#110](https://github.com/sebelapetr/sebela.dev/issues/110) adds detail destinations, homepage Exploring and roadmap source links. [#111](https://github.com/sebelapetr/sebela.dev/issues/111) delivers the resource diary/time operation, which [#112](https://github.com/sebelapetr/sebela.dev/issues/112) reuses for books and [#113](https://github.com/sebelapetr/sebela.dev/issues/113) extends to events. [#114](https://github.com/sebelapetr/sebela.dev/issues/114) waits for all three time categories and reconciles their totals. [#115](https://github.com/sebelapetr/sebela.dev/issues/115) delivers the remaining supporting-content journey and assembled-domain handoff.
- The current loop is sequential. Independence in the dependency graph does not authorize concurrent edits: detail/diary work can share roadmap contracts, navigation and seed exports; bookshelf/event work can share time-target persistence, contracts, diary composition and generated clients. All backend slices can share migration metadata, package exports, module maps, seed registration and cache dependencies. Serialize these edits or assign disjoint file ownership before any future parallel run; never generate competing client/migration artifacts concurrently.
- Security, contracts and domain logic remain test-first, with real Postgres for persistence guarantees. Each carried-over page receives its own Playwright/responsive/theme comparison. Each slice verifies its own warmed-cache invalidation and fallback recovery. [#115](https://github.com/sebelapetr/sebela.dev/issues/115) checks completeness rather than postponing those obligations.
- Stable source targets and the existing mock RoadmapCard belong to this phase; live LLM, retrieval, memory and public/admin MCP implementations do not. This is a data/UI phase, so its name alone does not introduce LLM eval requirements.
- The seed format and loader grow with each owning slice. [#115](https://github.com/sebelapetr/sebela.dev/issues/115) verifies the complete fictional domain and documents the simple one-time import acceptance checklist. The external conversion mapper, owner data, real reconciliation report and actual launch import stay outside the repository/in phase 8. There is no continuous synchronization or import framework. The diary-entry replacement stays in phase 5.
- [#115](https://github.com/sebelapetr/sebela.dev/issues/115) records coverage of all 24 PRD stories, the issue PRs and verification evidence, including the phase-8 boundary for real data. No additional final-handoff issue is created.

## Running the phase

After the prerequisite owner merges, complete [#109](https://github.com/sebelapetr/sebela.dev/issues/109) interactively and obtain the overview approval. Only then does the owner start or resume the unattended AFK segment:

```bash
harness/run-phase.sh 04-ai-roadmap
```

Starting the loop before the first HITL issue is complete cannot advance the phase: the loop skips the gate and all AFK issues remain blocked. A no-eligible-issues or phase-done report alone is not evidence of completion; inspect open HITL, blocked, failed or skipped issues and the handoff criteria.

Implementation branches/PRs target `phase/04-ai-roadmap`. The orchestrator may squash-merge reviewed, green issue PRs into that phase branch; only the owner merges the final phase PR into `master`.
