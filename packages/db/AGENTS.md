# @sebela/db

PostgreSQL schema, committed migrations and persistence operations. The only package that contains SQL. Read the root `AGENTS.md` first; this file covers only what is specific to this package.

## What it is

A library used only by `@sebela/services`. It may import nothing from this repository except `@sebela/config` (dependency table in `docs/repository-structure.md`). Drizzle tables, query builders, pools and driver errors never leave it: callers receive domain records and documented results.

## Public interface

Only the subpaths declared in `exports` of `package.json` are public.

| `src/modules/profile`  | `src/modules/profile/index.ts`  | `ProfilePersistence`: find, create, update and delete the one person in `profile.persons`. A unique, always-true `singleton` column makes the database refuse a second row, so concurrent creates give exactly one success and `{ ok: false, reason: "conflict" }` for the rest. Also the ordered catalogs `profile.technologies` and `profile.topics` (private `catalogs.ts`, types in private `types.ts` re-exported by the entry): list, find, create, update and delete by slug. Also `profile.experiences` with the ordered link table `profile.experience_technologies` (private `experiences.ts`): list (current roles, `ended_on` null, first, then `started_on` desc, `ended_on` desc, slug), find, create, update and delete by slug, each read with its organization, its technologies in link order and its projects (position, then slug). Every write runs in one transaction, so an experience and its links are stored completely or not at all: the organization and the technologies are locked `FOR KEY SHARE` against a concurrent delete, an update locks its experience `FOR UPDATE` so concurrent link replacements serialize, and a refusal rolls the transaction back and is returned as `unknown_organization`, `unknown_technologies` (with the slugs), `repeated_technologies`, `invalid_period` (check constraint `experiences_period_is_ordered`), `conflict` (unique slug) or `not_found`. An update with `technologies` replaces every link in the given order; without it the links stay. The organization and technology foreign keys have no cascade, so a linked organization or technology is `referenced`; the links cascade only with their experience, and an experience that owns a project is `referenced`. Also `profile.projects` with the ordered link table `profile.project_technologies` (private `projects.ts`): list (grouped by owning experience in the experience order, then position, then slug), find, create, update and delete by slug, each read with its experience slug and its technologies in link order. A project has exactly one experience: `experience_id` is a required foreign key without a cascade (indexed), so an update that sends `experience` moves the project and nothing can leave it without an owner. Writes run in one transaction that locks the experience and the technologies `FOR KEY SHARE` and, on update, the project `FOR UPDATE`; a refusal is returned as `unknown_experience`, `unknown_technologies` (with the slugs), `repeated_technologies`, `invalid_period` (check constraint `projects_period_is_ordered`), `conflict` (unique slug across all experiences) or `not_found`. The project dates are not checked against the experience period. A linked technology is `referenced`; the links cascade only with their project, and a delete refused by a future referencing table is `referenced`. Helpers shared by records with ordered technology links (the experience order, the technology-slug lookup with its refusals, the rollback-and-return refusal and `clock_timestamp()`) live in private `relations.ts`. Postgres error codes are read in private `database-errors.ts`. Files outside modules: `config.ts` (environment validation), `connection.ts` (the `pg` pool and its Drizzle wrapper, private), `migrate.ts` (the Drizzle migrator over `migrations/`), `persistence.ts` (composes the module persistences over one pool), `testing.ts` and `cli/migrate.ts` (the migration command). Module tests build their persistence from their own entry and `connection.ts`, never from `persistence.ts`, which would close a module cycle. `drizzle.config.ts` is the tooling configuration that reads the private `schema.ts` files.

## Migrations

- Migrations are generated from the schema files and committed in `migrations/` (SQL plus Drizzle's `meta/` journal). Never edit an applied migration; change `schema.ts` and generate a new one.
- Generate: `pnpm --filter @sebela/db db:generate --name <what-changed>`. It needs no database.
- Apply: `pnpm --filter @sebela/db db:migrate`. It builds the package and runs `dist/cli/migrate.js` with the settings of the process environment, then `.env.local`, `.env` and `.env.example` of the checkout (the earlier source wins). It migrates an empty database and does nothing on an up-to-date one. The API never runs migrations when it starts.
- Each domain gets its own PostgreSQL schema (`profile`, `auth`). Drizzle records applied migrations in the `drizzle` schema.

## Adding an entity end to end

1. Add the table to the owning module's `schema.ts` and a persistence operation to its `index.ts`, with a test in the module against a temporary database. Generate the migration.
2. Add the service operation in `@sebela/services` (domain rules and errors), then contracts and routes in `@sebela/contracts` and `apps/api`.
3. Update the module maps of every touched package.

## Tests

`pnpm --filter @sebela/db test`. Every test file creates its own temporary database through `createTemporaryDatabase` with the role from the environment (a worktree role has `CREATEDB`), uses small fictional fixtures and drops the database afterwards. Tests need a running Postgres and `DATABASE_USER`/`DATABASE_PASSWORD`; there is no mocked database.
