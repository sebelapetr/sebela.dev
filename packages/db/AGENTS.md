# @sebela/db

PostgreSQL schema, committed migrations and persistence operations. The only package that contains SQL. Read the root `AGENTS.md` first; this file covers only what is specific to this package.

## What it is

A library used only by `@sebela/services`. It may import nothing from this repository except `@sebela/config` (dependency table in `docs/repository-structure.md`). Drizzle tables, query builders, pools and driver errors never leave it: callers receive domain records and documented results.

## Public interface

Only the subpaths declared in `exports` of `package.json` are public.

| Export               | Entry            | What it provides                                                                                                                                                                                                                                                   |
| -------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `@sebela/db`         | `src/index.ts`   | `readDatabaseConfig(env)` (validates `POSTGRES_HOST`, `POSTGRES_PORT`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD`; no fallbacks), `migrateDatabase(config)`, `createPersistence(config)` returning `{ profile, apiKeys, close }`, and the record types. |
| `@sebela/db/testing` | `src/testing.ts` | Test support only: `createTemporaryDatabase(config, { migrated })` creates a separate `test_<random>` database with the configured role, migrates it unless `migrated: false`, and `drop()` removes it. Never used by runtime code.                                |

| `src/modules/profile`  | `src/modules/profile/index.ts`  | `ProfilePersistence`: find, create, update and delete the one person in `profile.persons`. A unique, always-true `singleton` column makes the database refuse a second row, so concurrent creates give exactly one success and `{ ok: false, reason: "conflict" }` for the rest. Also the ordered catalogs `profile.technologies` and `profile.topics` (private `catalogs.ts`, types in private `types.ts` re-exported by the entry): list, find, create, update and delete by slug. A unique slug turns duplicate and concurrent creates into `conflict`; the check constraint `technologies_group_matches_tier` (a primary technology has a group, a secondary none) turns an inconsistent create or update into `inconsistent`; positions are non-negative. Technologies are listed by tier, group (enum order), position and slug, topics by position and slug. Also `profile.organizations` (private `organizations.ts`): list (by `lower(name)`, then slug), find, create, update and delete by slug, with a unique slug; a delete refused by a foreign key of a referencing table (code 23503) is `{ ok: false, reason: "referenced" }` and deletes nothing; a technology or topic delete refused the same way is `referenced` too. Also `profile.experiences` with the ordered link table `profile.experience_technologies` (private `experiences.ts`): list (current roles, `ended_on` null, first, then `started_on` desc, `ended_on` desc, slug), find, create, update and delete by slug, each read with its organization, its technologies in link order and its projects (position, then slug). Every write runs in one transaction, so an experience and its links are stored completely or not at all: the organization and the technologies are locked `FOR KEY SHARE` against a concurrent delete, an update locks its experience `FOR UPDATE` so concurrent link replacements serialize, and a refusal rolls the transaction back and is returned as `unknown_organization`, `unknown_technologies` (with the slugs), `repeated_technologies`, `invalid_period` (check constraint `experiences_period_is_ordered`), `conflict` (unique slug) or `not_found`. An update with `technologies` replaces every link in the given order; without it the links stay. The organization and technology foreign keys have no cascade, so a linked organization or technology is `referenced`; the links cascade only with their experience, and an experience that owns a project is `referenced`. Also `profile.projects` with the ordered link table `profile.project_technologies` (private `projects.ts`): list (grouped by owning experience in the experience order, then position, then slug), find, create, update and delete by slug, each read with its experience slug and its technologies in link order. A project has exactly one experience: `experience_id` is a required foreign key without a cascade (indexed), so an update that sends `experience` moves the project and nothing can leave it without an owner. Writes run in one transaction that locks the experience and the technologies `FOR KEY SHARE` and, on update, the project `FOR UPDATE`; a refusal is returned as `unknown_experience`, `unknown_technologies` (with the slugs), `repeated_technologies`, `invalid_period` (check constraint `projects_period_is_ordered`), `conflict` (unique slug across all experiences) or `not_found`. The project dates are not checked against the experience period. A linked technology is `referenced`; the links cascade only with their project, and a project with a case study (or another referencing record) is `referenced`. Every project read carries its case study or `null`. Also `profile.case_studies` (private `case-studies.ts`): find, create, update and delete the case study of a project, addressed by the project's slug. `project_id` is unique and a foreign key without a cascade, so a project has at most one case study, concurrent creates give exactly one success and `conflict` for the rest (insert `ON CONFLICT DO NOTHING`), and a project keeps its case study until the case study itself is deleted. A create locks the project `FOR KEY SHARE` inside its transaction and answers `unknown_project` for a missing one; update and delete answer `not_found` for a missing project or case study. The case studies of listed projects are loaded in one extra query (`loadCaseStudies`), not per project. Also `profile.explorations` (status enum `exploration_status`: `built`, `tested`, `designed`; ordered `concepts` as a `jsonb` array of strings) with the ordered link tables `profile.exploration_technologies` and `profile.exploration_topics` (private `explorations.ts`, migration `0006_explorations`): list (position, then slug), find, create, update and delete by slug, each read with its technologies and topics in link order. An exploration has no foreign key to an experience or a project. Writes run in one transaction that locks the technologies and topics `FOR KEY SHARE` and, on update, the exploration `FOR UPDATE`; a refusal is returned as `unknown_technologies` or `unknown_topics` (with the slugs), `repeated_technologies`, `repeated_topics`, `invalid_period` (check constraint `explorations_period_is_ordered`), `conflict` (unique slug) or `not_found`. An update with `technologies` or `topics` replaces every link of that kind in the given order; without it the links stay. The technology and topic foreign keys have no cascade, so a linked technology or topic is `referenced`; the links cascade only with their exploration. The services in `profile.services` with their ordered evidence in `profile.service_evidence` (private `services.ts`, migration `0007_services`): list (position, then slug), find, create, update and delete by slug, each read with its evidence in stored order and the named project (with its experience slug) or exploration resolved. An evidence row is keyed by service and position, its `kind` (enum `service_evidence_kind`: `project`, `exploration`, `link`) sets exactly its own columns (check constraint `service_evidence_matches_kind`), and partial unique indexes keep each project and exploration once per service. Writes run in one transaction that locks the named projects and explorations `FOR KEY SHARE` and, on update, the service `FOR UPDATE`; a sent evidence list replaces all rows. A refusal is returned as `unknown_projects` or `unknown_explorations` (with the slugs), `repeated_projects`, `repeated_explorations`, `conflict` (unique slug) or `not_found`. The project and exploration foreign keys have no cascade, so a named project or exploration is `referenced` on delete; the evidence rows cascade only with their service. The education records in `profile.education` (private `education.ts`, migration `0008_education`): list (position, then slug), find, create, update and delete by slug. The kind is the enum `education_kind` (`school`, `course`, `certification`, `milestone`); check constraints keep the position non-negative (`education_position_not_negative`), at least one date set (`education_period_is_dated`) and the end not before the start (`education_period_is_ordered`). Each write is a single statement whose resulting row the checks see, so a refused period is returned as `undated_period` or `invalid_period`, a taken slug as `conflict` and an unknown slug as `not_found`; nothing refers to an education record, so a delete is never `referenced`. Helpers shared by records with ordered technology links (the experience order, the technology-slug and topic-slug lookups with their refusals, the rollback-and-return refusal and `clock_timestamp()`) live in private `relations.ts`. Postgres error codes are read in private `database-errors.ts`. Files outside modules: `config.ts` (environment validation), `connection.ts` (the `pg` pool and its Drizzle wrapper, private), `migrate.ts` (the Drizzle migrator over `migrations/`), `persistence.ts` (composes the module persistences over one pool), `testing.ts` and `cli/migrate.ts` (the migration command). Module tests build their persistence from their own entry and `connection.ts`, never from `persistence.ts`, which would close a module cycle. `drizzle.config.ts` is the tooling configuration that reads the private `schema.ts` files.

## Migrations

- Migrations are generated from the schema files and committed in `migrations/` (SQL plus Drizzle's `meta/` journal). Never edit an applied migration; change `schema.ts` and generate a new one.
- Generate: `pnpm --filter @sebela/db db:generate --name <what-changed>`. It needs no database.
- Apply: `pnpm --filter @sebela/db db:migrate`. It builds the package and runs `dist/cli/migrate.js` with the settings of the process environment, then `.env.local`, `.env` and `.env.example` of the checkout (the earlier source wins). It migrates an empty database and does nothing on an up-to-date one. The API never runs migrations when it starts.
- Each domain gets its own PostgreSQL schema (`profile`, `auth`). Drizzle records applied migrations in the `drizzle` schema.

## Adding an entity end to end

1. Add the table to the owning module's `schema.ts` and a persistence operation to its `index.ts`, with a test in the module against a temporary database. Generate the migration.
2. Add the service operation in `@sebela/services` (domain rules and errors), then contracts and routes in `@sebela/contracts` and `apps/api`.
3. Update the module maps of every touched package.

## Tests

`pnpm --filter @sebela/db test`. Every test file creates its own temporary database through `createTemporaryDatabase` with the role from the environment (a worktree role has `CREATEDB`), uses small fictional fixtures and drops the database afterwards. Tests need a running Postgres and `DATABASE_USER`/`DATABASE_PASSWORD`; there is no mocked database.
