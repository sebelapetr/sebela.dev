# llm-agent

The reusable portfolio chat agent: a Python library that answers one visitor question at a time with a guarded, bounded, bilingual (EN/CS) answer over public content reads. Read the root `AGENTS.md` first; this file covers only what is specific to this package. The phase PRD is `.plan/done/06-llm-agent/prd.md`, and the eval specification is `.plan/done/06-llm-agent/evals.md`.

## What it is

- **A library, not a service.** There is no FastAPI app, no MCP server, no port and no Dockerfile. `apps/ai-service` (phase 7) and `apps/mcp-public` (phase 8) will wrap it.
- **Public content only.** Content comes over HTTP from the API's public read routes, through a handwritten allowlist on top of the generated client, the workspace package `sebela_api_client` (`packages/api-client-python`). That package holds every operation of the API, write operations included; only `llm_agent.tools.content` imports it (plus the eval harness's fixture check of `GET /v1/person`), and the agent's use stays limited to the public read operations. Python never imports `@sebela/services` or `@sebela/db` and never reaches Postgres. It holds no content-write key and sends no `Authorization` header.
- **Three stages in one LangGraph flow:**
  - Security is Claude Haiku 5.5 at `medium` effort. It classifies the question as ALLOW, BLOCK or UNCERTAIN.
  - Main is Claude Haiku 5.5 at `medium` effort (`high` until the owner's selection on #183; decision 0024). It answers through the read tools.
  - Output Guard is deterministic code with no model. It validates sources, links and blocks, and it repairs or replaces the draft. It removes from the answer text every source reference token that is not a source of this turn, in both languages. A token is `src`, up to three separators (any dash, `_` or a space, or none) and a number with any word characters after it, not inside a word; a new token right after the number ends it (`src-1src-99` is two tokens). Tokens are compared after Unicode compatibility folding (NFKC), case folding and dash folding, with invisible characters inside a token ignored: format characters (such as a zero-width space), combining and enclosing marks (such as a variation selector or the combining grapheme joiner), the Hangul fillers and the braille blank. Outside a token these characters are kept. A known limitation: prose that has the shape of a token, such as "src 2024 folder", is treated as an unknown ref and removed. A valid ref is kept in its canonical form (`src-1`). Only the site of each removal is tidied (the space before it, the separator joining it to a kept ref, or the brackets it leaves empty); the rest of the text is not edited. The removal runs again on its own result, at most four passes, so a ref rebuilt from the text around a removed one is removed too; if one still remains, the draft is replaced (`unknown_ref`). The scan is linear in the length of the text. A text left empty is replaced. It attaches the trusted contact card to every honest unknown: an `insufficient_evidence` outcome, a replaced draft, `show_contact`, and a draft whose `unpublished` flag says the specific fact the visitor asked for is not published, even when the model chose `answered`.
- **Nothing reaches the caller before the Output Guard approves it.** A classifier failure counts as unavailable. It never counts as allow.

**Limits** (`ExecutionLimits`, approved 2026-11-19):

- Deadline: 60 s for the whole execution, including the caller's admission time (`admission_elapsed_s`). Each Security attempt may take 8 s, each Main attempt 25 s, and each tool call 5 s.
- Retries: one retry for the whole execution, out of at most 5 model attempts. A `Retry-After` (or `retry-after-ms`) pause is honoured, but a retry whose pause would reach the deadline is not made, and a retried attempt never gets more time than the deadline leaves.
- Tokens: a question may have at most 1,000 tokens.
  - Security: 4,000 in, 768 out.
  - Main: 16,000 in, 8,192 out.
  - Execution total: 80,000 in, 16,384 out.
  - History: at most 6 complete exchanges and 6,000 tokens (3,000 under UNCERTAIN). Selection keeps the newest exchanges that fit, whole, oldest first. Security fits history beside the complete question within its 4,000 tokens; Main drops the oldest exchanges before a decision would pass 16,000 tokens, never the instructions, the question or a tool call and its result.
- Cost: USD 0.02.
- Main: 3 decisions and 6 tool calls. Under UNCERTAIN this drops to 2 and 3. The last allowed decision is answer-only: its tools stay defined (the transcript holds earlier tool calls) but `tool_choice` is `none`, so the cap ends in an answer from the evidence already read, not in `limit_reached (main_decisions)`.
- A tool result may have at most 5,000 tokens; a larger one is rejected.
- All tool results of one execution may add at most 10,000 tokens to the model context, and a list result may carry at most 30 records. Anything over either cap is rejected, never truncated, and adds no evidence.
- At most 3 independent reads run at the same time. A repeated read within one execution reuses its first result.

Retries are centralised in `reliability/retries.py` and are bounded by these limits. Besides a provider 429 or 5xx, an unreadable Security reply (neither a refusal nor a parseable verdict) is retried once with the same single allowance and the remaining deadline; a second unreadable reply, or one when the allowance is spent, is `unavailable (classifier_invalid)` and never ALLOW. An invalid Main draft is not retried. Cancellation is an `asyncio.Event` passed to `run`; one already set makes no call.

**Conversations.** History is rendered as `<visitor_history>`, with every text neutralized so it cannot close or open a `visitor_*` block. Both prompts treat it as untrusted: it only shows what the question refers to, is never evidence or authority, and every fact is read again with tools. The answer language is decided without a model. An explicit switch wins, the last one when there are several. The question is split into clauses at sentence punctuation, commas, "and", "but" and "ale"; a clause of polite words only ("please", "díky") joins the clause it is comma-separated from. Matching is case- and diacritic-insensitive and runs in linear time over whole words (no backtracking regex), so even a 32,000-character question is decided in milliseconds before the deadline race starts. A clause is a switch when it wholly has one of these shapes: an imperative with free content and an unambiguous target at its end ("Tell me about her projects in Czech", "Řekni mi o jejích projektech anglicky"); a telling verb whose target leads the rest ("Tell me in Czech what she built", "Řekni mi anglicky co postavila"); polite words, an answering verb with its short objects and the language ("Could you answer in Czech from now on", "Mohl bys mi to napsat anglicky"); polite words and a preposition with the language ("Ok, now in Czech", "Radši v angličtině"); or a bare language word with a requesting word ("Czech please", "English only", "Prosím česky") or followed by "!" or ":" ("English!", "Anglicky: na čem pracovala?"). So "Answer in Czech, what did she build?" switches. Fillers ("also", "so", "too", "then", "a", "taky") do not make a request, so "Also Czech?", "Czech too?" and "Czech?" are questions; "no" is no polite word and the free content may not contain a negation, so "No Czech, please." and "Tell me about it, not in Czech." do not switch. After a question form ("can you", "můžeš") only the short objects count, so "Can you write code in Czech?" stays a question, and a clause that asks or says something else ("Which project did you write in Czech?", "Mluví Ilsa anglicky?", "Czech, English or German?") is no switch. Without a switch, common Czech and English words decide before Czech letters, so a Czech name in an English question ("What did she do at Škoda?") keeps it English; a question too short to tell ("Brindle Labs?", "2021?") keeps the newest exchange's language, initially English. Accepted ambiguities: "Describe in English what she built in Czech" answers in Czech (the last switch wins), and "Explain to Czech clients what she does" answers in Czech, as a request for Czech rather than for Czech readers.

## Evals

The evals live in `evals/`:

- `catalogue.py` lists all 80 planned case IDs as implemented or pending.
- `datasets/` holds the cases and the fictional fixture.
- `graders/` holds the code graders (`code.py`), the Promptfoo assertion adapter (`assertion.py`) and the Sonnet rubric (`rubric.py`).
- `gate.py` applies the gates.
- `budget.py` keeps the campaign ledger and enforces one ceiling per phase campaign; `campaigns.json` holds the campaigns (the phase loop's steward reads it too).
- `judging.py` buys the rubric judgements of one chunk of a paid run: one Message Batches API batch (the default) or direct calls (`--judge-mode direct`), with the reservation and charging rules (Policy, Judge cost).
- `anomaly.py` holds the early anomaly stop of a paid run (Policy, Early stop).
- `comparison.py` holds the Main-model comparison: its fixed subset with a rationale per case, the candidates, their comparison-only execution limits, the expected cost and the side-by-side report that merges slices.
- `run.py`, `provider.py` and `promptfooconfig.yaml` hold the runner. Promptfoo drives the cases.

Gates (`.plan/done/06-llm-agent/evals.md`):

- Every critical case passes in 100% of its repeats.
- Useful ordinary answers reach at least 90%, separately for EN and CS.
- Supported citations reach at least 95%.
- False blocking is at most 5% per language.
- Every case runs 3 independent repeats. A Main-model comparison repeats once and is never a gate (Policy).

Policy:

- **Which cases run.** An issue runs only the cases it affects: `--case` per ID, 3 repeats each.
- **Main-model comparison (issue #183, owner-approved screening; [owner decision on comparing Sonnet](https://github.com/sebelapetr/sebela.dev/issues/183#issuecomment-7061361495), 2026-11-21).** `--compare <candidate>` runs the fixed subset `comparison-v1` of `evals/comparison.py`: 20 implemented cases, 10 families in EN and CS (Q01, Q04, Q15, Q17, S01, S04, S05, S15, S18, S20), 1 repeat each. The direct attacks S08–S14 are left out, because the fixed Security stage stops them before Main. Only the Main stage changes; Security stays Haiku 5.5 `medium` and the judge stays the Sonnet 5.5 `medium` rubric. The candidates are `haiku-medium` (the pinned baseline, the Main default since the selection below), `haiku-high` (the default and baseline when the comparison ran) and `sonnet-medium`; Sonnet uses the judge's pinned prices. The summary has mode `compare`, gate scope `comparison` and `pass: false` whatever the figures are; its `comparison` block records the candidate's model and effort, useful/citation/false-blocking/critical counts and rates per language, latency p50/p95, cost, case-runs expected and recorded, `limit_reached` and the execution limit. The selected configuration then runs the whole catalogue with 3 repeats on the phase pull request; only that run can pass the gates.
  - **Comparison-only execution limit.** Each candidate's execution limit is derived from its pinned prices and the caps: one Security call at 4,000 input and 768 output tokens at Security's prices, plus every allowed Main decision (`main_decisions`, 3) at the 16,000-token input cap as tool results grow the context, the Main input bounded by the execution's 80,000-token input cap and the Main output by its 16,384-token aggregate output cap. The budget reserves the whole output cap before each decision, so this is what a tool-using answer needs. Where that worst case fits the default USD 0.02 (both Haiku candidates, USD 0.0138), the run uses the default `ExecutionLimits`. For `sonnet-medium` it is USD 0.2606, built by `ComparisonLimits` in `evals/` and handed to the agent only by the comparison runner. Retries are not added: a retry after an attempt of unknown usage may still stop as `limit_reached`, as it does under the defaults, and the summary counts those runs. The public request schema and every ordinary run keep the USD 0.02 cap (`ExecutionLimits`, tested); `ChatAgent.run` trusts the limits it is given and does not revalidate them.
  - **The per-run limit and slices.** A comparison whose reservation exceeds the owner's USD 1.00 per-run limit is refused with exit 2, and the message lists slices of the subset that fit. The limit is checked on the whole comparison's reservation, since a comparison is an issue run; the declared allowance is then reserved chunk by chunk like any paid run (Reservation per chunk below). The Haiku candidates reserve USD 0.69 each in batch judge mode (20 subject runs at USD 0.02 plus 8 batched judge calls) and run whole; they are expected to cost about USD 0.12 each. The whole Sonnet subset would reserve USD 5.50, so `--compare sonnet-medium` runs in seven `--case` slices (an ID outside the subset or named twice is refused with exit 2): `Q01-en Q01-cs Q04-en`, `Q04-cs Q15-en Q15-cs`, `Q17-en Q17-cs S01-en`, `S01-cs S04-en S04-cs`, `S05-en S05-cs S15-en`, `S15-cs S18-en S18-cs` and `S20-en S20-cs` (batch-mode reservations USD 0.89, 0.89, 0.85, 0.78, 0.78, 0.78 and 0.52; `--judge-mode direct` needs eight slices, and the refusal message lists them). Expected cost, from #181's per-case tokens and #182's judge cost: about USD 0.70 for all seven. `--compare-report` merges the slices of one candidate into one column, refusing a case recorded twice.
  - **Selecting Sonnet as the Main default** is a separate, versioned configuration change with its own execution-limit decision; the comparison limit does not carry over.
  - **Report and exit codes.** A finished comparison prints `comparison (not a gate)` with the case-runs recorded against those expected, `limit_reached` and the execution limit. Exit 0 when every expected case-run was recorded without an extra failure, 1 when a run is short or failed, 2 when it is blocked (an option error, the per-run limit, the allowance, a fingerprint whose Main model or effort does not match the candidate). `--compare-report` exits 2 when the summaries differ in anything other than the Main model, effort and execution limit (runtime, prompts, tools, guard, Security, pricing, dataset, expectations, judge, subset, repeats), or when a summary is not JSON or is incomplete.
  - **Comparison answers are never pooled.** Each stored answer carries `comparison: {version, candidate}` and the candidate's `main_model`/`main_effort`; `--regrade` and an issue or gate pool refuse them.
- **Judge cost (issue #183, [owner decision on the eval cost controls](https://github.com/sebelapetr/sebela.dev/issues/183#issuecomment-7064345423)).**
  - **Batches.** After the subject runs of a chunk, every judge request of that chunk goes into one [Message Batches API](https://docs.anthropic.com/en/docs/build-with-claude/batch-processing) batch at half price; `custom_id` is `<case>-r<repeat>`, and results are matched by it, never by position. The runner polls every 30 s for at most 60 min, then cancels the batch, waits up to 10 min for the cancel to end it and keeps the results that succeeded before it: those are charged measured cost, the others fail with `did not end within 3600 s`. When the cancel itself fails after its retries (for example repeated HTTP 409), the batch's status is retrieved once more: if it has ended, its results are read and the succeeded ones charged measured cost as above; otherwise every request is charged its whole reservation as uncertain. Retrieve, results and cancel are idempotent and are retried on a transient error (HTTP 408, 409, 429 or 5xx, a lost connection, a timeout) after 2, 4, 8, 16 and 32 s; the results are read whole again, so nothing is charged twice. Create is retried only on 429 and 529, which prove no batch was made; any other create failure may have bought a batch and is not repeated. A batch that cannot be created or whose state cannot be read after the retries, and each errored, cancelled, expired or missing result, is a visible failure of that case-run (never a pass) and is charged its whole reservation as uncertain; only succeeded results are charged measured cost. The judge model, effort, instructions, rubric and input hash are the same as in a direct call, so batch and direct judgements stay comparable; a stored judgement records `batch` and, in a batch, its `batch_id`. `--judge-mode direct` keeps one direct call per request for debugging, at full price. The subject is never batched, so its latency stays measured.
  - **Prompt caching.** The judge request has two cache breakpoints: after the fixed system block (instructions and rubric) and after the case's question and evidence, so the 3 repeats of a case share a prefix and only the answer differs. Inside a batch the breakpoints use the 1-hour TTL, in a direct call the 5-minute one. The prompt is split into content blocks only: the judge now receives two user blocks (question and evidence, then the answer) instead of one, but the JSON keys keep their order, so `input_hash` and the rubric version `rubric-v5` are unchanged and judgements stored before this change stay compatible (regradable and comparable). Caching is best-effort and may raise or lower the judge cost: a 1-hour cache write in a batch costs 2× × 0.5 = 1.0× the base input price against 0.5× for the same tokens uncached, so a written prefix that is never read costs more; the fixed instructions block is probably below Sonnet's minimum cacheable length and then is simply not cached, and a batch whose requests are processed apart reads nothing. The reservation prices the whole input bound as a 1-hour write, so it covers the worst case either way. Cost is priced from the reported usage: cache writes at 1.25× (5 minutes) or 2× (1 hour) the input price, cache reads at 0.1× (`rubric.py`, pricing `JUDGE_PRICING_VERSION`), and the batch discount of 0.5 applies on top of every token, cache tokens included.
  - **Reservation.** A judge call reserves its upper bound in its mode: the 8,000-token input bound priced as a 1-hour cache write plus the whole output cap, halved in batch mode (`run.JUDGE_CALL_RESERVATION_USD`, `JUDGE_DIRECT_CALL_RESERVATION_USD`). A run's reservation and its comparison slices follow `--judge-mode`; `direct` needs more slices.
  - **Expected cost and reservation of the full 80 × 3 run.** Expected about USD 1.07: 240 subject runs at #181's mean tokens (about USD 0.37) plus 120 judged case-runs at #182's mean judge cost, halved (about USD 0.70); direct judging would be about USD 1.77. Caching is not counted in the estimate, since it may raise or lower it. The whole run's upper bound is USD 9.18 in batch mode (USD 13.56 with `--judge-mode direct`), but it is never reserved at once (Reservation per chunk below): the largest chunk reserves at most USD 0.68 (12 subject runs at USD 0.02 plus 12 batched judge calls), so the run starts under a realistic allowance such as USD 2.00 and runs in one go.
- **Reservation per chunk (issue #183, [owner decision on the per-chunk reservation](https://github.com/sebelapetr/sebela.dev/issues/183#issuecomment-7064482195)).** Every paid run (ordinary `--case`, `--all`, a comparison and `--regrade --judge`) is split into the early chunk (the cases of the first 6 case-runs, Early stop below) and then bounded chunks of at most 12 case-runs (`run.CHUNK_CASE_RUNS`: 4 cases at 3 repeats, 12 at 1 repeat). Each chunk reserves its own subject executions and judge calls just before it starts (the formula above; a regrade reserves the judge requests its chunk still needs), then runs its subject runs and then its batch judging. Only the early chunk has to fit before anything starts; a smaller allowance refuses the run with exit 2 before the test API starts and nothing is charged. One test API serves the whole run. When the next chunk's reservation no longer fits what remains of the allowance, the run stops: it prints `stopped: allowance: …`, records the reason in the summary (`stopped`), lists that chunk and every later case under `pending` and exits 2. The gate fails and pending cases are never passed. The local ledger keeps one entry per run, rewritten before and after every chunk, with a `chunks` list of each chunk's cases, case-runs, reservation, measured and uncertain charge. Before a chunk starts, the entry counts that chunk at its whole reservation as spent and uncertain (`provisional_usd`, the chunk marked `provisional`); when the chunk ends, its measured charge replaces that. An interrupted or killed run therefore never under-counts: its unfinished chunk stays counted at its whole reservation. An allowance below the early chunk's reservation refuses the run with exit 2 before anything starts; nothing is spent and no ledger line is written.
- **The per-run limit of USD 1.00 ([owner decision](https://github.com/sebelapetr/sebela.dev/issues/183#issuecomment-7064482195)).** It applies to issue runs (an issue's affected cases and a Main-model comparison), which run in slices when their reservation would exceed it (Pooled slices below). It does not apply to the full phase-PR run, `--all`, which runs every implemented case in one go under the declared allowance. The runner refuses a comparison whose reservation exceeds it. From phase 7 on it also caps every issue run (`--stage issue`, the default) at the campaign's per-run stop: the run's allowance is at most USD 1.00, so it stops with the rest pending once the next chunk's reservation no longer fits (Budget below), and the developer slices the cases. The finished phase-6 campaign has no such cap in code.
- **Wall time and the run deadline (issue #183).** A paid run or `--regrade --judge` has an overall deadline, `--deadline-minutes` (default 150, `run.DEADLINE_MINUTES`). It is checked before every chunk after the early one; once it has passed, no further chunk starts: the run prints `stopped: deadline: …`, records it in the summary (`stopped`), lists that chunk and every later case under `pending`, writes the summary and the ledger and exits 2, so the gate fails. A chunk that has started always finishes: its subject runs (about 1.5–3 min for 12 case-runs) and then, when it has judged cases, its batch (at most 60 min of polling plus 10 min for the cancel). `--all` is about 21 chunks, about 13 of them with a judge batch. Expected wall time: about 50 min of subject runs plus a few minutes per batch, roughly 1–2 hours (batch latency of the full run is not measured yet). Worst case: the deadline plus one chunk, about 150 + 76 = 226 min. A run that reaches the deadline is resumed with `--case` for its pending cases.
- **One run per checkout.** Concurrent paid runs in one checkout are unsupported: each opens its allowance from the same ledger, so both could spend the same remainder. Run paid evals one at a time per checkout. The ledger itself is rewritten under a lock (`ledger.json.lock`) and replaced in one step, so two runs do not lose each other's entries.
- **Runs that never started (issue #183, [owner decision on the eval cost controls](https://github.com/sebelapetr/sebela.dev/issues/183#issuecomment-7064345423)).** When the test API does not start, the fixture person cannot be read or the fixture check fails before Promptfoo starts, nothing is charged: the ledger records scope `not started`, the summary has `started: false` and the failure `not started: <reason>`, and the run exits 2. Once Promptfoo has started, unmeasured cost consumes its whole reservation as before.
- **Early stop (issue #183, [owner decision on the eval cost controls](https://github.com/sebelapetr/sebela.dev/issues/183#issuecomment-7064345423)).** A paid run (also a comparison and a `--regrade --judge`) runs its first chunk first: the cases holding the first 6 case-runs (2 cases at 3 repeats, 6 at 1 repeat). After that chunk, and only when cases remain, the run stops when 2 or more of the first 6 case-runs ended `limit_reached`, `unavailable` or with a provider error, when any judge request failed, or when the uncertain cost exceeds 10% of the measured cost. A single subject run whose cost was not measured consumes its whole USD 0.02 reservation as uncertain, while a first chunk is expected to measure only a few cents (6 subject runs at about USD 0.0015 plus their judgements), so one such run in the first chunk is enough to stop the run. It prints `stopped: <reason>`, records it in the summary (`stopped`), lists the remaining cases under `pending` and exits 2; pending cases are never passed. The summary also records `judge_mode`. There is no flag to turn the stop off.
- **Grader fixes.** A deterministic grader fix is checked with a free `--regrade`.
- **Pooled slices (proposed method, pending owner confirmation in the #179 pull request).** When an issue's affected cases would reserve more than the USD 1.00 per-run limit, they run in slices; the full phase-PR run (`--all`) is not sliced. All slices must share one fingerprint: the same subject, dataset and rubric versions. Their `answers/*.json` are copied into one folder, and a free `--regrade <folder>` grades the pool. The gates apply to the pool, not to each slice, and a slice may fail its own gates. When a case is rerun, its new answers replace the old ones in the pool. Answers with another fingerprint are never pooled.
- **Model judging.** A changed rubric is judged again with `--regrade <run> --judge --campaign <phase-folder> --allowance <usd>`. That is paid and charged to the campaign.
- **When answers become incompatible.** The dataset version hashes only what the agent sees (question, language, fixture and allowed tools). Changing an expectation keeps stored answers regradable. The subject versions include a `runtime` fingerprint of every module of `src/llm_agent/` and of the generated client `sebela_api_client` (`runtime_sources()` in `pipelines/chat/versions.py`), and the `pricing` version, so any change to the package code (a prompt, a model setting, a guard rule, a tool projection) needs fresh answers. A dependency upgrade in `uv.lock` is not fingerprinted: bump the package version with it.
- **Budget.**
  - **A ceiling per phase campaign** ([decision 0026](../../docs/decisions/0026-eval-cost-controls-for-later-phases.md), point 7; issue #371). `evals/campaigns.json` names every campaign after its phase folder with its ceiling, its cumulative stop for issue runs and its per-run stop for issue runs: `06-llm-agent` USD 13.00 (the finished phase-6 campaign with the ceiling the owner set in issue #183, no stops in code), `07-ai-service` USD 4.00 with USD 1.50 for issue runs and USD 1.00 per issue run, `07.1-jev-gateway` USD 2.00 and `08-mcp-public` USD 2.30, both with USD 1.00 per issue run. A later phase gets its entry when its budget is approved. Phase 7's USD 0.50 margin, released only by the owner, is not a separate bound in code: the owner keeps it through the allowance a run declares.
  - **A paid command names its campaign and stage.** `--campaign <name>`, or the environment variable `SEBELA_EVAL_CAMPAIGN`, which the phase loop sets to its phase; both may be given when they agree. `--stage issue` (the default) is work on an issue; `--stage phase-pr` is the full run at the phase pull request and its affected rerun, which the owner starts; the runner takes the stage as declared, and the guard refuses the option to the phase loop and to subagents (`docs/permissions.md`, Denied). A paid command that names no campaign, an unknown one or two different ones is refused with exit 2 before anything starts: there is no default campaign and no fallback to a larger ceiling. A free regrade, `--check-fixture` and `--compare-report` need none.
  - **One ledger, scoped per campaign.** Every entry of the local ledger (`.tmp/evals/llm-agent/ledger.json`) records its campaign and stage; an entry written before campaigns were named belongs to `06-llm-agent`. A run counts only against its own campaign, so one phase cannot spend another's acceptance run.
  - **Other worktrees, in the phase loop.** A worktree's ledger knows only its own runs. The phase loop keeps every run it has seen in every checkout (`.worktrees/logs/<phase>/eval-spend.json`, written by the steward at its checks, before each iteration and after it) and names that record in `SEBELA_EVAL_KEPT_RUNS`; the runner adds to its own ledger's sum every run in it that its ledger does not hold — the runs of the other checkouts, and those of an earlier worktree in the same folder (`budget.kept_runs`; a run whose id is in the ledger is read from the ledger) — so the ceiling and the cumulative stop for issue runs hold across the issue worktrees. A record that cannot be read is a block (exit 2); one that does not exist yet adds nothing. The steward replaces the record in one step and starts a damaged one again at its next check, so the block does not last. Outside the loop the variable is not set and both hold per checkout: the declared `--allowance` carries the rest. The steward, which reads every ledger, is what stops the loop at the issue stop (`docs/testing.md`, Running paid evals, What is enforced where).
  - **What a run may spend.** The smallest of: the declared remaining allowance (`--allowance`, refused above the campaign's ceiling), what the ledger leaves of the campaign's ceiling and, for an issue run, what the ledger leaves of the cumulative stop for issue runs and the per-run stop. An exhausted ceiling or issue stop is a block that names it (exit 2); the coverage stays pending and never passes.
  - **The spend line.** A paid run prints `spend: expected <usd> before the run; <usd> of the <campaign> ceiling (<usd>) remain` when it starts and `spend: expected <usd>, actual <usd> (uncertain <usd>); <usd> of the <campaign> ceiling (<usd>) remain` with its summary; the summary's `cost` block carries it (`spend_line`, with `campaign`, `stage`, `ceiling_usd`, `expected_usd` and `campaign_remaining_usd`) and the ledger entry records `expected_usd`. Put the final line into the issue comment and the pull request. The expected cost is an estimate from measured means (`run.expected_usd`), not the reservation.
  - Unmeasured cost consumes its whole reservation.
  - Each chunk is reserved just before it starts (Reservation per chunk above).
  - A missing key or an exhausted allowance is a visible block (exit 2), never a pass.
- **CI.** The job `Python agent model evals` of `model-evals.yml` runs `--all` on the phase pull request into `master`, or on manual dispatch. Its campaign is the phase folder of the pull request's head branch `phase/<phase-folder>` at the stage `phase-pr`, or the dispatch inputs `campaign` and `stage`; without a known campaign the job is a visible block. Its allowance comes from the dispatch input or the repository variable `LLM_AGENT_EVAL_ALLOWANCE_USD`, which the owner sets to that campaign's remainder before making the phase pull request ready. Since the run reserves per chunk, it fits a realistic allowance (it is expected to cost about USD 1.07; a chunk reserves at most USD 0.68); when the allowance runs out mid-run the rest is pending and the job fails. A CI runner has no ledger, so after every run the owner sets that variable to the remainder the job log names (the notice `llm-agent eval allowance`), or the next run could spend the same allowance again. It uploads only the redacted `summary.json`, which also reports the latency p50 and p95 of the case-runs, and the ledger. Wall time: the run's 150-minute deadline plus at most one chunk (about 76 min) bounds the eval step, which has `timeout-minutes: 240`; the job has 270. Expected about 1–2 hours like a local `--all`. The allowance notice and the summary upload run even when the eval step fails or times out (`if: always()`); without a summary, the notice is computed from the ledger, which counts an unfinished chunk at its whole reservation.
- **Storage.** Answers stay in the git-ignored `.tmp/evals/llm-agent/`, written only after a credential scan.

## Tests

- `tests/unit/` runs on scripted fakes at the model and content boundaries. It covers the following:
  - allow, block, uncertain and classifier failure;
  - provider 429 and 5xx responses;
  - invalid and oversized tool results;
  - repair and replace;
  - every cap, the deadline and cancellation;
  - two isolated concurrent runs;
  - history selection, trimming, forged history and the language switch (`test_conversation.py`);
  - admission time, Retry-After, attempt/token/cost caps, a responsive event loop, cancellation during reads and telemetry failure (`test_execution_limits.py`);
  - the contact card on every honest unknown, including an `answered` draft flagged `unpublished`, and none on an ordinary evidenced answer or a refusal;
  - unknown source refs removed from the text in EN and CS and in any case, dash or Unicode variant, valid ones canonicalised, only the removal sites tidied, no ref rebuilt by a removal, and linear time (`test_output_guard.py`, `test_chat_agent.py`);
  - the retried unreadable classifier reply, no retry when the deadline cannot hold the backoff, and the answer-only last Main decision (`test_chat_agent.py`, `test_model_factory.py`);
  - that no unapproved draft is delivered.
- `tests/integration/` calls the generated client and the agent against the real API, which serves the fictional fixture on a temporary database.
- `tests/evals/` tests the eval code itself: the catalogue, the graders, the rubric, the gate, the budget, the runner and the S10 impersonation grader (`test_impersonation_grader.py`: recorded and constructed refusals, real impersonation in EN and CS, linear time), the Main-model comparison (`test_comparison.py`: subset size, languages and families, option errors, repeat count, scope `comparison`, the comparison-only limits over every Main decision with the real budget and the public cap, the per-run refusal and suggested `--case` slices, record marking and fingerprint checks, report consistency, slice merging and the recorded versions). Paid calls are faked.

Pitfall: a module-scoped async fixture needs `@pytest_asyncio.fixture(scope="module", loop_scope="module")`, and its tests need `@pytest.mark.asyncio(loop_scope="module")`. Otherwise the fixture's event loop is closed under the test.
