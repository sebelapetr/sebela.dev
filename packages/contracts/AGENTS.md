# @sebela/contracts

Zod schemas and types shared by the API and its clients. Read the root `AGENTS.md` first; this file covers only what is specific to this package.

## What it is

A library with no runtime dependencies in this repository except `@sebela/config` for tooling (dependency table in `docs/repository-structure.md`). It knows nothing about HTTP routing, services or the database: it defines what crosses the API boundary. The API validates requests with these schemas and generates its OpenAPI document from them, so a schema change is a contract change and updates the OpenAPI expectations in `apps/api`.

## Public interface

Only the root export `@sebela/contracts` (`src/index.ts`) is public.

| Export                                                                                                                                | What it provides                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PersonSchema`, `PersonCreateSchema`, `PersonUpdateSchema`, `PersonLinkSchema`                                                        | The person as returned (ISO timestamps, `null` for an unset optional field) and the write bodies. Write bodies are strict: unknown fields are rejected. An update needs one field.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `Person`, `PersonCreate`, `PersonUpdate`, `PersonLink`                                                                                | The inferred types; the write types are the parsed outputs, with defaults applied.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `TechnologySchema`, `TechnologyListSchema`, `TechnologyCreateSchema`, `TechnologyUpdateSchema`, `technologyTiers`, `technologyGroups` | A catalog technology as returned and its write bodies: a lower-case hyphenated slug (immutable, not in the update), the `primary`/`secondary` tier, the `core`/`ai_engineering_focus` group that a primary entry needs and a secondary one must not have, an optional static website-logo key (a key, not a URL or upload) and a non-negative integer position. Strict bodies; an update needs one field; a list is a plain array.                                                                                                                                                                                                                                                                                                                                                                    |
| `TopicSchema`, `TopicListSchema`, `TopicCreateSchema`, `TopicUpdateSchema`                                                            | A profile topic as returned and its write bodies: slug, name and position, with the same slug and position rules.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `OrganizationSchema`, `OrganizationListSchema`, `OrganizationCreateSchema`, `OrganizationUpdateSchema`                                | An organization as returned and its write bodies: slug, a name of at most 200 characters, an optional `http`/`https` website with a domain host and an optional Markdown description of at most 5000 characters (`null` when unset). Strict bodies, so a logo reference is refused until media exists; an update needs one field and cannot change the slug; a list is ordered by name ignoring case, then slug.                                                                                                                                                                                                                                                                                                                                                                                      |
| `ExperienceSchema`, `ExperienceListSchema`, `ExperienceCreateSchema`, `ExperienceUpdateSchema`, `experienceKinds`                     | An experience as returned, with its `Organization` and its `Technology` list resolved in link order, and its write bodies, which name the organization and the technologies by slug: title, the `main_job`/`side_project`/`own_business` kind, ISO `startedOn`, `endedOn` (`null` for a current role), a Markdown summary, ordered plain-text responsibilities, `inCv`. Strict bodies; the end is not before the start and each technology is listed once when the body carries them. A create defaults the end to `null` and responsibilities and technologies to empty; an update needs one field, cannot change the slug, and a sent `technologies` list replaces every link while an omitted one keeps them. A list puts current roles first, then the latest start, the latest end and the slug. |
| `SlugParamsSchema`                                                                                                                    | The `{slug}` path parameter of a catalog record.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `Experience*`, `Organization*`, `Technology*`, `Topic*`, `TechnologyTier`, `TechnologyGroup`, `SlugParams`                            | The inferred types of the schemas above.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `ErrorResponseSchema`, `errorCodes`, `ErrorCode`, `ErrorResponse`                                                                     | The common error shape of every failed request and the full list of error codes, each with its fixed status (documented in `src/errors.ts`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

Schemas carry an OpenAPI component id through `.meta({ id })`; keep ids stable, because they name components in the generated document.

## Module map

| Module                | Entry                          | Responsibility and hidden decisions                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Depends on | Tests                                                                                                                                                               |
| --------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/modules/profile` | `src/modules/profile/index.ts` | The person contract: field limits, trimming, `http`/`https` links with a domain host, ISO date of the career start, defaults of a create and the partial update. The technology and topic catalog contracts (private `catalogs.ts`): slug and logo-key formats, the tier/group rule, positions and the slug path parameter. The organization contracts (private `organizations.ts`): field limits, the website format and the strict bodies. The experience contracts (private `experiences.ts`): kinds, ISO dates and the period rule, relations written by slug and read resolved, unique technologies and the replace-or-keep update semantics. Shared field schemas (trimmed bounded text, `http`/`https` URL, key, slug, timestamps) live in private `fields.ts`. | `zod`      | `src/modules/profile/index.test.ts`, `src/modules/profile/catalogs.test.ts`, `src/modules/profile/organizations.test.ts`, `src/modules/profile/experiences.test.ts` |

Files outside modules: `errors.ts` (the common error contract, shared by every module, tested in `src/errors.test.ts`) and `index.ts` (the public export).
