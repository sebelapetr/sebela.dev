# @sebela/contracts

Zod schemas and types shared by the API and its clients. Read the root `AGENTS.md` first; this file covers only what is specific to this package.

## What it is

A library with no runtime dependencies in this repository except `@sebela/config` for tooling (dependency table in `docs/repository-structure.md`). It knows nothing about HTTP routing, services or the database: it defines what crosses the API boundary. The API validates requests with these schemas and generates its OpenAPI document from them, so a schema change is a contract change and updates the OpenAPI expectations in `apps/api`.

## Public interface

Only the root export `@sebela/contracts` (`src/index.ts`) is public.

## Chat contract

The chat's application contract is defined in phase 3 and has no API route yet: the website's browser-local mock implements it, and phase 7's API transport and website adapter implement the same events. Nothing here knows about the transport (server-sent events, fetch, framing); an adapter turns its framing into these events, and the website validates each one with `ChatStreamEventSchema` before it changes a conversation.

- **Submission.** `ChatSubmissionSchema`: `conversationId` (random UUID from the client; identifies, never authorises), `requestId` (UUID for this one question; a retry reuses it, so phase 7 can make it idempotent) and the trimmed `question`.
- **Events.** Each carries `requestId`, the assistant `messageId` and an `eventId` that grows with arrival. `start` opens the answer; `text_delta` appends text; `block` delivers one complete typed block; `sources` (once) delivers the Sources block's payload; `related` (once) one or two onward links; `complete` ends with an outcome (`answered`, `insufficient_evidence`, `refused`, `unavailable`); `error` ends with a stable code and `retryable`.
- **Guarantees an adapter keeps.** An attempt starts with `start`, or fails at once with `error` (a failure before the first event). Exactly one terminal event ends it and nothing follows it. A stream that ends without one is an interruption, never a silent success. Events of one attempt arrive in order; a repeated `eventId`, or any `eventId` not above the last accepted one (even one never seen), is a duplicate the client ignores rather than an order violation. `advanceChatAttempt` applies these rules one event at a time; `validateChatStream` checks a whole recorded stream and is the scenario check a real adapter must pass.
- **Safe content.** Block, source and link addresses are site paths or `http`/`https` addresses; no other scheme, protocol-relative address or backslash trick validates. Text is plain text; the website renders it without HTML.

## Website invalidation contract

What the API (`apps/api`, "Website invalidation") sends the website after a committed content write, so the website can refresh its cached pages. Nothing here knows about caches or routes: the receiver maps each validated change to its own explicit dependency map and never treats anything in a notification as an address or cache key.

- **Request.** `POST` with `content-type: application/json`. The body is the UTF-8 JSON of an `InvalidationNotification`, at most `invalidationMaxBodyBytes` (4,096) bytes. Headers: `sebela-invalidation-timestamp`, whole seconds since the epoch at signing, and `sebela-invalidation-signature`, `v1=` followed by the lower-case hex HMAC-SHA256, keyed with the shared secret, of the timestamp, a `.` and the exact body bytes.
- **Notification.** Strict: `eventId` (UUID, new per notification and kept by its retries), `occurredAt` (ISO date-time) and `changes`, 1 to 16 `ContentChange`s. A change is `{ domain, record, action }`: `domain` one of `contentDomains` (`person`, `technology`, `topic`, `organization`, `experience`, `project`, `case-study`, `testimonial`, `exploration`, `service`, `education`, `current-focus`, `roadmap-area`, `roadmap-module`, `roadmap-resource`, `roadmap-book`, `roadmap-event`, `roadmap-diary`, `roadmap-project-idea`, `roadmap-followed-source`, `roadmap-glossary-term`, `media`), `record` `null` for the person, a UUID for media, a `YYYY-MM-DD` date for a learning diary day (also when one of its time entries changed) and a slug otherwise (a case study by its project's slug), `action` `created`, `updated` or `deleted`. A change names only the written record, never the records it was or is related to, so a receiver that must cover relation changes and deletions invalidates everything that may depend on the domain, or the whole profile.
- **Secret.** A dedicated, server-only secret of at least `invalidationSecretMinLength` (32) characters, shared by the API and the website only. Signing or verifying with a shorter one throws.
- **Verifying.** `verifyInvalidationNotification({ secret, body, timestamp, signature, now })` takes the raw body bytes as received (read with a bound of `invalidationMaxBodyBytes`, before any parsing) and the two header values, and returns `{ ok: true, notification }` or `{ ok: false, reason }`. It checks in this order: `payload_too_large` (the body exceeds the limit), `missing_signature` (a header is missing or empty), `stale` (the timestamp is not whole seconds or lies more than `invalidationToleranceSeconds`, 60, from `now`), `invalid_signature` (any other scheme, length or alphabet, or a mismatch, compared in constant time), then `malformed` (a correctly signed body that is not a valid notification). Only an `ok` result may invalidate anything.
- **Delivery.** At least once, unordered across retries; a retry keeps `eventId` and the body bytes with a fresh timestamp and signature. A receiver answers 2xx when it accepted the notification and 4xx when it refused it; the API retries only on network errors, timeouts, 5xx and 429. A duplicate or out-of-order notification must be harmless: invalidation means "refetch current data", never "apply this data".
