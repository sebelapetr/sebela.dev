# Testing

What is tested, in which order, and how.

## Principle

Test external behaviour, not implementation: an HTTP request and its response, a rendered page, a tool call and its result, a function's output for an input. A test that breaks when code is refactored without changing behaviour is a bad test.

The project exists to ship a good product. The rules below are strict where a mistake is costly and light where a human eye judges better than an assertion.

## Where test-first is mandatory

The test is written first and must fail without the implementation. The reviewer checks the order in the branch history.

- Security: authentication — every private route rejects a request without a valid API key, and every write is a private route
- API contracts
- Services and domain logic
- Bug fixes — first a test that reproduces the bug

## Test surfaces and the red–green–refactor cycle

An approved issue/PRD identifies the behaviour and the public operation to test. Record the relevant surface (HTTP request, service operation, persistence operation, pure transformation or rendered visitor journey), what it observes and the important failure cases. Existing approval covers those tests; an unattended agent does not ask the owner to approve the same surface again. Ask only if a material scope/domain decision is genuinely unresolved.

Work in small observable slices: write one behavioural test, run it and confirm failure for the missing behaviour, commit the red test, implement enough to pass, then rerun relevant checks. Refactor after green without changing behaviour, and keep the tests. An import error or broken fixture is not the intended red evidence. Expected values come from the requirement or independently worked examples, not the implementation formula repeated in the assertion.

Tests enter the module through the operation they exercise and assert results/errors/state visible through that contract. Do not mock the internal call graph or assert helper call counts/order. Nontrivial internal pure functions may have focused tests without becoming public exports solely for tests. Do not add tests that only restate configuration, generated files or trivial forwarding code. Required security/HTTP/validation/persistence behaviour still needs tests even if a handler delegates it.

Persistence integration tests use real Postgres and separate temporary databases. Controlled clocks/randomness and external provider fakes are appropriate at real external interfaces; they do not replace actual database integration. Test failure/rollback outcomes through the relevant persistence/service/HTTP contract; low-level integrity checks are valid in tests whose subject is persistence integrity. Local-storage tests may use disposable real files; normal CI never needs Bunny credentials.

Both storage drivers run the same driver-contract cases. The Bunny driver runs them through an in-memory S3 endpoint plugged in as its transport, so the real S3 client builds and signs every request without a network. One opt-in suite, `packages/services/src/modules/storage/bunny-s3.integration.test.ts`, runs against a real development zone and is skipped unless `STORAGE_BUNNY_INTEGRATION=1`. Run it only with the development zone's credentials: set `STORAGE_BUNNY_ENDPOINT`, `STORAGE_BUNNY_REGION`, `STORAGE_BUNNY_ZONE`, `STORAGE_BUNNY_PASSWORD` and an https `STORAGE_PUBLIC_BASE_URL` in the shell, then run `STORAGE_BUNNY_INTEGRATION=1 pnpm --filter @sebela/services exec vitest run src/modules/storage/bunny-s3.integration.test.ts`. It writes below a fresh `development/integration-<random>/` prefix and deletes only the files it created. The same file holds the private storage checks (store, read and delete, no read outside the prefix), skipped unless `PRIVATE_STORAGE_BUNNY_INTEGRATION=1`; run them only with dedicated development keys of a private zone (`PRIVATE_STORAGE_BUNNY_ENDPOINT`, `PRIVATE_STORAGE_BUNNY_REGION`, `PRIVATE_STORAGE_BUNNY_ZONE`, `PRIVATE_STORAGE_BUNNY_PASSWORD`). CI runs the private driver contract with `local` and the in-memory endpoint only.

Use the project-local [tdd reference](../.claude/skills/tdd/SKILL.md); [codebase-design](../.claude/skills/codebase-design/SKILL.md) helps if the interface itself is unclear. Follow the UI and MCP/AI verification policies below; these references do not extend test-first requirements to typography or replace model evals with mocks.

## Where visual evidence is the standard

Layout, typography and responsive polish are accepted on:

- the acceptance criteria of the issue,
- Playwright checks for behaviour (navigation, interaction, no horizontal scroll),
- screenshots at **360, 768 and 1280 px**, in **light and dark** mode,
- for a page meant to be printed (the CV), a separate check with print media in both schemes: its colours, what it hides and a screenshot,
- a visual review by the reviewer and the owner.

A test written before the markup is not required here.

## Evals-driven development

MCP tools and AI features are developed evals-first.

- Evals are written before the implementation and state a pass threshold.
- They are written with promptfoo, pinned as an exact dev dependency of the suite's package and locked, not fetched for every run through `pnpm dlx`. A runner may run a few case-runs at once when each has its own fixture and results stay independent, bounded well inside the provider's rate limits (MCP Admin: four). They call real models, so they run on demand and for changes to the AI parts (`mcp-admin`, `ai-service`, `mcp-public`, the `llm-agent` package and `memory`), not on every pull request.
- Developers and agents run them locally while they work, through a package script wrapped in `node harness/with-secrets.mjs --`, which gives the command the `ANTHROPIC_API_KEY` of the main checkout's `.env.secrets` without the agent seeing it (`docs/permissions.md`, Environment files); an issue runs only affected cases (the go-ahead: [Running paid evals](#running-paid-evals)) and its eval gate is met by that local run, whose case IDs, partial/full scope, redacted summary and cost go into the pull request. Proposed method, pending owner confirmation in the #179 pull request: when the affected cases exceed the per-run spending limit, the issue runs them in slices with one fingerprint, copies their answers into one folder, grades that pool with a free `--regrade`, and applies the gates to the pool (Python agent: `packages/llm-agent/AGENTS.md`, Evals, Policy). Shared model/prompt/tool/context changes can affect the whole catalogue. Reuse compatible stored answers to verify deterministic grader fixes without new generation (MCP Admin: `node evals/run.js --regrade <run-folder>`; Python agent: `uv run --locked python -m evals.run --regrade <run-folder>` in `packages/llm-agent`). Changed model judging still consumes its own paid budget (Python agent: `--regrade <run-folder> --judge --allowance <usd>`). The Python agent judges through the Message Batches API at half price with prompt caching by default (`--judge-mode direct` for debugging), retrying only the idempotent batch calls and keeping the results that succeeded before a timeout; a run that never started (the test API or fixture failed before Promptfoo) is charged nothing, and a paid run stops after its first 6 case-runs on early anomalies, reporting the remaining cases pending, never passed (`packages/llm-agent/AGENTS.md`, Evals, Policy). Each eval suite pins one model and effort, the one its real client uses (MCP Admin: Claude Sonnet 5.5 at `medium`, `.plan/done/05-mcp-admin/evals.md`; Python agent: Security Claude Haiku 5.5 at `medium`, Main Claude Haiku 5.5 at `medium` and a Claude Sonnet 5.5 `medium` judge, `.plan/done/06-llm-agent/evals.md` with the Main default changed by [decision 0024](decisions/0024-main-agent-haiku-medium.md)). A paid Python agent command also names its phase campaign (`--campaign <phase-folder>`) and declares that campaign's remaining allowance (`--allowance <usd>`), which a local ledger caps further at the campaign's own ceiling and stops ([Running paid evals](#running-paid-evals)). A missing key or an exhausted allowance is a visible block, never a pass (`packages/llm-agent/AGENTS.md`, Evals). Without the key the eval gate cannot run, and the issue waits for the owner.
- **In CI, paid evals start by themselves only on a phase pull request; only the suites it affects run, and not on every push.** `model-evals.yml` gives every eval suite (one per app or package with evals: MCP Admin and the Python agent `packages/llm-agent` now; `apps/ai-service` and `apps/mcp-public` as they gain evals) its own job with the paths that can change its behaviour: its own folder and what it depends on. For MCP Admin that is `apps/mcp-admin/`, its own job in the workflow, and of the API only what it calls: a change of a route it calls in the committed OpenAPI document, of the API client's runtime or of their locked dependencies (`scripts/checks/mcp-admin-evals-affected.mjs`; a route added for another consumer, with its API, services, database and contracts, does not run it). For the Python agent that is `packages/llm-agent/`, `apps/api/`, `packages/contracts/`, `packages/api-client/`, `packages/services/`, `packages/db/`, the root `pyproject.toml`, `uv.lock`, `.python-version`, `pnpm-lock.yaml` and the workflow. A suite runs in full on a **phase pull request** (head branch `phase/<phase-folder>` into `master`) when it is opened, reopened or marked ready for review, is not a draft and changes one of the suite's paths, and by hand (`workflow_dispatch`, one suite or all). New commits on that pull request do not start another charged run; the owner starts it again by hand when a fix needs it. Every other pull request into `master` (a fix, a dependency update, documentation) starts no paid eval, whatever it changes (the owner's decision of 2026-11-21, #337: maintenance pull requests had started four runs in a day). When such a change really needs a suite, start it by hand on its branch (Actions, `Model evals`, Run workflow, or `gh workflow run model-evals.yml --ref <branch> -f suite=mcp-admin`); every run is charged (MCP Admin: about USD 1.3–1.9), so say in the pull request why it was needed and what it cost. Issue pull requests into phase branches never run paid evals. The Python agent job (`Python agent model evals`) runs every implemented case with 3 repeats. It reserves its budget per bounded chunk of about 12 case-runs, each just before it starts, not for the whole run, so the full run fits a realistic `LLM_AGENT_EVAL_ALLOWANCE_USD` (about USD 1.07 expected, at most USD 0.68 reserved per chunk); when the allowance runs out mid-run, the remaining cases are pending, the gate fails and nothing is counted as passed ([owner decision](https://github.com/sebelapetr/sebela.dev/issues/183#issuecomment-7064482195)). The per-run limit of USD 1.00 applies to issue runs, not to this phase-PR run. Its declared remaining campaign allowance comes from the manual run's `allowance` input or the repository variable `LLM_AGENT_EVAL_ALLOWANCE_USD`. Without one, the job fails visibly instead of granting a fresh USD 10. A CI runner has no ledger, so the declared value is the only record of what remains: the job log ends with a notice naming the new remainder, and the owner sets `LLM_AGENT_EVAL_ALLOWANCE_USD` to it after every run (or passes it as the next dispatch input), otherwise the next run could spend the same allowance again. Its model key is scoped to the eval step, and it uploads only the redacted `summary.json`. Provider comparisons stay explicit and budgeted, and are never a release pass (Python agent: `--compare <candidate> --allowance <usd>` runs a fixed 20-case subset with 1 repeat and records scope `comparison`, under a comparison-only execution limit derived from the candidate's pinned prices while ordinary runs keep the default; a candidate whose subset would reserve more than the per-run limit runs in `--case` slices; its answers are marked and never pooled into a gate; `--compare-report <run-folder>...` merges the slices and puts stored comparisons side by side for free, refusing summaries whose settings differ beyond the Main model; `packages/llm-agent/AGENTS.md`, Evals, Policy). This is the policy for every future eval suite, not only phase 5.
- Safety suites must pass completely. Other suites have a threshold set from the first baseline; it is never lowered to pass a run.
- They cover desired and forbidden behaviour: choosing the right tool, factual grounding, saying "I don't know", direct and indirect prompt injection, unsupported claims, source correctness, restraint with destructive tools.
- Evals live in `apps/mcp-admin/evals/`, `packages/llm-agent/evals/` and `packages/memory/evals/`. Phase 6 gates the package stages/structured reads before a server exists; phases 7 and 8 add HTTP/web/MCP integration; phase 9 adds retrieval/ingest evals without an LLM judge, phase 9.1 adds tool selection and grounded-answer evals, with graph and ontology evals after launch. Do not make a package-only phase depend on a future transport or real RAG.
- Code graders check deterministic properties; model graders use versioned rubrics calibrated against human labels. Human review covers ambiguous cases, grader disagreements and a sample of automatically passed answers. Record human scores and release decisions. At each AI phase's acceptance, 12 recorded answers (6 EN / 6 CS) plus all disputed/ambiguous results are scored in the phase PR or a linked report. In phase 6 the owner delegated the scoring of the 12 answers to a model, as recorded on #183: those are model grades, not human labels, and the judge was compared with them ([phase 06 evaluation report](evals/06-llm-agent.md)). From phase 7 on the owner scores them personally (#215, #216). Include case/run IDs, commit, model/effort, rubric version, scores and notes. PR approval accepts that evidence; it is not itself an individual human score and cannot waive a failing safety gate. See the fixed phase-6 gates and campaign allowance in `.plan/done/06-llm-agent/evals.md`.
- **Each AI phase publishes an evaluation report at its acceptance**, as `docs/evals/<phase-folder>.md` (phase 6: [`docs/evals/06-llm-agent.md`](evals/06-llm-agent.md)), linked from the README's AI section. It states, for the accepted run: what the suite covers (case groups, languages, repeats) and the pass thresholds; the result per gate with the commit and the runtime, prompt, expectations and model versions; the models and the recorded cost; every full run that failed, its cause and its fix, linked to the issue or pull request; the graded answers beside the judge's verdicts and what the comparison showed; and what the suite does not test. Every figure is copied from the phase's acceptance issue or a linked issue or pull request and names that source. Nothing is computed or run again for the report, and a figure the record lacks is written as "not recorded". Fictional data only: no real personal data, keys or infrastructure details.
- **Every grade names its grading criteria version.** The wording of the criteria shown to a grader is kept in [`docs/evals/grading-criteria.md`](evals/grading-criteria.md), one `criteria-v<n>` per wording, added before the first grade under it and never edited afterwards. A set of grades records the criteria version, the run and its commit, the run's runtime and expectations versions, and who or what graded (a person, or a model with its identifier and on whose delegation). A model's grades are recorded as model grades, never as human grades. The phase 6 grades were given by a model and carry no criteria version, because their wording was not recorded (#309).
- Measure attack success from outcomes and executed tool calls, plus legitimate-question false positives, latency and cost. Passing a finite safety suite is a release gate, not proof of absolute security.
- Use fictional adversarial fixtures. Real visitor/owner data never enters committed regression datasets.

### Running paid evals

A paid run is money of the owner's. These rules hold for every paid eval run.

- **When they start by themselves.** Only on a phase pull request (head `phase/<folder>` into `master`) that is not a draft, when it is opened, reopened or marked ready for review, and then only the suites its change affects; otherwise by manual dispatch, which is the owner's or on the owner's word. The orchestrator opens the phase pull request as a draft (no evals) and leaves the switch to the owner, so a phase pull request is never closed, reopened or switched between draft and ready without the owner's explicit word.
- **A ceiling per phase campaign, enforced in code.** Every phase has its own eval campaign, named after its phase folder, with its own ceiling and its own part of the ledger (`packages/llm-agent/evals/campaigns.json`, enforced by `evals/budget.py`; [decision 0026](decisions/0026-eval-cost-controls-for-later-phases.md), point 7): phase 7 USD 4.00, of which issue runs may spend USD 1.50 cumulatively and USD 1.00 per run; phase 7.1 USD 2.00; phase 8 USD 2.30; the finished phase-6 campaign keeps its USD 13.00. A paid Python agent command names its campaign (`--campaign <phase-folder>`, or `SEBELA_EVAL_CAMPAIGN`, which the phase loop sets) and its stage (`--stage issue`, the default, or `--stage phase-pr` for the owner's full run at the phase pull request). A missing or unknown campaign is refused; no run falls back to another campaign's ceiling, so one phase cannot spend another's acceptance run. An exhausted ceiling or stop leaves the coverage pending; it never passes (`packages/llm-agent/AGENTS.md`, Evals, Budget).
- **Go-ahead.** (a) For issue work the owner's agreement is the phase's campaign budget and its stops, recorded in a decision or on the phase's acceptance issue (for example [decision 0026](decisions/0026-eval-cost-controls-for-later-phases.md)). Within them a developer runs only the affected cases through the secret wrapper, states the expected cost and the remaining allowance in the issue or pull request, and needs no per-run word. (b) A full run of a suite, any run beyond those stops and anything that raises a ceiling needs the owner's explicit word first. (c) The phase pull request's full run starts only when the owner makes it ready.
- **Order of work.** Fix the known failures first; run only the affected cases as a targeted check (`--case`); run the full catalogue last. When only a code grader or an expectation changed and the runtime fingerprint is unchanged, regrade the saved answers (`--regrade <run folder>`, free) instead of generating again. A changed judge rubric needs a paid rejudge: `--regrade <run folder> --judge --campaign <phase-folder> --allowance <usd>` (the judge refuses to run without a campaign and an allowance). The Python suite has `--case`, `--regrade`, `--judge`, `--campaign`, `--stage` and `--allowance`; MCP Admin has `--case` and `--regrade` and no `--judge`. Details: `packages/llm-agent/AGENTS.md`, Evals (arrives with phase 6).
- **A changed check.** A grader or expectation change that makes a failing answer pass is a weakened check until shown otherwise: it needs the owner's approval recorded on the issue (`AGENTS.md`, hard rule 9), negative tests written first, and a reviewer who compares the base and the changed grader on adversarial inputs.
- **The spend line.** After a paid run the issue comment and the report carry one line: the expected cost before the run, the actual cost after it and what remains of the phase ceiling. The Python runner prints it (`spend: expected …, actual … (uncertain …); … of the <campaign> ceiling (…) remain`), the phase loop logs one with every iteration and comments it on the issue after an iteration that paid for evals (`docs/agents.md`, The steward).
- **In the phase loop the steward watches the spend.** Every 5 minutes while an iteration runs it reads the eval ledgers against the phase ceiling and the paid CI runs. The loop stops by code when the ceiling is reached or a run under way is projected past it, when an issue run passed the per-run stop, or when a pull request of the phase started a paid CI run nobody asked for; the steward model may also stop it for wasteful work — a paid run repeated with unchanged input, a full run where a targeted check or a free `--regrade` would do (`docs/agents.md`, The steward).
- **During a long local run** the orchestrator watches the real spend in the eval ledger and stops at a limit the owner stated; a CI run of the `llm-agent` suite is bounded by its job's `allowance` input (or the repository variable on a pull request); the MCP Admin job has no allowance input. Do not project a full `llm-agent` run linearly from its first chunk: ordinary judged cases come first and code-graded ones later (the order of `evals/catalogue.py`, a consequence of the catalogue, not a guarantee), so that overestimates.
- **After every run** the owner sets the repository variable `LLM_AGENT_EVAL_ALLOWANCE_USD` (it exists from phase 6 on) to the remaining allowance of the campaign whose phase pull request runs next, or the orchestrator does on the owner's instruction and records the value on the issue; an agent never changes it on its own. Uncertain spend (reserved, interrupted) counts as spent.

### Memory evals

The retrieval evals of `packages/memory/evals/` (`packages/memory/AGENTS.md`, Evals) measure search without an LLM judge: recall@pool over graded relevance, nDCG, precision, MRR, correct and false empty results below the relevance floor, provenance accuracy, latency and cost per query.

- `pnpm --filter @sebela/memory eval [--case <id>] [--publish <name>] [--max-cost-usd <n>] [--min-interval-ms <n>] [--variant reranked|hybrid|vector|fulltext]` runs through `node harness/with-secrets.mjs --`, which supplies `VOYAGE_API_KEY`; `--plan` prints what would run, free. A run spends at most USD 1 (the default and the maximum of `--max-cost-usd`), enforced as the API's monthly retrieval ceiling (embedding and reranking) on the run's fresh database.
- A measured run starts the API's end-to-end server on a temporary database with the fictional demo seed, indexes it and records the candidate pools through the API's `knowledge` command (all questions embedded in one batch), then sends every question to the private search route, one at a time. Provider calls are paced at least `--min-interval-ms` apart (default 21 000 ms, safe for a key limited to 3 requests a minute; lower it for a higher limit), and the run's API and command retry a rate-limited call up to 6 times, waiting at most a minute each; the summary records the pacing. It needs the running Postgres and a build of the API's packages.
- `--variant` picks what is measured, passed to the run's API as `RETRIEVAL_EVAL_VARIANT`: `reranked`, the deployed search (the default: vector and full-text candidates fused by reciprocal rank, scored by the reranker, the floor on its score), or a baseline: `hybrid` (the fused pool in its order, no reranker, no floor), `vector` (cosine similarity, the floor on it) or `fulltext` (Postgres text search over the same chunks, no query embedding, no floor). The summary records each returned passage's score, so the floor and the final count can be calibrated offline from one run with the floor at 0. That setting exists for eval runs only; a deployment leaves it unset.
- The gate is `evals/thresholds.json`: frozen minimums for what the phase PRD gates (recall@pool, nDCG, correct-empty rate), with the baselines and the method they were set by; MRR, hit rate, precision, the false-empty rate, provenance accuracy, latency and cost are reported, not gated. It applies only to a complete run of the deployed variant it names, and a slice that deploys another pipeline switches that variant in the same change; a partial run or another variant reports metrics and why the gate did not apply. A failed gate exits 1 and lists each failing metric. Later slices may only raise a threshold.
- Cases the system cannot answer yet (`plan.js`) are reported pending, never passed; without the key every case is pending (exit code 2). Publish paid baselines to `evals/results/` with their cost, and post the cumulative spend in the pull request.
- Ordinary tests never call the provider: the deterministic fake embedder is a bag of words, so a test query uses the target record's own words and a no-evidence query uses words absent from the seed. `evals/evals.test.ts` checks dataset, graders, plan and options with `pnpm test`.

## Knowledge publication and source privacy

- Phase 9 tests the terminal ingest boundary before implementation: supported formats/extraction limits, local sensitivity checks, approval tied to content/version, no external embedding call before approval and no public access to pending/rejected material.
- Test API fact precedence, source/version labels, atomic replacement, withdrawal/deletion, index rebuild and embedding-model migration with real Postgres/pgvector plus fake embeddings.
- Approved extra passages may be public; raw originals, staging metadata and storage credentials are not. Test attempted downloads through public media/API/CDN routes and private-local-root path traversal. Optional Bunny tests use development-only credentials; ordinary CI needs none.
- Later graph/ontology assertions retain provenance and source withdrawal rules. Compare measured quality against the prior deployed baseline; passing a test suite never proves every secret or contradiction can be recognized.

## Authentication as a property

There is one test that walks every route of the API and asserts: each write route and each private route returns 401 without a valid API key. A new route is covered automatically, so a write can never be left open by mistake. The chat conversation routes are the one named exception, with their own tests that they can touch only the caller's own conversation.

The API's audit coverage is the same kind of property (`apps/api/src/audit.test.ts`): it walks every route the HTTP framework registered, and any route for a method other than `GET`, `HEAD` or `OPTIONS` that is not an audited content write fails it, so a newly registered write cannot skip the audit. For every audited write it also checks that a refusal without a key or an invalid request stores no audit entry, and that reads store none.

Admin MCP adds deterministic tests for authentication before discovery, every HTTP method/session operation, next-request revocation, strict entity/field allowlists, injection/path/SSRF attempts, credential redaction and bounded work. Deployment verification proves that both MCP Admin and private content-write API routes are unreachable through the public edge, with the authenticated internal/SSH-tunnel path working. MCP destructive annotations and model restraint evals are not substitutes for enforced authorization or supported-client approval configuration.

MCP Admin's tests (`pnpm --filter @sebela/mcp-admin test`) run in two layers, and its container policy is a repository check. `src/app.test.ts` drives the HTTP surface in-process against a fake API at the content module's transport. `src/content-tools.test.ts` drives the content tools the same way: the registry, strict arguments, field and identifier checks, read-before-write, provenance, conflicts and lost answers reconciled through the audit or reported `uncertain` without a second write. `src/media-tools.test.ts` drives the `upload` tool the same way: the size bound and strict base64, the file name and media type sent to the API, the API's refusals reported as field errors, storage failure, redirects not followed, lost answers reconciled through the audit, and attaching only a returned media ID or one the owner stored with the API's `media upload` command, whose own test (`apps/api/src/cli/media.test.ts`) sends a file from disk over the real media route. `src/learning-tools.test.ts` drives the six learning task tools the same way: strict inputs and annotations, resource lookup by stored name, slug or link without requesting the link, collision candidates, canonical statuses, session endpoints with offsets, a Prague-midnight split, a book logged once on its linked resource and a book without one refused with an error that names the missing link, event attendance through the session action, overlaps as conflicts, a lost session answer reconciled through the audit or reported `uncertain` without a second write, books without a status and a created resource kept as a partial result when its session is refused. `src/learning.e2e.test.ts` runs those tasks through MCP Admin against the real API: notes appended to the day's earlier notes and audited as a session, a midnight split and a book's session, an overlap refused with nothing written, and a new resource and an event whose dates add no time. `src/content.e2e.test.ts` runs a save and a protected delete `src/mcp.e2e.test.ts` connects the SDK test client to a real MCP Admin and the real API's end-to-end server on a temporary database with ephemeral named fixture keys, which reach only the client's A grader change that can turn a verdict raises that case's grader version (`GRADER_VERSIONS` in `evals/graders.js`), which every summary pins beside the model and dataset, so results graded by different versions are not compared silently. `node evals/run.js --check-fixture` starts and stops the eval fixture without a model, and `evals/evals.test.ts` checks the catalogue, graders and gate deterministically, and that every scenario's setup or concurrent API edit has a body its update contract accepts.

## Property tests

A property test states a rule that must hold for every input of a piece of pure logic and lets [fast-check](https://fast-check.dev/) generate the inputs: hundreds of values per run, biased towards the edges that matter (a time-zone change, a midnight, a `</script>`, a `..` segment), and shrunk to the smallest counter-example when the rule breaks. It complements the example tests beside it; it never replaces them.

- **Where.** Pure functions whose rule is easy to say and hard to cover by examples: encoders and escapes, parsers and validators of untrusted input, and arithmetic over dates and times. Today: the inline-script literal (`apps/web/src/modules/_shared/inline-script.property.test.ts`), the diary's split of a session at Prague midnights (`packages/services/src/modules/roadmap/diary-time.property.test.ts`) and the storage keys (`packages/services/src/modules/storage/keys.property.test.ts`). Logic that runs in the database, such as the roadmap statistics, is covered by integration tests instead.
- **How.** The file sits beside the module as `<name>.property.test.ts` and runs with the package's other Vitest tests. The test name states the rule. A property touches no database, network, file or clock, so it is as fast as a unit test. Its inputs come from the seed, but the code under test may still draw its own randomness. The storage keys' properties call `newKey`, which names each file with `crypto.randomUUID()`. A printed seed therefore replays the generated prefixes and extensions but not the same UUIDs. Those properties hold for any UUID, so the outcome does not depend on it. A rule that compares against the code's own helpers needs an independent oracle: the diary's date properties read Prague dates with their own `Intl.DateTimeFormat`, not the module's `diaryDateOf`.
- **Fixed size.** Each file sets a fixed `numRuns`, so a run takes the same time on every machine and `pnpm test` grows by seconds, not minutes. Do not raise it to hunt for rare failures in CI; bias the generators towards the edges instead.
- **Inputs in the domain.** Generators produce what the function can receive. When the caller refuses a value before it reaches the function (the diary refuses fractions of a second, for example), the generator does not draw it, and a comment says why.
- **Broken on purpose.** A new property is shown once to fail when its rule is broken in the code, in the pull request, not in a commit.
- **Reproducing a failure.** A failure prints the counter-example, the `seed` and the `path`. Pass both to the same assertion, `fc.assert(property, { numRuns, seed, path })`, to replay that case while you fix it, then remove them again. Randomness the code draws itself, such as the UUID of a storage key, is not replayed. A counter-example that is a real bug is fixed test-first: add it as an example test, see it fail, then fix the code.

## Website browser tests

The website's Playwright tests (`apps/web/e2e/`, `pnpm test:e2e`) read a real API, never a mock: the API's end-to-end server (`apps/api/src/cli/e2e-server.ts`) creates a temporary database, migrates it, loads a small fictional seed folder from `apps/web/e2e/fixtures/` with its own temporary local storage, and drops both when it stops. The demo seed and the checkout's database are never used. They cover behaviour (content and links, the missing-photo fallback, the unavailable state and its retry, keyboard order), automated accessibility (axe), touch targets and no horizontal scroll, and take the screenshots at 360, 768 and 1280 px in light and dark mode that the visual review uses. Each page's spec checks it in detail; `e2e/handoff.spec.ts` checks the site as a whole — every page with the longest fictional content (`fixtures/with-long-content/`), whole words in labels, print, and the client, recruiter, evaluator, chat and keyboard journeys across pages. The complete containerised stack has its own browser step against the website container (`pnpm test:web-stack`, CI below), which `pnpm test:e2e` leaves out. Spec files run in parallel and the tests of one file in order: 3 workers on a development machine, 4 in CI, or the number in `E2E_WORKERS`. Files share only the main stack, which they read and never change; the blocks that need other content start their own API and website on a temporary database and free ports. Set `E2E_WORKERS=2` (or `1`) on a machine that is busy with other work. `test:e2e` runs through `harness/one-at-a-time.mjs e2e`, so on one machine at most one website browser-test run is active across the main checkout and every worktree; a second run waits (it says whose run it waits for) and gives up after 60 minutes (`ONE_AT_A_TIME_MAX_WAIT_MINUTES`). Parallel phase loops on a small shared server would otherwise exhaust its memory. Details and prerequisites: `apps/web/AGENTS.md`, Tests.

## Consumer contract tests

`apps/api/src/client.test.ts` calls the real app through the generated `@sebela/api-client`, over a temporary database, as a server-side consumer would: the public person read, the authenticated writes, and the validation, not-found, conflict, authentication and rate-limit errors through the contract's types. Requests go to the app's `fetch` directly, so no port or host is involved. Every pull request that adds, removes or changes a route or a contract schema regenerates the client (`pnpm generate:api-client`), commits the result and extends these cases for the changed operations; CI's drift check fails otherwise.

## Configuration in tests

Tests follow the same rule as the code: no hard-coded port, local host address or database name (see [the hard-coded configuration check](repository-structure.md#the-hard-coded-configuration-check)). A test takes an expected port from `.env.example` or from the configuration it passes in, and leaves a fixed value to fixture files whose purpose is to hold it.

## Databases

- Each worktree has its own database and database role, and its tests connect with that role's credentials (see `docs/repository-structure.md`). The harness tests check the worktree lifecycle through a fake at the harness's database interface, so `node --test harness/` needs no Docker; `node harness/worktree-databases.e2e.mjs` checks the same lifecycle against a real, disposable Postgres from `compose.yaml`, on demand and in the CI job `Worktree database lifecycle` (see [Worktree databases](repository-structure.md#worktree-databases)). The backend stages of setup and cleanup (install, migration, storage, seed) are tested through a fake at the harness's backend interface, including a failure at each stage, retry and slot bookkeeping; `node harness/worktree-backend.e2e.mjs` runs them for real on two worktrees of a temporary clone, with local storage and no cloud keys, on demand and in the CI job `Worktree backend setup` (see [Worktree backend setup](repository-structure.md#worktree-backend-setup)).
- Tests use a separate temporary database, so they never touch the data an agent is looking at in the browser. Each backend test file (`apps/api`, `packages/services`, `packages/db`) creates its own `test_<random>` database through `@sebela/db/testing` with the role from `DATABASE_USER`/`DATABASE_PASSWORD`, migrates it from the committed migrations (or leaves it empty when the test is about an empty database) and drops it afterwards. There is no mocked database.
- The backend tests read `POSTGRES_HOST`, `POSTGRES_PORT`, `DATABASE_NAME`, `DATABASE_USER` and `DATABASE_PASSWORD` from the process environment, falling back to `.env.local`, `.env` and `.env.example` of the checkout (their `vitest.config.ts`). Turborepo's strict environment mode hides undeclared variables from tasks, so `turbo.json` passes exactly these through to `test` (`passThroughEnv`; they do not change cache keys).
- Tests use small fictional fixtures, never the demo seed, so that editing demo content cannot break a test. The one exception is the seed command's own test (`apps/api/src/cli/seed.test.ts`), which loads the demo seed to prove the default folder loads completely.

## Local checks

The machine is shared. Run the checks the change affects, push, and let CI run the full matrix; do not repeat the full matrix locally. Never run several full test suites at the same time on this machine: parallel full suites from two sessions once pushed the load on its four cores above 20 and turned minute-long checks into quarter-hours. In the phase loop the steward sees the machine's load, its free disk space and the full suites running at once, warns about them, and its model may stop the loop for several full suites at once or a full local matrix that CI repeats (`docs/agents.md`, The steward).

Checks run at three points before CI, each lighter than the next:

| When                                                                                                     | What runs                                                                                                        | Where it is described                                  |
| -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| An agent edits or writes a file                                                                          | Prettier on that file                                                                                            | [Permissions](permissions.md#formatting-after-an-edit) |
| A commit is made                                                                                         | Prettier and ESLint on the staged files; the commit message against Conventional Commits. No typecheck, no tests | [Git workflow](git-workflow.md#local-hooks)            |
| A developer agent hands off, or a general agent that changed CI, script, infrastructure or harness files | Lint and typecheck of the changed packages, their dependents and the root, in its worktree. No tests             | [Permissions](permissions.md#handoff-checks)           |

The developer still runs the tests and the build for what it changed before it finishes; CI runs everything.

### Browser tests by role

The website's browser suite (`pnpm test:e2e`) takes minutes, so each role runs only its share of it:

Locally nobody runs the whole suite: it takes long, it competes for the memory of the machine the parallel phase loops share, and CI runs it anyway before anything merges.

- **Every developer (frontend, backend, AI):** only the spec files its change adds or touches, by path (`pnpm --filter @sebela/web test:e2e e2e/<name>.spec.ts`, after `pnpm --filter @sebela/web build`), and while fixing one failure only that test (`-g "<title>"`). A change that cannot change the website (what CI's `Website affected` step skips: documentation as [Documentation selects no work](#ci) defines it, `.claude/`, `harness/`, the MCP apps, the AI service, `packages/llm-agent`, `packages/memory`) runs no browser tests at all.
- **Reviewer:** the specs the change adds or touches, plus the specs of the pages a changed shared part feeds (a shared component, a website module, an API route or contract the pages read), once per review; none when the change cannot change the website. A re-review after fixes runs only the specs the fixes touch and the ones that failed. The reviewer does not run the whole suite.
- **CI:** the whole suite on every pull request the website is affected by, as the condition for merging; the orchestrator merges only with every check green, so a spec broken elsewhere is caught there.

## Coverage

Coverage informs and never gates ([issue #310](https://github.com/sebelapetr/sebela.dev/issues/310)): there is no threshold, and no check fails because of a coverage value.

- **Measured:** the lines of handwritten source (`src/`) that the existing unit and integration tests run, in every app and package that tests with Vitest: `apps/api`, `apps/mcp-admin`, `apps/web`, `packages/contracts`, `packages/db`, `packages/memory` and `packages/services`. Vitest's V8 provider (`@vitest/coverage-v8`) collects it; a source file that no test loads counts as uncovered.
- **Excluded:** generated code — every `generated/` folder below `src/`, which covers the API client's `packages/api-client/src/generated/` (the API client has no tests of its own either) — as well as test files and type declarations. Not measured at all: the website's Playwright tests, the evals, and the plain JavaScript tooling tested with Node's runner (`harness/`, `scripts/`, `@sebela/config`). The summary lists members without coverage measurement and members without tests (`@sebela/api-client`, `@sebela/ui`) by name.
- **How:** `coverage()` from `@sebela/config/vitest` is the one setting every `vitest.config.ts` passes as `test.coverage` (`packages/config/AGENTS.md`). It collects only when `TEST_COVERAGE` is `true`, so a local `vitest run` is unchanged; Turborepo includes the variable in the `test` task's hash (`env`), so a run with coverage never reuses the cached result of a run without it. Each measured member writes `coverage/lcov.info`. `scripts/checks/coverage-summary.mjs` reads them and reports covered and total lines per member, per language (TypeScript, Python) and overall. A member counts as measured when it declares a coverage provider: `@vitest/coverage-v8` in its `package.json`, or `pytest-cov` in the `pyproject.toml` of a Python member; one that declares it but has no report did not run its tests in that job.
- **In CI:** the quality job sets `TEST_COVERAGE=true`, so the affected packages' tests collect it, and its step `Coverage summary`, after the drift check, writes the table to the job summary (also after a failed test, not after a cancelled run). A pull request shows the packages it ran and names the others as not run. **The full run:** on a push to `master` that changes a file other than documentation, or whose base cannot be resolved, the job also runs the tests of every other package (`turbo run test`; the packages tested before are cache hits, their reports already on disk), so the figure covers the whole workspace, and keeps the coverage site (below) as the artifact `coverage` (90 days). A push of documentation alone, a merged changelog pull request among them, runs neither: the figure cannot change, and the published badge stays as it is. `scripts/checks/coverage-full-run.mjs` decides (step `Full coverage run on master`), from the same change without its documentation as the affected packages ([CI](#ci), Documentation selects no work); a pull request or a run started by hand never runs it. Because of the full run, a failing or flaky test in a package the push did not touch now fails the `master` run of CI and holds back the badge until it is fixed or rerun; that is accepted, as the figure is meant to cover every package. **Cost:** this change's own pull request, which selects every package, ran the step `Affected package tasks` (the same 36 tasks) in 3 min 02 s with coverage, against 3 min 13 s (#316, run 44936710956) and 3 min 14 s (#311, run 44935125480) without, within the runners' variation; run one after another on a development machine, every package's tests took 315 s with coverage against 294 s without (about 7 %, mostly `@sebela/api`). The summary takes under a second. The full run on `master` adds the tests of the packages a push did not affect, a few minutes, on `master` only. Tests that must hold on a busy runner avoid absolute wall-clock limits: `packages/memory`'s long-run checks (`src/modules/documents/index.test.ts`) compare the processor time of a whole run with that of a quarter of it (linear work stays near four times, quadratic reaches sixteen, the test fails at eight), and its PDF tests, which start a fresh worker loading the PDF parser for every reading, have a timeout of three readings at the module's own 10 s limit, as a guard against a hang only ([#349](https://github.com/sebelapetr/sebela.dev/issues/349)).
- **Python** (`packages/llm-agent`, from phase 6): not measured yet; tracked in [#348](https://github.com/sebelapetr/sebela.dev/issues/348). The summary already reads a Python member's `coverage/lcov.info`; the member needs `pytest-cov`, its `test` task writing that report when `TEST_COVERAGE` is `true` (`--cov --cov-report=lcov:coverage/lcov.info`), and `src/llm_agent/generated/` omitted (`[tool.coverage.run]`).
- **Badge and site:** the README's coverage badge is a shields.io endpoint badge reading `coverage.json` from the repository's GitHub Pages site, `https://sebelapetr.github.io/sebela.dev/` (the owner's decision on #310: a self-published figure, no outside service, account or secret). The `Coverage summary` step writes the site with `--site`: `coverage.json` (schema version 1, label `coverage`, the overall figure such as `83.8%`, always the README's neutral `525252`, as there is no threshold), `coverage-summary.json` (the figures per language and package) and an `index.html` with the table and a link to this section, without scripts or other resources. The site is public and holds only coverage figures and package names. `.github/workflows/coverage-pages.yml` publishes the [coverage site](#coverage) to GitHub Pages. It starts when a CI run completes (`workflow_run`) and checks out nothing and runs no tests. Its job `Coverage site of the CI run` looks only at a successful push run of this repository's `master`, never at a pull request's run (a fork's branch called `master` included), and asks whether that run kept the artifact `coverage` (`actions: read`). A run that kept none, a push of documentation alone, ends the workflow green without deploying, and the published badge stays. Otherwise `Publish the coverage site` downloads the artifact and deploys it with `actions/upload-pages-artifact` and `actions/deploy-pages` in the `github-pages` environment, which GitHub limits to the default branch, with `actions: read`, `pages: write` and `id-token: write`; the workflow's own permissions are `contents: read`. One deployment runs at a time. Pull request runs of CI are unchanged by it. `scripts/checks/coverage-full-run.test.mjs` checks the decision and both workflows' use of it.
- **Locally:** `TEST_COVERAGE=true pnpm test --force` (or `pnpm --filter <package> test`), then `node scripts/checks/coverage-summary.mjs`. `--force`, because Turborepo does not keep the reports in its cache: a cached result writes none, and the summary then names the package as not run. The `coverage/` folders are ignored by Git, ESLint and Prettier.

## CI

Lint, typecheck, tests and build must pass before a pull request can merge. A failing check is fixed, not disabled. The orchestrator merges an issue pull request only when every check reported on it is green (`gh pr checks --watch`).

Two workflows run on every pull request and on pushes to `master`; `ci.yml` also runs when the release workflow starts it on its changelog pull request (`workflow_dispatch` with the input `base`, compared like a pull request; `docs/release-workflow.md`, Changelog). A phase branch has no push run: it changes through issue pull requests, which ran CI on their merge with it, and its open phase pull request runs CI on every push, so a push run would check the same commit twice. Every job runs on every event: none is skipped by a path filter, so a status is never left waiting or reported as skipped.

**Website jobs.** `Website end to end` and `Website stack smoke` start with the step `Website affected`: when every file the change touches is documentation (below) or one that cannot change the website — `.claude/`, `harness/`, `apps/mcp-admin/`, `apps/mcp-public/`, `apps/ai-service/`, `packages/llm-agent/`, `packages/memory/`, `model-evals.yml` or `commit-messages.yml` — the job reports success at once and starts no browser or stack; the step's log lists the documentation left out and the other files. Any other file, a new branch or a base that cannot be resolved runs the job in full, so a change to the API, the contracts, the shared packages, the lockfile, the scripts or this workflow always runs it. Their screenshots and reports are kept for 14 days.

**Documentation selects no work** (the owner's decision of 2026-11-21): a change to documentation alone starts no package tasks, browser tests or image builds wherever work is selected by the apps and packages a change touches, and on `master` no [full coverage run](#coverage). Documentation is Markdown anywhere (the app and package `README.md` and `AGENTS.md` included) and everything in `docs/` and `.plan/`, whatever a folder inside them is called (`docs/evals/` holds the evaluation reports, not the inputs of an eval); outside those two folders, Markdown in a folder that code reads is not: a `src/`, `evals/` or `fixtures/` folder (the retrieval eval documents of `packages/memory/evals/datasets/`, the seed folder `apps/web/e2e/fixtures/without-profile/`, which exists only through its README) and `.claude/skills/`, whose content skills MCP Admin's tests and evals give the model. Nor is Markdown a package's build reads: `packages/llm-agent/AGENTS.md`, which its `pyproject.toml` names as the readme of the built package. The rule is one function, `harness/lib/documentation.mjs`, used by the developer handoff hook (`docs/permissions.md`, Hooks) and by `scripts/checks/without-documentation.mjs`, which CI and the release plan use. Turborepo 2.11's `--affected` and `turbo query affected` select a package for any changed file in its folder, and task `inputs` do not change that selection, only cache hashes, so the script hands Turborepo the change without its documentation instead: a commit made for the run, the head's tree with every documentation file put back as it was at the merge base, as a child of the head (`head <base>`, set as `TURBO_SCM_HEAD`; `files <base>` lists the changed files that are not documentation). Turborepo's own rules (global files, the lockfile, dependents) then apply unchanged to the rest. The root checks (`pnpm ci:root`), the hard-coded configuration and private-terms checks, the API client drift check and the commit-message check still run on every change, and every required job still reports success. The paid model evals apply the same idea through `scripts/checks/mcp-admin-evals-affected.mjs` (below); moving them to the shared rule follows phase 6.

`.github/workflows/scorecard.yml` runs the [OpenSSF Scorecard](https://github.com/ossf/scorecard) supply-chain checks on `master`: weekly, on every push to `master`, when a branch protection rule changes and by hand (`workflow_dispatch`). It is not a required status check and does not run on pull requests. Its single job, `Scorecard analysis`, checks out the repository without persisted credentials, runs `ossf/scorecard-action`, keeps the SARIF result as an artifact for five days, uploads it to code scanning (Security → Code scanning) and publishes it to the Scorecard API, which serves the README badge. Its job permissions are only those the action documents (`security-events: write`, `id-token: write`, `contents: read`, `actions: read`); the Scorecard API accepts published results only while the workflow has no top-level write permissions, env or defaults and the job uses only the approved actions, so keep it that way when changing it. `.github/CODEOWNERS` names the owner as code owner of everything, one of the Scorecard checks; branch protection does not require code-owner reviews. `Signed-Releases` (Scorecard v5.7.0) reads the first five releases the GitHub API lists and, among them, the files of those that have any, skipping releases without files; the `.intoto.jsonl` bundles each release attaches (`docs/release-workflow.md`, Release files) are the provenance files it gives full credit for. `.github/scorecard.yml` (not the workflow `.github/workflows/scorecard.yml`) holds Scorecard's maintainer annotations: the reason beside a check that this project cannot meet or that Scorecard cannot detect, where Scorecard and a reader of the file can see it. It annotates `Code-Review` as `not-applicable` (a single maintainer; Scorecard counts no bot or AI review, and every change still passes a pull request, CI and an agent review before the owner merges) and `Packaging` as `not-detected` (the release does publish the images, through `scripts/release/images.mjs`, where Scorecard does not look for the push). `Maintained` is not annotated: it is low only because the repository is younger than 90 days, which Scorecard reports correctly and which no reason describes, and it rises by itself. Checks that can still be improved are not annotated either. An annotation adds context only: it changes no score, and the action publishes its result to the Scorecard API without annotations. In the action's SARIF output (Scorecard v5.7.0 in `ossf/scorecard-action` v2.6.0), an annotated check that is below its threshold produces no result, so it raises no code scanning alert; `Packaging`, reported as inconclusive, raises none anyway. Scorecard takes the first of `scorecard.yml`, `scorecard.yaml`, `.scorecard.yml`, `.scorecard.yaml`, `.github/scorecard.yml` and `.github/scorecard.yaml`, so do not add another; a file it cannot parse is ignored with a log line, and the analysis still runs. The file is no workflow, so the Scorecard API's restrictions on the workflow are unaffected.

All jobs use the Node.js version from `.nvmrc`; pnpm comes from `packageManager` in `package.json`. The root commands are the same ones contributors run locally (see [repository structure](repository-structure.md#root-commands)).

**Pinned actions** (the owner's decision of 2026-11-21): every third-party action and reusable workflow in `.github/workflows/` is pinned to a full commit SHA with its version as a trailing comment (`uses: actions/checkout@<40-hex SHA> # v7.0.1`), so a moved or re-pointed tag cannot change what CI or the release runs. A new or updated action is pinned the same way: resolve the tag to its commit with `gh api repos/<owner>/<repo>/commits/<tag> --jq .sha` and write the exact version in the comment. Local actions (`./...`) are not pinned; a Docker action names an image digest. `scripts/checks/pinned-actions.test.mjs` runs the check (`scripts/checks/pinned-actions.mjs`) on the repository's workflows as part of `node --test scripts/`, so an unpinned `uses:` or a SHA without its version comment fails the `Hard-coded configuration check` job.

**Pinned pnpm in the images:** the API, website and MCP Admin images install pnpm with `npm ci` from `infra/pnpm`, whose npm lockfile holds an integrity hash for pnpm and each of its native executables, never with `npm install` (pinned by version only). `scripts/checks/image-pnpm.test.mjs` keeps that version equal to `packageManager` and fails the same job on an `npm install` in a Dockerfile (`infra/README.md`, pnpm in the images).

**Dependabot** (`.github/dependabot.yml`) keeps the pinned actions current: once a month it opens one pull request into `master` with every GitHub Actions update grouped together, updating the SHA and the version comment, under a `ci: bump …` header that the commit-message check accepts. Its `npm` entry for `infra/pnpm`, the hash-pinned pnpm of the container images, opens a monthly `chore(deps): bump …` pull request for a newer pnpm, which must also move `packageManager` in `package.json` before `scripts/checks/image-pnpm.test.mjs` passes. Every week it also updates the pnpm workspace, its minor and patch updates grouped, the Dockerfiles' base images in one pull request, and the uv workspace of the Python members, grouped like the pnpm workspace. Dependabot locks with its own, newer uv, which the lower bound of `required-version` admits; `uv sync --locked` with the repository's uv then checks its lockfile, and `scripts/checks/uv-version.test.mjs` keeps that uv the one CI installs. What each entry does and how its pull requests are handled: [git workflow](git-workflow.md#dependency-pull-requests). Dependabot pull requests get no repository Actions secrets and, like every pull request that is not a phase pull request, select no paid eval suite: `Affected eval suites` ends green and the suites' jobs are skipped, also when a bump changes an action of `model-evals.yml`, MCP Admin's or the API client's locked dependencies, or the Python agent's (`uv.lock`). The owner decides whether such an update needs a manual, charged run of the affected suite (`workflow_dispatch`: `mcp-admin`, or `llm-agent` for a uv update of the chat agent's libraries) before merging.

**Affected packages.** The quality job checks out the full history and compares the head without its documentation (above) with the pull request's base commit, or on a push with the commit before the push (`TURBO_SCM_BASE`). Which packages that selects, and when every package is selected, is described in [Affected packages](repository-structure.md#affected-packages). A change to the shared configuration selects its consumers; a change to the harness, the checks or other root files selects no package, but the root tasks run on every change regardless.

**CI checks the head of the branch, not each commit.** A test-first issue branch has a commit with a failing test before the implementation; only the tip of the branch must pass.

**Evidence that a failure fails the pipeline** is recorded on the pull request that set the pipeline up (#75, issue #20): the run of a deliberately broken commit and the run of the commit that reverted it are linked there. No model evals, release pipeline or deployment runs in CI in phase 1.
