# Testing

What is tested, in which order, and how.

## Principle

Test external behaviour, not implementation: an HTTP request and its response, a rendered page, a tool call and its result, a function's output for an input. A test that breaks when code is refactored without changing behaviour is a bad test.

The project exists to ship a good product. The rules below are strict where a mistake is costly and light where a human eye judges better than an assertion.

## Where test-first is mandatory

The test is written first and must fail without the implementation. The reviewer checks the order in the branch history.

- Security: authentication — every private route rejects a request without a valid API key, and every write is a private route
- API contracts
- Services and domain logic
- Bug fixes — first a test that reproduces the bug

## Test surfaces and the red–green–refactor cycle

An approved issue/PRD identifies the behaviour and the public operation to test. Record the relevant surface (HTTP request, service operation, persistence operation, pure transformation or rendered visitor journey), what it observes and the important failure cases. Existing approval covers those tests; an unattended agent does not ask the owner to approve the same surface again. Ask only if a material scope/domain decision is genuinely unresolved.

Work in small observable slices: write one behavioural test, run it and confirm failure for the missing behaviour, commit the red test, implement enough to pass, then rerun relevant checks. Refactor after green without changing behaviour, and keep the tests. An import error or broken fixture is not the intended red evidence. Expected values come from the requirement or independently worked examples, not the implementation formula repeated in the assertion.

Tests enter the module through the operation they exercise and assert results/errors/state visible through that contract. Do not mock the internal call graph or assert helper call counts/order. Nontrivial internal pure functions may have focused tests without becoming public exports solely for tests. Do not add tests that only restate configuration, generated files or trivial forwarding code. Required security/HTTP/validation/persistence behaviour still needs tests even if a handler delegates it.

Persistence integration tests use real Postgres and separate temporary databases. Controlled clocks/randomness and external provider fakes are appropriate at real external interfaces; they do not replace actual database integration. Test failure/rollback outcomes through the relevant persistence/service/HTTP contract; low-level integrity checks are valid in tests whose subject is persistence integrity. Local-storage tests may use disposable real files; normal CI never needs Bunny credentials.

Both storage drivers run the same driver-contract cases. The Bunny driver runs them through an in-memory S3 endpoint plugged in as its transport, so the real S3 client builds and signs every request without a network. One opt-in suite, `packages/services/src/modules/storage/bunny-s3.integration.test.ts`, runs against a real development zone and is skipped unless `STORAGE_BUNNY_INTEGRATION=1`. Run it only with the development zone's credentials: set `STORAGE_BUNNY_ENDPOINT`, `STORAGE_BUNNY_REGION`, `STORAGE_BUNNY_ZONE`, `STORAGE_BUNNY_PASSWORD` and an https `STORAGE_PUBLIC_BASE_URL` in the shell, then run `STORAGE_BUNNY_INTEGRATION=1 pnpm --filter @sebela/services exec vitest run src/modules/storage/bunny-s3.integration.test.ts`. It writes below a fresh `development/integration-<random>/` prefix and deletes only the files it created. The same file holds the private storage checks (store, read and delete, no read outside the prefix), skipped unless `PRIVATE_STORAGE_BUNNY_INTEGRATION=1`; run them only with dedicated development keys of a private zone (`PRIVATE_STORAGE_BUNNY_ENDPOINT`, `PRIVATE_STORAGE_BUNNY_REGION`, `PRIVATE_STORAGE_BUNNY_ZONE`, `PRIVATE_STORAGE_BUNNY_PASSWORD`). CI runs the private driver contract with `local` and the in-memory endpoint only.

Use the project-local [tdd reference](../.claude/skills/tdd/SKILL.md); [codebase-design](../.claude/skills/codebase-design/SKILL.md) helps if the interface itself is unclear. Follow the UI and MCP/AI verification policies below; these references do not extend test-first requirements to typography or replace model evals with mocks.

## Where visual evidence is the standard

Layout, typography and responsive polish are accepted on:

- the acceptance criteria of the issue,
- Playwright checks for behaviour (navigation, interaction, no horizontal scroll),
- screenshots at **360, 768 and 1280 px**, in **light and dark** mode,
- for a page meant to be printed (the CV), a separate check with print media in both schemes: its colours, what it hides and a screenshot,
- a visual review by the reviewer and the owner.

A test written before the markup is not required here.

## Evals-driven development

MCP tools and AI features are developed evals-first.

- Evals are written before the implementation and state a pass threshold.
- They are written with promptfoo, pinned as an exact dev dependency of the suite's package and locked, not fetched for every run through `pnpm dlx`. A runner may run a few case-runs at once when each has its own fixture and results stay independent, bounded well inside the provider's rate limits (MCP Admin: four). They call real models, so they run on demand and for changes to the AI parts (`mcp-admin`, `ai-service`, `mcp-public`, the `llm-agent` package and `memory`), not on every pull request.
- Developers and agents run them locally while they work, through a package script wrapped in `node harness/with-secrets.mjs --`, which gives the command the `ANTHROPIC_API_KEY` of the main checkout's `.env.secrets` without the agent seeing it (`docs/permissions.md`, Environment files); an issue runs only affected cases and its eval gate is met by that local run, whose case IDs, partial/full scope, redacted summary and cost go into the pull request. Shared model/prompt/tool/context changes can affect the whole catalogue. Reuse compatible stored answers to verify deterministic grader fixes without new generation (MCP Admin: `node evals/run.js --regrade <run-folder>`); changed model judging still consumes its own paid budget. Each eval suite pins one model and effort, the one its real client uses (MCP Admin: Claude Sonnet 5.5 at `medium`, `.plan/done/05-mcp-admin/evals.md`). Without the key the eval gate cannot run, and the issue waits for the owner.
- **In CI, only the suites a change affects run, and not on every push.** `model-evals.yml` gives every eval suite (one per app or package with evals: MCP Admin now; `packages/llm-agent`, `apps/ai-service` and `apps/mcp-public` as they gain evals) its own job with the paths that can change its behaviour: its own folder and what it depends on (for MCP Admin `apps/mcp-admin/`, `apps/api/`, `packages/contracts/`, `packages/api-client/`, `packages/services/`, `packages/db/`). A suite runs in full on a pull request into `master` when it is opened, reopened or marked ready for review, unless it is a draft and the pull request changes one of its paths, and by hand (`workflow_dispatch`, one suite or all). New commits on that pull request do not start another charged run; the owner starts it again by hand when a fix needs it. Issue pull requests into phase branches never run paid evals. Phase 6 extends the workflow with its Python runner and keeps provider comparisons explicit and budgeted. This is the policy for every future eval suite, not only phase 5.
- Safety suites must pass completely. Other suites have a threshold set from the first baseline; it is never lowered to pass a run.
- They cover desired and forbidden behaviour: choosing the right tool, factual grounding, saying "I don't know", direct and indirect prompt injection, unsupported claims, source correctness, restraint with destructive tools.
- Evals live in `apps/mcp-admin/evals/`, `packages/llm-agent/evals/` and `packages/memory/evals/`. Phase 6 gates the package stages/structured reads before a server exists; phases 7 and 8 add HTTP/web/MCP integration; phase 9 adds retrieval/ingest evals without an LLM judge, phase 9.1 adds tool selection and grounded-answer evals, with graph and ontology evals after launch. Do not make a package-only phase depend on a future transport or real RAG.
- Code graders check deterministic properties; model graders use versioned rubrics calibrated against human labels. Human review covers ambiguous cases, grader disagreements and a sample of automatically passed answers. Record human scores and release decisions. For phase 6, the owner scores 12 recorded answers (6 EN / 6 CS) plus all disputed/ambiguous results in the phase PR or a linked report. Include case/run IDs, commit, model/effort, rubric version, scores and notes. PR approval accepts that evidence; it is not itself an individual human score and cannot waive a failing safety gate. See the fixed phase-6 gates and campaign allowance in `.plan/06-llm-agent/evals.md`.
- Measure attack success from outcomes and executed tool calls, plus legitimate-question false positives, latency and cost. Passing a finite safety suite is a release gate, not proof of absolute security.
- Use fictional adversarial fixtures. Real visitor/owner data never enters committed regression datasets.

### Memory evals

The retrieval evals of `packages/memory/evals/` (`packages/memory/AGENTS.md`, Evals) measure search without an LLM judge: recall@pool over graded relevance, nDCG, precision, MRR, correct and false empty results below the relevance floor, provenance accuracy, latency and cost per query.

- `pnpm --filter @sebela/memory eval [--case <id>] [--publish <name>] [--max-cost-usd <n>] [--min-interval-ms <n>] [--variant reranked|hybrid|vector|fulltext]` runs through `node harness/with-secrets.mjs --`, which supplies `VOYAGE_API_KEY`; `--plan` prints what would run, free. A run spends at most USD 1 (the default and the maximum of `--max-cost-usd`), enforced as the API's monthly retrieval ceiling (embedding and reranking) on the run's fresh database.
- A measured run starts the API's end-to-end server on a temporary database with the fictional demo seed, indexes it and records the candidate pools through the API's `knowledge` command (all questions embedded in one batch), then sends every question to the private search route, one at a time. Provider calls are paced at least `--min-interval-ms` apart (default 21 000 ms, safe for a key limited to 3 requests a minute; lower it for a higher limit), and the run's API and command retry a rate-limited call up to 6 times, waiting at most a minute each; the summary records the pacing. It needs the running Postgres and a build of the API's packages.
- `--variant` picks what is measured, passed to the run's API as `RETRIEVAL_EVAL_VARIANT`: `reranked`, the deployed search (the default: vector and full-text candidates fused by reciprocal rank, scored by the reranker, the floor on its score), or a baseline: `hybrid` (the fused pool in its order, no reranker, no floor), `vector` (cosine similarity, the floor on it) or `fulltext` (Postgres text search over the same chunks, no query embedding, no floor). The summary records each returned passage's score, so the floor and the final count can be calibrated offline from one run with the floor at 0. That setting exists for eval runs only; a deployment leaves it unset.
- The gate is `evals/thresholds.json`: frozen minimums for what the phase PRD gates (recall@pool, nDCG, correct-empty rate), with the baselines and the method they were set by; MRR, hit rate, precision, the false-empty rate, provenance accuracy, latency and cost are reported, not gated. It applies only to a complete run of the deployed variant it names, and a slice that deploys another pipeline switches that variant in the same change; a partial run or another variant reports metrics and why the gate did not apply. A failed gate exits 1 and lists each failing metric. Later slices may only raise a threshold.
- Cases the system cannot answer yet (`plan.js`) are reported pending, never passed; without the key every case is pending (exit code 2). Publish paid baselines to `evals/results/` with their cost, and post the cumulative spend in the pull request.
- Ordinary tests never call the provider: the deterministic fake embedder is a bag of words, so a test query uses the target record's own words and a no-evidence query uses words absent from the seed. `evals/evals.test.ts` checks dataset, graders, plan and options with `pnpm test`.

## Knowledge publication and source privacy

- Phase 9 tests the terminal ingest boundary before implementation: supported formats/extraction limits, local sensitivity checks, approval tied to content/version, no external embedding call before approval and no public access to pending/rejected material.
- Test API fact precedence, source/version labels, atomic replacement, withdrawal/deletion, index rebuild and embedding-model migration with real Postgres/pgvector plus fake embeddings.
- Approved extra passages may be public; raw originals, staging metadata and storage credentials are not. Test attempted downloads through public media/API/CDN routes and private-local-root path traversal. Optional Bunny tests use development-only credentials; ordinary CI needs none.
- Later graph/ontology assertions retain provenance and source withdrawal rules. Compare measured quality against the prior deployed baseline; passing a test suite never proves every secret or contradiction can be recognized.

## Authentication as a property

There is one test that walks every route of the API and asserts: each write route and each private route returns 401 without a valid API key. A new route is covered automatically, so a write can never be left open by mistake. The chat conversation routes are the one named exception, with their own tests that they can touch only the caller's own conversation.

The API's audit coverage is the same kind of property (`apps/api/src/audit.test.ts`): it walks every route the HTTP framework registered, and any route for a method other than `GET`, `HEAD` or `OPTIONS` that is not an audited content write fails it, so a newly registered write cannot skip the audit. For every audited write it also checks that a refusal without a key or an invalid request stores no audit entry, and that reads store none.

Admin MCP adds deterministic tests for authentication before discovery, every HTTP method/session operation, next-request revocation, strict entity/field allowlists, injection/path/SSRF attempts, credential redaction and bounded work. Deployment verification proves that both MCP Admin and private content-write API routes are unreachable through the public edge, with the authenticated internal/SSH-tunnel path working. MCP destructive annotations and model restraint evals are not substitutes for enforced authorization or supported-client approval configuration.

## Website browser tests

The website's Playwright tests (`apps/web/e2e/`, `pnpm test:e2e`) read a real API, never a mock: the API's end-to-end server (`apps/api/src/cli/e2e-server.ts`) creates a temporary database, migrates it, loads a small fictional seed folder from `apps/web/e2e/fixtures/` with its own temporary local storage, and drops both when it stops. The demo seed and the checkout's database are never used. They cover behaviour (content and links, the missing-photo fallback, the unavailable state and its retry, keyboard order), automated accessibility (axe), touch targets and no horizontal scroll, and take the screenshots at 360, 768 and 1280 px in light and dark mode that the visual review uses. Each page's spec checks it in detail; `e2e/handoff.spec.ts` checks the site as a whole — every page with the longest fictional content (`fixtures/with-long-content/`), whole words in labels, print, and the client, recruiter, evaluator, chat and keyboard journeys across pages. The complete containerised stack has its own browser step against the website container (`pnpm test:web-stack`, CI below), which `pnpm test:e2e` leaves out. Spec files run in parallel and the tests of one file in order: 3 workers on a development machine, 4 in CI, or the number in `E2E_WORKERS`. Files share only the main stack, which they read and never change; the blocks that need other content start their own API and website on a temporary database and free ports. Set `E2E_WORKERS=2` (or `1`) on a machine that is busy with other work. `test:e2e` runs through `harness/one-at-a-time.mjs e2e`, so on one machine at most one website browser-test run is active across the main checkout and every worktree; a second run waits (it says whose run it waits for) and gives up after 60 minutes (`ONE_AT_A_TIME_MAX_WAIT_MINUTES`). Parallel phase loops on a small shared server would otherwise exhaust its memory. Details and prerequisites: `apps/web/AGENTS.md`, Tests.

## Consumer contract tests

`apps/api/src/client.test.ts` calls the real app through the generated `@sebela/api-client`, over a temporary database, as a server-side consumer would: the public person read, the authenticated writes, and the validation, not-found, conflict, authentication and rate-limit errors through the contract's types. Requests go to the app's `fetch` directly, so no port or host is involved. Every pull request that adds, removes or changes a route or a contract schema regenerates the client (`pnpm generate:api-client`), commits the result and extends these cases for the changed operations; CI's drift check fails otherwise.

## Configuration in tests

Tests follow the same rule as the code: no hard-coded port, local host address or database name (see [the hard-coded configuration check](repository-structure.md#the-hard-coded-configuration-check)). A test takes an expected port from `.env.example` or from the configuration it passes in, and leaves a fixed value to fixture files whose purpose is to hold it.

## Databases

- Each worktree has its own database and database role, and its tests connect with that role's credentials (see `docs/repository-structure.md`). The harness tests check the worktree lifecycle through a fake at the harness's database interface, so `node --test harness/` needs no Docker; `node harness/worktree-databases.e2e.mjs` checks the same lifecycle against a real, disposable Postgres from `compose.yaml`, on demand and in the CI job `Worktree database lifecycle` (see [Worktree databases](repository-structure.md#worktree-databases)). The backend stages of setup and cleanup (install, migration, storage, seed) are tested through a fake at the harness's backend interface, including a failure at each stage, retry and slot bookkeeping; `node harness/worktree-backend.e2e.mjs` runs them for real on two worktrees of a temporary clone, with local storage and no cloud keys, on demand and in the CI job `Worktree backend setup` (see [Worktree backend setup](repository-structure.md#worktree-backend-setup)).
- Tests use a separate temporary database, so they never touch the data an agent is looking at in the browser. Each backend test file (`apps/api`, `packages/services`, `packages/db`) creates its own `test_<random>` database through `@sebela/db/testing` with the role from `DATABASE_USER`/`DATABASE_PASSWORD`, migrates it from the committed migrations (or leaves it empty when the test is about an empty database) and drops it afterwards. There is no mocked database.
- The backend tests read `POSTGRES_HOST`, `POSTGRES_PORT`, `DATABASE_NAME`, `DATABASE_USER` and `DATABASE_PASSWORD` from the process environment, falling back to `.env.local`, `.env` and `.env.example` of the checkout (their `vitest.config.ts`). Turborepo's strict environment mode hides undeclared variables from tasks, so `turbo.json` passes exactly these through to `test` (`passThroughEnv`; they do not change cache keys).
- Tests use small fictional fixtures, never the demo seed, so that editing demo content cannot break a test. The one exception is the seed command's own test (`apps/api/src/cli/seed.test.ts`), which loads the demo seed to prove the default folder loads completely.

### Browser tests by role

The website's browser suite (`pnpm test:e2e`) takes minutes, so each role runs only its share of it:

Locally nobody runs the whole suite: it takes long, it competes for the memory of the machine the parallel phase loops share, and CI runs it anyway before anything merges.

- **Every developer (frontend, backend, AI):** only the spec files its change adds or touches, by path (`pnpm --filter @sebela/web test:e2e e2e/<name>.spec.ts`, after `pnpm --filter @sebela/web build`), and while fixing one failure only that test (`-g "<title>"`). A change that cannot change the website (the same paths CI's `Website affected` step skips: `docs/`, `.plan/`, `.claude/`, `harness/`, the MCP apps, the AI service, `packages/llm-agent`, `packages/memory`, Markdown) runs no browser tests at all.
- **Reviewer:** the specs the change adds or touches, plus the specs of the pages a changed shared part feeds (a shared component, a website module, an API route or contract the pages read), once per review; none when the change cannot change the website. A re-review after fixes runs only the specs the fixes touch and the ones that failed. The reviewer does not run the whole suite.
- **CI:** the whole suite on every pull request the website is affected by, as the condition for merging; the orchestrator merges only with every check green, so a spec broken elsewhere is caught there.

## CI

Lint, typecheck, tests and build must pass before a pull request can merge. A failing check is fixed, not disabled. The orchestrator merges an issue pull request only when every check reported on it is green (`gh pr checks --watch`).

Two workflows run on every pull request and on pushes to `master`. A phase branch has no push run: it changes through issue pull requests, which ran CI on their merge with it, and its open phase pull request runs CI on every push, so a push run would check the same commit twice. Every job runs on every event: none is skipped by a path filter, so a status is never left waiting or reported as skipped.

**Website jobs.** `Website end to end` and `Website stack smoke` start with the step `Website affected`: when every file the change touches is one that cannot change the website — `docs/`, `.plan/`, `.claude/`, `harness/`, `apps/mcp-admin/`, `apps/mcp-public/`, `apps/ai-service/`, `packages/llm-agent/`, `packages/memory/`, Markdown anywhere, `model-evals.yml` or `commit-messages.yml` — the job reports success at once and starts no browser or stack; the step's log lists the files. Any other file, a new branch or a base that cannot be resolved runs the job in full, so a change to the API, the contracts, the shared packages, the lockfile, the scripts or this workflow always runs it. Their screenshots and reports are kept for 14 days.

`.github/workflows/model-evals.yml` runs paid model evals, so it is not a required status check and runs only what a change affects: on a pull request into `master` when it is opened, reopened or marked ready for review, unless it is a draft (new commits start no charged run), and by hand (`workflow_dispatch`, one suite or all). Each eval suite is one job behind the `Affected eval suites` job, which compares the pull request with its base:

| Job                     | Steps                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Affected eval suites`  | Lists the files the pull request changes against its base and marks each suite affected when one of its paths changed; a manual run marks the chosen suite, or all                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `MCP Admin model evals` | When affected (`apps/mcp-admin/`, `apps/api/`, `packages/contracts/`, `packages/api-client/`, `packages/services/`, `packages/db/`, `pnpm-lock.yaml` or the workflow): `pnpm install --frozen-lockfile`; the `postgres` service of `compose.yaml` as in the quality job; the build of MCP Admin, the API and their dependencies; the complete catalogue through `node evals/run.js` with the repository secret `ANTHROPIC_API_KEY`, which fails without the secret or when a gate fails. Only the redacted `summary.json` is kept, as the artifact `mcp-admin-evals`; the stored answers stay out of it |

A new eval suite adds its own job with its own paths in the same way.

All jobs use the Node.js version from `.nvmrc`; pnpm comes from `packageManager` in `package.json`. The root commands are the same ones contributors run locally (see [repository structure](repository-structure.md#root-commands)).

**Affected packages.** The quality job checks out the full history and compares `HEAD` with the pull request's base commit, or on a push with the commit before the push (`TURBO_SCM_BASE`). Which packages that selects, and when every package is selected, is described in [Affected packages](repository-structure.md#affected-packages). A change to the shared configuration selects its consumers; a change to the harness, the checks or other root files selects no package, but the root tasks run on every change regardless.

**CI checks the head of the branch, not each commit.** A test-first issue branch has a commit with a failing test before the implementation; only the tip of the branch must pass.

**Evidence that a failure fails the pipeline** is recorded on the pull request that set the pipeline up (#75, issue #20): the run of a deliberately broken commit and the run of the commit that reverted it are linked there. No model evals, release pipeline or deployment runs in CI in phase 1.
