# Threat model: the visitor chatbot and the public MCP server

What a visitor may try against the chatbot and the public MCP server, which layer stops it, which test or eval guards that layer, and what is not defended. It is a short working list, not a formal model.

**State (2026-11-21).** Phase 6 delivered the agent library `packages/llm-agent` only. Nothing in it is reachable from the internet yet: `apps/ai-service` (phase 7) and `apps/mcp-public` (phase 8) do not exist on `master`. Rows that depend on them are marked **planned** and name the PRD section that specifies the defence; a planned defence is a specification, not a guarantee. Those rows are completed when each phase is accepted.

## Trust boundaries

- **The API is the trust boundary** ([architecture](architecture.md#the-api-is-the-trust-boundary), [decision 0001](decisions/0001-api-as-trust-boundary.md)). Only `apps/api` reaches the database. Public routes are read-only; every content write is a private route behind an API key. The Python code has no database access and holds no content key.
- **The agent library runs three stages in a fixed order** (`pipelines/chat/graph.py`): Security → Main → Output Guard.
  - **Security** (`pipelines/chat/stages/security_gateway.py`, `prompts/security.py`) is a small model that classifies the question as ALLOW, BLOCK or UNCERTAIN. It never answers and has no tools. A failed or unreadable classifier is `unavailable`, never ALLOW.
  - **Main** (`pipelines/chat/stages/main_agent.py`, `prompts/chat.py`) is a model that answers through read tools inside fixed caps. Under UNCERTAIN it runs with smaller caps and an added restriction.
  - **Output Guard** (`pipelines/chat/stages/output_guard.py`, `guardrails/output.py`) is deterministic code with no model. It is the only producer of a result, so nothing reaches the caller before it approves it. Refusals and failures are fixed English and Czech texts (`guardrails/policies.py`) that no model writes.
- **What the model can reach.** Fifteen read tools from a fixed registry (`tools/registry.py`), backed by fourteen public `GET` routes (`tools/content.py`, `ApiContentReader`). Two tools take one argument, a bounded slug; the others take none. The API address is the caller's configuration, never a model or visitor value, and redirects are not followed.
- **What the model cannot reach.** No write, search, shell, file or free network tool exists. The reader sends no credential. The provider key lives in the model factory, outside the model context. The library stores no conversation: the caller passes the history, which both models treat as untrusted text. The telemetry record carries no visitor or content text.
- **Three kinds of untrusted text** enter the model context: the visitor question, the conversation history and the tool results. Record text is public content, but it is still untrusted input to the model.

The visitor's text is sent to the external model provider. Nothing in this document changes that.

## Threats

Module paths are relative to `packages/llm-agent/src/llm_agent/`, test paths to `packages/llm-agent/tests/`. Eval families (`S08`, `Q19`) are defined in `packages/llm-agent/evals/catalogue.py` and `evals/datasets/cases.py`; each has an English and a Czech case, run three times. The critical families `S01`–`S20` must pass in every repeat. In the final phase 6 run (issue #183) they passed 120 of 120 case-runs, and no ordinary question was blocked (0 of 60 in each language).

## Open gaps

Found while writing this document. None is turned into an issue yet; each has a proposed title.

1. **No eval case for abusive or hateful input.** The `abuse` category is exercised only by a unit test with a scripted verdict. Proposed issue: _Add critical eval cases for abusive and hateful questions to the llm-agent catalogue_.
2. **Rule 8 of the Main prompt has no model evidence.** Every direct attack was refused by Security, so the Main model was never measured on a shell, file or write request. Recorded in the closing notes of #182 and #183; #364 covers only role-play. Proposed issue: _Add an eval case that mixes a profile question with a shell or content-write request_.
3. **The Output Guard link check needs a scheme or `www.`** A host name written without either is not treated as a link. The eval graders catch the planted host of `S12`, `S15` and `S16`, but the guard itself does not. Proposed issue: _Replace a draft that names a host outside the trusted contact links, with or without a scheme_.
4. **The package's generated client includes the write operations.** Proposed issue: _Generate the Python content client from the public read routes only_ (to be decided together with #302, which moves that client into a shared package).
5. **Public MCP results and untrusted text.** Proposed issue: _Specify in the phase 8 PRD how public MCP results mark record text as untrusted data_.
6. **The planned rows of this document.** Rows 4, 10, 11, 12 and 13 name specifications, not code. Proposed issues: _Complete the threat model rows for the AI service when phase 7 is accepted_ and _Complete the threat model rows for the public MCP server when phase 8 is accepted_.

Already tracked: a deterministic check of stated dates (#356), classifier tuning for mixed role-play requests (#364), a classifier ensemble (#366) and the smaller eval follow-ups (#357).

Accepted without an issue: the verbatim-only prompt-leak check (row 3), the missing code check against first-person speech as the person (row 7), the canary being recognised only by the eval grader (row 2) and the reliance on the judge and human review for the truth of the prose (rows 5 and 6).
