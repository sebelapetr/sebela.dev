# Architecture

How the system is layered and why. Parts belonging to later phases are described as planned; see `.plan/00-overview/prd.md` for the phase of each.

## Overview

```text
browser -> web -> api -> ai-service -> packages/llm-agent (chat pipeline)
external agent -> mcp-public -> ai-service (read capabilities) -> api
owner's agent -> mcp-admin -> api (authenticated content writes)
api -> packages/services -> packages/db -> PostgreSQL
                        -> packages/memory (knowledge ingest/retrieval orchestration)

Retrieval persistence is owned by packages/db in the same pgvector-enabled Postgres.

AI-service tools read public content/search through api over HTTP.
```

## The API is the trust boundary

The website, `mcp-admin` and `ai-service` reach content only through `apps/api` over HTTP. The website's one other read, the current CV PDF's public stored file at the address the API gives, is described under Website. The public MCP adapter reaches AI read capabilities through `ai-service`, which reads the content API. Only the API backend accesses persistence.

This is a security decision, not a preference for HTTP. The system has write access for agents, two MCP servers with different threat models and a public chatbot. Content authorization is enforced at the API. FastAPI separately authenticates its internal generation route and applies AI runtime admission; public MCP reads cannot invoke it. Neither Python app can bypass content authorization.

The cost is extra HTTP hops and independently managed runtime processes. This is accepted for the content and AI boundaries.

## Module responsibilities and composition

A domain may have an HTTP module in the API, an operation in services and a persistence module in db. Those are different responsibilities, not three public versions of the same implementation. HTTP adapts the request/response and applies security; services coordinate the domain use case; db performs cohesive persistence operations and owns SQL/transaction mechanics. Contracts describe transport data independently of services and db. Storage hides provider SDKs/key layout; media coordinates upload checks, metadata, attachment and cleanup.

Create resources at the backend startup/composition entry and the corresponding maintenance CLI path. Keep package dependencies unchanged: API composition calls permitted services entries, and services use db through persistence entries. Do not import db directly into API startup as a shortcut, or pass raw database/SDK handles out to HTTP/client code. Pass validated configuration and the required capabilities once; runtime modules do not repeatedly read environment variables or construct hidden clients. Close owned resources at shutdown.

For a multi-record mutation, the caller requests a complete operation. Services ask db to perform the necessary atomic persistence change; callers never manage SQL transaction primitives. One named exception: a services use case that must apply many complete operations as one (today only the seed load) runs them inside `Persistence.transaction(work)`, a caller-scoped unit of work that commits or rolls back all of them, runs their own transactions as savepoints and still hands over only persistence operations ([decision 0015](decisions/0015-caller-scoped-unit-of-work-for-the-seed.md)). File storage and database commits are not one transaction: media explicitly owns validation, ordering and compensation/cleanup on failure. Public interfaces document these guarantees and expected errors.

SQL and driver objects do not cross these entries. A caller holding a transaction, a table or an S3 client could perform half of an operation, bypass validation or depend on one driver, and every change of persistence or provider would reach it. Callers receive domain results and documented errors instead.

Module dependencies are acyclic and cross only explicit entries. [Repository structure](repository-structure.md#backend-module-layout) defines imports/placement; [code standards](code-standards.md#deep-modules) explains interface design and review. Required HTTP/security adapters remain even if they are small; deep modules do not remove the API trust boundary.

## Data

- **The API/database is authoritative for structured facts.** Approved supplemental documents add explanations and context without overriding API facts. Nothing in the repository mirrors real content or original documents.
- One database, separate Postgres schemas per domain: `profile`, `auth` (API keys), `ai_roadmap`, later schemas for chat, retrieval and private ingest state. Migrations are applied by the db package's own command (`pnpm --filter @sebela/db db:migrate`); starting the API never migrates. Domains are linked through shared topics and technologies.
- Content is written through the API — by agents using `mcp-admin` — and appears on the website without a redeploy. Backend maintenance CLIs (seed/key commands and phase-9 knowledge ingest) reuse services and their persistence operations in-process; these are not client/Python database-access exceptions.
- The repository ships a fictional demo seed. The owner's real data is loaded once from a private seed outside the repository; afterwards safety comes from database backups.

## Files

- Images and the CV file are kept in object storage behind one interface with two drivers: Bunny Storage through its S3-compatible API, and local disk for tests, CI and environments without keys.
- Uploads go through a private API route; nothing uploads to the bucket directly.
- The database stores a file's key; the public base address is configuration.
- Uploads are proved by their content: PNG, JPEG, WebP and PDF only, within configured byte and image-dimension limits, checked structurally with work bounded by the file size. Pixels are deliberately never decoded: a structural walk keeps the work predictable and needs no image library, at the cost of accepting a well-formed file whose image data is corrupt. The API generates every key; a file name never chooses where a file goes.
- Files of the local driver are served by the API itself at a public route under the key, inline, with the recorded type, `nosniff` and a content security policy that loads nothing. Images are also sandboxed; a PDF is not, because browser PDF viewers refuse to render a sandboxed document, and it is offered under the file name of its key, so the current CV opens in the browser; files of the Bunny driver are served by the zone's CDN pull zone from `STORAGE_PUBLIC_BASE_URL`, never from the storage API.
- Profile records refer to media by identifier (the person's photo and current CV PDF, an organization's logo, a project's cover, a testimonial's author photo), and so does a bookshelf book's cover. Referenced media cannot be deleted. The current CV PDF is uploaded as prepared, not generated.
- A file the media workflow cannot remove, after a failed record write or a deleted record, is logged with its key without secrets and stays as an orphan no record refers to; it is removed by hand. A successful response never refers to a missing file.
- Development and production use separate storage zones with separate keys.

### Bunny Storage

The `bunny-s3` driver talks to a Bunny storage zone through Bunny's S3-compatible API with the maintained AWS S3 client, path-style, using only PutObject and DeleteObject. Sources, checked on 2026-11-16: [S3 compatibility](https://bunny.net/docs/storage/s3) and the [storage changelog](https://bunny.net/docs/storage/changelog).

- **Status.** S3 compatibility is a public preview (since 2026-07-09); behaviour may still change.
- **Zone.** S3 compatibility must be enabled when the zone is created; an existing zone cannot be switched. Only the regions the documentation lists have an S3 endpoint (`https://<region>-s3.storage.bunnycdn.com`); other regions answer 501.
- **Credentials.** The access key id is the zone name (also the bucket) and the secret is the zone password. They are signed into requests and never sent, logged or put into an error.
- **Limitations that shape the driver.** No ACLs, object lock, versioning, server-side encryption or lifecycle rules, and conditional writes are not documented, so a new file is not guarded against replacement by the zone; keys carry 122 random bits instead. Bunny validates `x-amz-checksum-sha256`, so every upload sends it and the SDK's default CRC32 checksum is turned off. Bunny documents `NoSuchKey` (404) but not what a single DeleteObject of a missing key answers, so the driver counts `NoSuchKey` as removed and every other failure, another 404 such as `NoSuchBucket` included, as an error. Metadata is limited to 2 KB; the driver sends none. Requests are rate-limited (500 per second).
- **Delivery.** Public files are served by a CDN pull zone attached to the storage zone; `STORAGE_PUBLIC_BASE_URL` is its https address and may not be the storage endpoint. Presigned addresses are not used. Uploads still pass through the private API.
- **Minimum configuration.** `STORAGE_DRIVER=bunny-s3`, `STORAGE_BUNNY_ENDPOINT`, `STORAGE_BUNNY_REGION`, `STORAGE_BUNNY_ZONE`, `STORAGE_BUNNY_PASSWORD`, `STORAGE_ENVIRONMENT`, `STORAGE_PUBLIC_BASE_URL` and, in `development`, `STORAGE_WORKTREE`.
- **Zones and keys per environment.** Production has its own zone and password, held only by the production deployment. Development has a separate zone that every development worktree shares; each worktree writes below `development/<worktree>/` and its driver refuses any key outside that prefix, so it cannot touch another worktree's or production's files. A development worktree never needs the production password, and the local driver needs no key at all.
- Logos of technologies are static assets of the website, not uploads.
- From phase 9, knowledge originals use a separate private Bunny Storage Zone/credentials without a public Pull Zone/CDN mapping, or a separate private local root outside static serving. Reuse the configured `bunny-s3`/`local` drivers, but private operations do not yield public URLs. An unavailable provider fails explicitly rather than silently switching stores.
- Public query embeddings/reranking require API-owned retrieval and overall-AI budget admission, including anonymous MCP searches; public read-only status does not make hosted search free. Exhaustion/provider failure is distinct from finding no evidence.
- Back up originals and source/version/approval metadata; embedding indexes are derived and rebuildable. Only the backend/maintenance path reads originals; neither MCP nor Python receives storage credentials.

## Access

- No user accounts and no login UI.
- The API has two groups of routes:
  - **Public** — no authentication; read-only, except that a visitor may create, continue and delete their own chat conversation (phase 7). The website and the assistant use these.
  - **Private** — protected by an API key checked in middleware. Every write is a private route.
- API keys are created with a command, shown once and stored only as a hash. Each has a name and can be revoked on its own. A key is used only by server-side callers and never reaches a browser: the website calls public routes only.
- Every request passes the same checks in order, before any handler: a per-client rate budget (health has its own), refusal of credentials in the query string, then on private routes the bearer key and a per-key budget, then on routes with path parameters their schema, then on routes with a body its content type, size and schema. Rate limits are bounded, in memory and per process; `X-Forwarded-For` counts only from configured trusted proxies. Every failure uses the common error shape of `@sebela/contracts`; CORS is not enabled. Details: `apps/api/AGENTS.md`.
- Every content write is audited by the API in the same transaction as the change (decision 0021): the API key that authenticated the request (never a value the request states), the operation and route, an optional bounded provenance label the caller states in the `sebela-provenance` header, the entity and record, and the record's public read before and after go to the private `audit` schema. An audit that cannot be stored rolls the content back; a refused or failed write and every read store nothing; credentials, other headers and file bytes are never stored. This covers every API caller alike, MCP Admin and direct API clients. The newest changes are read on the private `GET /v1/audit/changes`. A provenance label is what the caller said, never proof of who acted or that a human approved. The audit is not the website notification: notification stays best effort after the commit. Details: `apps/api/AGENTS.md`.
- A successful write passes through one notification attachment point in the API, which reports the content domain and record it changed. Its consumer is the website invalidation sender when `API_WEB_INVALIDATION_URL` and `API_WEB_INVALIDATION_SECRET` are set; otherwise it is a no-op. The knowledge indexing queue attaches to the same point when retrieval and a provider key are configured; the app takes several notifiers and calls each in turn, a failing one never stopping the next or the write.
- Profile/roadmap content has no per-record private flag. Auth, audit, conversations and pending/rejected ingest records are private operational state. Only approved knowledge passage projections are exposed; raw originals and staging data are not public. See `docs/domain-context.md`.
- Admin MCP and private content-write routes are internal/SSH-tunnel only, with authentication still required. Apply this to the public API proxy too, so it cannot provide a route around MCP's network boundary. The visitor-owned conversation exception remains public.

## Website

Next.js is used as a frontend only. Pages render on the server at request time, with caching and invalidation when content changes — not at build time. The build therefore needs no running API, and a content edit needs no deploy.

The website reads content from the API's public routes only. Two reads leave the API. For the CV PDF download (`/cv/pdf`) the website's server fetches the current PDF's stored file from the public `url` the API's media gives, which is the API's own file route with local storage and the storage's CDN pull zone (`STORAGE_PUBLIC_BASE_URL`) in production. A PDF directly below `WEB_MEDIA_BASE_URL` is read from `WEB_MEDIA_READ_BASE_URL` when that is set (the website container reads the API's file route inside the Compose network); any other address only over https or plain http on the API's own origin. It follows no redirect, sends no credentials and passes the file on only when it arrives whole as a PDF. This is a public file anyone can fetch, not a way around the API's access rules: which file is current is still decided by the API. The second is the stored images: pages name them by the website's own path `/media/<file>`, whose route reads the image file of that name directly below `WEB_MEDIA_BASE_URL` (the storage's public address with its environment and worktree folder), or below `WEB_MEDIA_READ_BASE_URL` when set, without a query, credentials or a redirect, never an address a visitor names. The image optimizer (`/_next/image`) reads only that path and no other host, so its settings depend on no environment and no internal address reaches a browser (decision 0018); which image a page shows is still decided by the API's media (`apps/web/AGENTS.md`, Media and previews).

From phase 3, committed API content writes notify the website's invalidation endpoint, authenticated with a dedicated server-only signing secret independent of content API keys. The website still reads only public API routes and holds no content API key. Validated content references map to affected pages, with safe duplicate delivery and bounded retries. Notification failure never undoes a committed write; time-based revalidation recovers from lost notifications. Freshness and failure criteria are defined in `.plan/done/03-web/prd.md` under "Cache invalidation guarantees". The website keeps the API's public reads in a bounded, process-local content cache; its receiver (`POST /internal/invalidation`) verifies the exact body bytes, maps each change's content domain through its own dependency map, never a caller-supplied address or cache key, and clears the whole profile cache, which every page, metadata output, sitemap, `llms.txt` and preview image is rendered from. Entries also expire after a fallback revalidation interval (`WEB_CONTENT_REVALIDATE_SECONDS`, 60 seconds by default), so a lost notification leaves content stale for at most that long while the API is available; this bounds failures and is not the ten-second target of healthy notifications. While the API is unavailable, an expired copy is served rather than an error, and an uncached page shows its unavailable state; failed reads are never cached as content. The endpoint is served on the website's public origin; its only protection is the signature, so the secret must stay server-side. The cache is per website process: a notification reaches one instance, so with several instances the others stay stale for up to one fallback interval (`apps/web/AGENTS.md`, Caching and invalidation).

Discovery outputs (sitemap, `llms.txt`, structured data and Open Graph cards) are built by the website from the same public reads as its pages, so they need no API route of their own and are refreshed by the same notifications. For the AI Roadmap these are the tree, area and module details, diary and day, statistics, bookshelf and book, events and the supporting lists (project ideas, followed sources, glossary terms); the content domains each write notifies are listed in `apps/api/AGENTS.md`.

Analytics are optional and off unless configured. With `WEB_ANALYTICS_SCRIPT_URL` and `WEB_ANALYTICS_WEBSITE_ID` set, every page loads a cookieless, Umami-compatible tracker after it becomes interactive, so it never blocks content or interaction; with both empty, or either unusable (validated on the server, logged without its value), pages carry no trace of it. The settings are read per request, so every page is rendered per request and the build output depends on no environment. Automatic tracking is turned off: the website reports one page view per navigation with only the canonical path (an address that is no page of the site as the fixed `/404`), never a query, a fragment, a conversation identifier or chat content, and a hook drops those from anything else the tracker would send. A tracker that fails to load or a collector that fails never breaks navigation, theme or chat. Smartlook and Google Analytics are not used, and there is no consent banner. The production account, its free plan's limits and deployment are phase 10's; choosing a cookieless tool does not by itself establish legal compliance (`apps/web/AGENTS.md`, Configuration).

## MCP servers and the AI runtime

| App/package          | Language         | Responsibility                                                                        |
| -------------------- | ---------------- | ------------------------------------------------------------------------------------- |
| `apps/mcp-admin`     | TypeScript       | Authenticated management tools -> private content API; internal/SSH-tunnel access     |
| `apps/mcp-public`    | Python           | Public read tools -> FastAPI capability routes; external agents bring their model     |
| `apps/ai-service`    | Python / FastAPI | Separate AI HTTP routes, chat generation, read capabilities and runtime lifecycle     |
| `packages/llm-agent` | Python           | Library: pipelines, shared read-tool implementations, providers, guardrails and evals |

Delivery is incremental: phase 6 builds the package and local runner; phase 7 wraps it in FastAPI and replaces the web mock using structured reads; phase 8 adds public MCP. Phase 9 builds the knowledge base behind a private, API-key search route; phase 9.1 adds the agent's search tool, public MCP search and public search with budget admission. Apps are separate deployables; the package is installed in Python app images and has no server lifecycle. Read capability implementations are shared through the package: chat invokes them internally and MCP calls them through FastAPI. The public MCP server exposes no chat tool. `mcp-admin` calls the content API directly and does not depend on the AI runtime.

`mcp-admin` is built on the official MCP TypeScript SDK behind Hono and stores no API key. The caller presents its own content API key as `Authorization: Bearer`; before discovery and on every later request MCP Admin checks it with the API's private `GET /v1/authentication`, which reuses the API's existing key verification and returns no key details, and fails closed when the API cannot answer. Its private API calls (content writes and the audit read) carry that key, and each write carries a `sebela-provenance` label the API audits with the verified key; its public reads carry neither. The API destination is MCP Admin's own configuration, never chosen by a caller or a tool argument, and redirects are not followed. It advertises seven content tools (`describe`, `list`, `get`, `save`, `delete`, `upload`, `recent_changes`) over one fixed entity-to-operation registry built from generated API routes and contract schemas, and six learning task tools (`find_resource`, `add_resource`, `set_resource_status`, `log_session`, `save_event`, `save_book`) over the same content module; a study session is the API's single atomic `POST /v1/roadmap/sessions`, and a link is only compared with stored links, never requested; `upload` sends caller-provided, size-bounded base64 file bytes to the API's private `POST /v1/media`, which inspects and stores them, and returns the media ID that `save` then attaches; it checks identifiers and fields before any call, reads a record before changing or deleting it, sends each write once and settles a lost answer through the API's audit rather than by retrying. It has no database, storage or arbitrary HTTP access; tool annotations are hints for the client, not consent, and authorization stays the API's. Request order, limits, tools and supported clients: `apps/mcp-admin/AGENTS.md`.

`apps/api` and `apps/ai-service` have separate routes and OpenAPI contracts. Content/event schemas are generated from the content API; FastAPI validates AI-specific contracts with Pydantic. Content authentication and its hashed-key store stay in TypeScript. Internal chat generation uses a separate service credential unavailable to the model, granting no content-write authority. Public AI read routes cannot call generation or private content routes.

## Knowledge and retrieval

- Phase 9 adds RAG over the owner's portfolio API content and extra owner-supplied Markdown/TXT/text-layer PDF documents. There is no duplicate crawl of rendered pages, external-source crawl or live web search.
- `packages/memory` retains its planned TypeScript knowledge/index boundary, called only by the API backend. It does not store visitor conversation memory. SQL/persistence remain behind the backend's db operations; Python reads bounded API capabilities only.
- Chunks, vectors, sources and versions live in a separate schema in the same PostgreSQL/pgvector. Hosted embeddings, full-text/vector/hybrid search and optional reranking are selected with evals; no second vector database is required.
- Terminal ingest stages extra files privately, extracts text under limits, runs local sensitivity checks and obtains explicit owner approval of that exact version before external embedding calls or public indexing. Rejected/pending content never reaches search or an agent. Automated checking is not proof of confidentiality.
- API facts take precedence over supplemental text. Known contradictory claims are held for owner resolution; extra material explains facts and context. Approved information can be disclosed publicly even though its original file has no public download.
- The index lives in the private `retrieval` schema (pgvector, 1024 dimensions): sources with their content hash and version, passages with their embedding and full text, and the provider usage of each call. `packages/db` owns the SQL; `packages/memory` owns chunking, change detection, the relevance floor and the spend ceiling behind ports; `packages/services` composes them with the Voyage adapter (`readRetrievalOptions`). Indexing embeds only sources whose hash changed, so a second run over unchanged content costs nothing.
- Search is the private `POST /v1/retrieval/search`: a `readOnly` route that is authenticated but neither audited nor announced, with the query in the body, never in a URL or log. Below the relevance floor it returns `no_evidence`; a provider that is not configured, fails or times out is `provider_unavailable` (a rate-limited call is first retried a bounded number of times, `RETRIEVAL_PROVIDER_RETRIES`; the message names the HTTP status class, never the answer's body) and a month at its spend ceiling (`RETRIEVAL_MONTHLY_CEILING_USD`) is `budget_exhausted`, both 503 and never "no evidence". Reindexing and the evals' candidate pools run through the API's `knowledge` command, not a route. Settings: `RETRIEVAL_*` in `.env.example`, the key `VOYAGE_API_KEY` from the owner's secrets (`apps/api/AGENTS.md`, Configuration).
- Public results contain current approved passages, safe source labels and canonical site links when a page exists. Extra sources without a public page have a label/identifier, never a fabricated URL or private storage link.
- Incremental indexing follows content writes with recoverable pending state; provider failure does not undo a committed content write. Delete/withdraw superseded evidence promptly. A committed write queues work in `retrieval.work_items` and, in the same transaction, drops a deleted record's sources and marks a changed record's sources stale, so search never shows superseded text. An in-process queue in the API works through the queue in bounded batches, retries a failed provider a bounded number of times, stops at the spend ceiling without losing work, and resumes after a restart. Vectors are cached by text hash, model and version, so a retry or a rebuild after a model change embeds each text at most once and counts its usage once. Rebuild from current API data and retained approved originals while preserving approval state.
- After the phase-10 launch, phase 11 adds a source-backed graph using a small initial schema; phase 12 develops the ontology and evaluates NVIDIA Auto Ontology separately. Neither introduces direct Python database access or an enterprise platform by default. Phase 13 handles external MCP UI independently.

## Chat

- The browser never talks to the assistant. It talks to the website, which talks to the API.
- **The API owns the conversation:** the anonymous visitor cookie, ownership of one conversation per browser identity, rate limits, bot detection, the daily budget, and storage of every conversation.
- Direct `/ask` navigation restores that identity's conversation; no session picker or cross-device identification. Losing the cookie loses the anonymous identity, and a URL alone grants no access.
- **The assistant produces the answer:** an input guard (a small model), generation by a model with read tools and search, deterministic output checks. It is stateless; the API sends it the conversation so far.
- Model-visible tools are allowlisted public reads; provider/service credentials stay outside model context. No content-write key or write tool enters the pipeline. Injection can still corrupt answers; direct/indirect attack evals measure the residual risk.
- `packages/llm-agent` runs exactly three LangGraph stages: Security Gateway (rules + cheap classifier, allow/block/uncertain), Main Agent (bounded tools loop) and Output Guard (deterministic schema/evidence/link checks, no LLM). Generation is buffered until validation; progress events may precede approved content.
- LangChain provides configured OpenAI/Anthropic model integrations. API reservations enforce global cost ceilings; runtime limits bound each call/attempt. Cancellation, deadlines, concurrency and idempotency are explicit contracts, described in the phase-7 PRD.
- Answers carry typed blocks (contact, experience, service, exploration, roadmap, sources) that the website renders with its own components. Public MCP initially returns structured data/text; external interactive UI is phase 13.
- Phase 3 defines the validated application event/block contract in `packages/contracts` and a browser-local mock adapter. Components depend on that contract rather than transport framing. Phase 7 implements the real API transport/adapter, including idempotent request identifiers and recoverable failures. The mock introduces no live conversation API or server-side storage.
- On the website (`apps/web`, module `chat`) the seam is `ChatAdapter`: `send(submission, signal)` yields an attempt's raw events in order and stops when the signal aborts. The conversation validates every event against the contract and enforces its order, so a broken transport fails one answer, never the page; a stream that ends without a terminal event is interrupted. One answer is open at a time, a question handed from the hero is taken exactly once, and the conversation's address (`/ask?c=<random id>`) carries no question and authorises nothing. In phase 3 conversations live in the tab (`sessionStorage`); phase 7 swaps in the API's adapter and server-side storage, retains the card renderers and extends the composer/lifecycle for the controls specified in its PRD.
- **Recovery on the website.** Only the active attempt changes the conversation: events of a cancelled, replaced or timed-out attempt, duplicates (an event identifier not above the last) and events of another request are ignored, while an event of another message breaks the contract and fails the answer as a retryable `invalid_stream`. An answer without an event for 20 s fails as a retryable `timeout` and its transport is stopped. A failure is never retried automatically; the visitor may retry the latest answer when it was interrupted or its error is `retryable`, which sends the same conversation, request identifier and question again and replaces the failed answer in place. "New chat", leaving and coming back, rerenders and repeated presses never send twice. In phase 3 this is enforced in the browser only. **Phase 7 handoff:** resolve the anonymous identity's own conversation from API storage; a foreign/unknown URL preserves and resolves that caller's history, never the other visitor's. An ordinary repeated request identifier recovers the existing operation; only a separate explicit retry action may create a new attempt for a failed question, without storing the question twice. Browser disconnection stops observation rather than generation; explicit Stop cancels. Add bounded progress/keepalive and update the quiet-time contract so waiting for Output Guard is not mistaken for a failed generation. The phase 3 test seam `window.__sebelaMockChatScenarios` (the browser tests' queue of mock failures, read by `apps/web` `hooks/use-conversation.ts`) ships with the mock and must be removed with it.
- Langfuse receives redacted traces; scoring runs off the visitor path under its own budget. Promptfoo covers component/end-to-end evals, pytest deterministic failures, and human review covers ambiguous and sampled automatically passed answers. Telemetry failure never bypasses budgets or blocks valid answers.
- **Phase-7 planned extension:** generation survives browser disconnect and persists through the API; explicit Stop cancels, and process-loss recovery does not automatically repeat paid work. One active chat/compact operation belongs to the anonymous identity across tabs. The web adds server-authoritative personal usage and manual `/compact`; the latter preserves visible history and treats its bounded summary as untrusted context. The three-stage answer graph remains unchanged.
- **Phase-7 telemetry boundary:** Langfuse Cloud EU receives metadata and locally pseudonymized content, with actual 30-day exported-content deletion. Public profile facts remain readable, forbidden identifying fields/credentials never enter export, and best-effort PII detection does not promise anonymity. The replaceable CPU/ONNX candidate is accepted only after bilingual and shared-CAX21/ARM64 measurements; unsafe/overloaded export degrades to metadata. It is separate from external LLM input handling and from the visitor response path. Details and proposed defaults are in the phase-7 PRD.

## Background work

There is no worker by default. One is added only for a concrete job. Reindexing after content writes runs in the API process over a durable queue in Postgres, which needs no separate worker.

## Deployment

Docker throughout: a Dockerfile per app and one Compose stack, the same composition locally and in production. The target is the owner's VPS. Production specifics are in `docs/release-workflow.md`.

Locally the API already runs this way (profile `api` of `compose.yaml`, `apps/api/AGENTS.md`, "Container stack"): a one-off migration service runs before the API, which never migrates itself, and the seed and API keys are explicit commands, so a start or restart never changes content. The image carries code and the fictional demo seed only; the owner's content stays outside the repository and the image and is loaded at run time. No production Compose file, reverse proxy, TLS or deployment exists yet.

The Compose stack separates three networks: `database` joins Postgres, the migration and the API; `content` joins the API and the website; `admin` joins the API and MCP Admin (profile `mcp-admin`). Only the API is on all three, so neither the website nor MCP Admin can reach Postgres, the website has no route to MCP Admin, and MCP Admin receives no database, migration or storage setting. MCP Admin is published on a loopback address only and is reached from elsewhere through an SSH tunnel; the public edge (phase 10) must expose neither it nor the API's private routes.
