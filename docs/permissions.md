# Permissions

What coding agents may do in this repository, and why. The configuration lives in `.claude/settings.json`; this document is the intent it implements.

## Principle

Free hands inside a worktree, hard limits at the boundaries. An agent should finish an issue without asking for confirmation at every step, and should be technically unable to do the few things that cause real damage.

## Allowed without asking

| Action                                                                                                                                                 | Why                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| Package manager and task runner commands, tests, lint, typecheck, build                                                                                | Normal development                                                                   |
| Reading git state; committing on the agent's own branch                                                                                                | Normal development                                                                   |
| Compose commands for the local Postgres                                                                                                                | Needed to run and test                                                               |
| Worktree setup and cleanup scripts                                                                                                                     | Part of the flow                                                                     |
| Reading, creating and editing `.env.local` inside the session's own worktree; editing `.env.example` and `.env.secrets.example` with placeholders only | Agents need to configure their development environment                               |
| Reading issues and pull requests                                                                                                                       | Context                                                                              |
| Creating a pull request                                                                                                                                | The orchestrator does this on its own                                                |
| Squash-merging a reviewed issue pull request into the phase branch (orchestrator only)                                                                 | Lets a phase run unattended; the owner still reviews the whole phase before `master` |

## Needs the owner's confirmation

| Action                                                    | Why                                     |
| --------------------------------------------------------- | --------------------------------------- |
| Creating issues                                           | Outward-facing and hard to undo cleanly |
| Anything the loop cannot decide alone                     | It stops and reports instead            |
| Changing dependencies in a way the issue did not call for | Supply-chain and maintenance cost       |

## Denied

| Action                                                                                                                                                                                                    | Why                                                                                                 |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Reading or editing environment files except `.env.example`, `.env.secrets.example` and `.env.local` inside the session's own worktree; above all `.env.secrets`                                           | Other worktrees, the main checkout, the owner's secrets and production configuration remain private |
| Reading `.context/` (subagents)                                                                                                                                                                           | Raw private notes; the repository is public                                                         |
| Merging into `master`, pushing to `master`, force-pushing a shared branch                                                                                                                                 | The owner is the only gate to `master`                                                              |
| Starting, stopping or rebuilding the shared Compose stack (project `sebela`: `pnpm stack:up`/`stack:down`/`stack:seed`, `docker compose up`/`down`/`build`… without an own `-p`) (subagents and the loop) | Every worktree and loop shares its Postgres; images built locally fill the system disk              |
| Editing outside the agent's own worktree                                                                                                                                                                  | Parallel agents must not collide                                                                    |
| Editing app or package code in the main checkout                                                                                                                                                          | All code goes through a worktree and a pull request                                                 |

## Hooks

The local environment exception requires a session running inside a Git-confirmed worktree of this repository. It covers `.env.local` at the worktree root and in its app folders. Both the written path and the resolved path must remain in that worktree; symbolic links do not grant access elsewhere. Exact file paths work with file tools and simple shell commands. Shell expressions with expansions, wildcards or directory changes are refused when they name environment files; broad searches for environment files are refused too.

### Environment files

Two documented examples split what agents may see from what they may not:

- **Settings** — `.env.example`: ports, addresses, limits, storage folders and the local passwords of the development database. The main checkout copies it to `.env` (Compose reads it); each worktree gets its own generated `.env.local`, which its agents read and change. The main checkout's `.env` stays private because it holds the Postgres superuser password.
- **The owner's secrets** — `.env.secrets.example`: keys for paid outside services, today `ANTHROPIC_API_KEY` for the model evals, and the owner's admin API key `SEBELA_ADMIN_API_KEY` (the key the owner's MCP client sends), which only the API's `media upload` command reads (`apps/api/AGENTS.md`, Commands). The owner copies it to `.env.secrets` in the main checkout only (mode `600`); Git ignores it, no worktree ever gets a copy, and agents may not read, edit or name it: the guard refuses it in every tool and shell command, and `.claude/settings.json` denies `Read`, `Edit` and `Write` of it. A command that needs a secret runs through `node harness/with-secrets.mjs -- <command>`, which finds the main checkout from the worktree, reads its `.env.secrets` and gives the values to that one process; a variable already set wins, so CI passes its repository secret the same way. Package scripts wrap their paid commands with it (for example an `eval` script), so agents run them without seeing the key.

This keeps a key out of the files, transcripts, logs and pull requests agents produce. It does not hide it from a process an agent deliberately writes to print its environment, so the key is a separate development key with a low spend limit, and agents never print, log or pass a secret on. Never export a secret in the shell that runs Claude Code or the phase loop: an `ANTHROPIC_API_KEY` there would bill the agent sessions to it instead of the owner's subscription.

Development environment files stay ignored by Git. Production credentials are kept outside development worktrees. A worktree's `.env.local` holds the credentials of that worktree's own database role, generated by the worktree script; they open only that worktree's databases. The Postgres superuser password stays in the main checkout's `.env` and never reaches a worktree. Never copy environment values into commits, documentation, pull requests or public logs. The guard checks paths, not whether a value is a production credential.

### Formatting after an edit

The file is formatted by the Prettier of the checkout it belongs to (`node_modules/.bin/prettier`, started in that checkout's root), so that checkout's configuration, `.prettierignore` and `.gitignore` apply and a worktree never uses another checkout's tools. Prettier skips file types it does not support. Files outside this repository, environment files, anything inside `.git` and symbolic links that lead out of their checkout are left alone. When Prettier cannot format the file, for example because of a syntax error, or the checkout has no installed tools, the reason goes back to the agent. The hook writes the file directly; that is no tool call, so formatting cannot trigger the hook again.

### Handoff checks

A developer agent (`backend-developer`, `frontend-developer`, `ai-developer`) hands off only work whose lint and typecheck pass. The same check runs at two points:

- **Handing back.** Before its `SubagentHandback` call, which delivers the report to the caller, the checks run. A failure refuses the call with the failing output, so the report does not reach the orchestrator until the checks pass.
- **Stopping.** When the developer stops, the checks run again. A failure keeps it working with the failing output. If it stops a second time while they still fail (`stop_hook_active`), the hook does not block again — that would loop — but reports the failure to the session as a system message.

**Which worktree.** The hook reads the developer's own transcript and takes the worktrees under `.worktrees/` that its edits, writes and shell commands name, plus the directory the session runs in. Paths it only read, prompts and tool output do not count. Each candidate must be a Git worktree of this repository; the main checkout holds no developer work and is not checked. A developer that acted in no worktree has nothing to check. A transcript that cannot be read refuses the handoff.

**Which parts.** In each worktree the hook compares with the nearest branch the issue branch can have been cut from (`master`, `main` or `phase/*`, local or on `origin`): committed, staged, unstaged and untracked files since the merge base. A file in `apps/<name>` or `packages/<name>` selects that package; Turborepo adds its dependents. A change to `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `turbo.json` or `.nvmrc`, or a branch without such a base, selects every package. The root tasks `lint:root` and `check:config` always run; Turborepo replays cached results for anything unchanged.

**The command.** `turbo run lint typecheck lint:root check:config --continue --output-logs=errors-only` with `--filter=//` and `--filter=<package>...` for each selected package, run with the worktree's own Turborepo, so every failure is reported in one pass. Tests are not part of it; CI runs them. A missing tool, a timeout or a check that cannot start counts as a failure. Other agents and the main session are not checked.

**What the guard is for.** It stops an agent's mistakes and improvised workarounds, not someone set on defeating it: a shell command can always be written in ways no parser foresees. Where it cannot tell what a command does, it refuses rather than guesses. The deny rules, the auto-mode classifier, CI and branch protection stand behind it, so no single rule in it has to be complete.

Rules on shell commands match the command as written, so they are a safety net, not a sandbox: an agent determined to get round them could. Branch protection on GitHub is the layer that cannot be talked round.

## Unattended runs

The phase loop runs Claude Code without a person present. In that mode nothing can be confirmed: an action that is not allowed here is simply refused and the run continues or stops. The allow and deny lists above are therefore the whole safety model of the loop — keep them tight.

## Notes

- Project settings add to the owner's global Claude Code settings; they must not replace the global hooks. A new project hook is a new entry next to the existing ones, never a replacement of the guard, the worktree hooks or the merge reminder.
- Access to data at runtime (public and private API routes, API keys) is a different subject. See `docs/architecture.md` and `docs/domain-context.md`.
