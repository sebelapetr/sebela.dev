# @sebela/web

The public website: a Next.js app (App Router) that renders its content from the API's public routes. Read the root `AGENTS.md` first; this file covers only what is specific to this app. Visual language: `docs/design.md` (binding).

## What it is

- The website reaches data only through the API over HTTP, with the generated `@sebela/api-client`, from server code. It never imports `@sebela/db` or `@sebela/services` (the import-boundaries lint rule enforces this) and never holds an API key: it reads public routes only.
- Every fact about the person — name, headline, bio, photo, email address, links — comes from the API. Components carry only UI copy: labels, headings and the site's own addresses (`src/modules/_shared/`). No experience years, employer names or contact values are written into the app.
- Pages render on each request (`connection()`), so the build needs no API and no settings. Caching (#56, #57), image optimisation (#55), the theme toggle and navigation (#50) and the chat (#51) belong to later issues.
- Tokens, fonts and shared components come from `@sebela/ui` through its declared exports (`packages/ui/AGENTS.md`).

## Commands

| Task                                                | Command                                       |
| --------------------------------------------------- | --------------------------------------------- |
| Development server on this checkout's address       | `pnpm --filter @sebela/web dev`               |
| Build (no API or settings needed)                   | `pnpm --filter @sebela/web build`             |
| Serve the build                                     | `pnpm --filter @sebela/web start`             |
| Unit tests (Vitest)                                 | `pnpm --filter @sebela/web test`              |
| Browser tests against a real API (build first)      | `pnpm --filter @sebela/web test:e2e`          |
| Browser tests with every build they need (as in CI) | `pnpm test:e2e` (from the repository root)    |
| Lint, typecheck (`next typegen`, then `tsc`)        | `pnpm --filter @sebela/web lint`, `typecheck` |

`dev`, `start` and `test:e2e` read the process environment, then `.env.local`, `.env` and `.env.example` of the checkout (the earlier source wins). `dev` and `start` go through `scripts/next.mjs`, which passes `WEB_HOST` and `WEB_PORT` to Next and refuses to start without them. `dev` first builds the workspace packages the app depends on. For a browser read in development, run the API of the same checkout (`pnpm --filter @sebela/api dev`) and then `dev`.

## Configuration

| Variable           | Meaning                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WEB_HOST`         | Interface the website listens on (`dev`, `start`).                                                                                                                                                                                                                                                                                                                                                       |
| `WEB_PORT`         | Port the website listens on; the port scheme of `docs/repository-structure.md`.                                                                                                                                                                                                                                                                                                                          |
| `WEB_API_BASE_URL` | Base address of the API whose public routes the website reads: its origin, or an origin with a path prefix in front of `/v1`. Validated once per process by `readWebConfig` on the first content request: an `http` or `https` address without credentials, query or fragment; the error names the variable, never its value. Worktree setup writes the worktree's own API origin into its `.env.local`. |

The build reads none of them. A missing or invalid `WEB_API_BASE_URL` fails the first request that needs content, not the build. A worktree created before the harness wrote `WEB_API_BASE_URL` (commit `e2db9b4`) has no value for it: add `WEB_API_BASE_URL=http://<its API_HOST>:<its API_PORT>` to its `.env.local`, or recreate the worktree.

## Content states

`getHomepage()` reads `GET /v1/person`, when the person has a photo `GET /v1/media/{id}`, and `GET /v1/projects`, uncached (`no-store`) and within 5 seconds each, once per request however many components ask.

- **Ready.** The homepage renders the hero (name, headline, short bio as inline Markdown, photo, the reserved place of the chat entry (#51), the calls to action "Work with me" to `/services` for clients and "View my experience" to `/experience` for employers), Selected work (the projects selected for the homepage as numbered rows, each linking to its exact case study or project on `/experience`; left out when none is selected), the contact block (`#contact`, the email address and the person's web links) and the footer (repository and CV).
- **Missing.** The API answers 404: no profile is published, and the page answers 404 (`not-found.tsx`).
- **Unavailable.** The API fails, is unreachable or too slow: `error.tsx` says the content is unavailable and offers "Try again" (HTTP 500). The website never shows an empty profile in its place.
- A photo that cannot be shown (not an image, no address, no dimensions, a failed read) leaves the profile without one: the portrait shows the initials instead. Links that are not `http` or `https` are left out; the short bio renders only paragraphs, emphasis, code and links, never raw HTML.

`/experience`: `getExperience()` reads `GET /v1/person`, `GET /v1/experiences`, `GET /v1/explorations`, `GET /v1/technologies` and `GET /v1/education` the same way (uncached, 5 seconds each, once per request, at the same time), then each distinct organization logo and testimonial author photo once through `GET /v1/media/{id}`; a logo or photo that is missing, not an image, without a web address or dimensions, or whose read fails is left out without failing the page.

- **Ready.** The header (name, the headline as the summary, whole years since `careerStartedOn` when set, "Read the CV" to `/cv`) and the career timeline in the API's order: every experience its own row with the anchor `experience-<slug>`, the organization's logo when it has a usable one, period, kind label (`main_job` reads "Full-time job"), title and organization; current ones open, older ones closed (`docs/design.md`, Timeline). Each experience lists its own projects (anchor `project-<slug>`) with their evidence; a project's case study (anchor `case-study-<project slug>`) sits behind a disclosure. A link to any anchor opens the disclosures around it, scrolls to it and focuses it on load, hash change and back/forward; an unknown anchor opens nothing (`docs/design.md`, Timeline, Anchors). Testimonials appear only beside the experience they belong to, each with its author's photo beside the quote when it has a usable one and nothing in its place otherwise. Below the timeline, in this order: Independent R&D (anchor `independent-rd`; each exploration with the anchor `exploration-<slug>`, its stored status as visible text with its meaning, its sentence and concepts), Technologies (groups with the anchors `technology-group-core`, `technology-group-ai-engineering-focus` and `technology-group-secondary`; core with the website's static logos, the AI engineering focus as text, the secondary technologies behind a disclosure that a link opens) and Education (compact rows). Each is left out when it has nothing to show (`docs/design.md`, Experience sections).
- **Empty.** A published profile without experiences shows the header and "No experience is published yet."; the other sections still appear when they have content, and none appears empty or with a placeholder.
- **Missing** and **unavailable** behave as on the homepage (404, `error.tsx`); a failed read of experiences, explorations, technologies or education makes the page unavailable, never a page with a section silently missing.

The destination pages `/services` and `/cv` arrive with later slices; their links are already correct.

## Tests

- **Unit** (`pnpm --filter @sebela/web test`): the configuration and the content mapping through the real generated client over a fake `fetch` — ready, missing, unavailable (server error, rate limit, a proxy's 502, no connection, timeout), only public routes without credentials or cache, the photo cases, the organization logo and testimonial author photo cases (present, absent, unusable, failed read) and the contact values; the period format (ordinals, `present`, same-day, no time-zone shift), the timeline mapping (API order, kinds of concurrent experiences kept apart, current open, testimonials only beside their own experience with their own author photo, empty data) and career years; the exploration statuses, the technology grouping (order, empty groups, known, unknown and missing logo keys) and the education rows. Written before the implementation.
- **End-to-end tests** (`test:e2e`, Playwright, Chromium): the built website against the API's end-to-end server (`apps/api`, `src/cli/e2e-server.ts`), a real API on a temporary database of its own, seeded from a small fictional fixture and dropped afterwards; the checkout's database and the demo seed are never touched. They check the content and its links, the contact anchor, keyboard order and visible focus (the button's ring, a text link's outline), the reserved chat place between the bio and the calls to action at every width, transitions ending at once under reduced motion, axe violations, touch targets of at least 44 px and no horizontal scroll at 360, 768 and 1280 px in light and dark mode, the initials fallback without a photo or email, and the unavailable state with a working retry. `e2e/experience.spec.ts` checks the timeline on the `with-experience` fixture: row order, anchors, kind labels, the logos (their alt text, and titles aligned with and without a logo), the expand policy, keyboard disclosure, testimonials beside their experience, the author photo beside its quote (alt text, loaded, nothing in its place without one, quotes aligned either way), the CV link and the empty state; the order of timeline, independent R&D, technologies and education, every exploration status as text and none in the timeline, core logos only where the website has one, the secondary technologies by keyboard and closed until found, the education rows, deep links to an exploration and to the secondary group (open, in view) and an unknown anchor, and no empty section without content. `e2e/selected-work.spec.ts` checks the homepage's Selected work (order, numbers, exact links, no role without a case study, left out without selected projects) and the deep links: projects inside their experience, the case-study disclosure by keyboard, a case study and a project inside a closed experience on a direct load (open, at its place below the header offset, focused, kept after hydration), client navigation from a teaser, hash changes, back and forward, an unknown or removed anchor, reduced motion, with axe, touch targets and no horizontal scroll at every width and mode. Screenshots of each width and mode go to `test-results/`.
- The main stack listens on this checkout's own `API_PORT` and `WEB_PORT`, so stop the checkout's dev servers first; the other stacks take free ports from the system. Run `pnpm --filter @sebela/web build` before `test:e2e`, or use the root `pnpm test:e2e`, which builds the website and the API first. They need the running Postgres and the checkout's `DATABASE_USER`/`DATABASE_PASSWORD`, and Chromium (`pnpm --filter @sebela/web exec playwright install chromium`).
