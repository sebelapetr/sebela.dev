# @sebela/web

The public website: a Next.js app (App Router) that renders its content from the API's public routes. Read the root `AGENTS.md` first; this file covers only what is specific to this app. Visual language: `docs/design.md` (binding).

## What it is

- The website reaches data only through the API over HTTP, with the generated `@sebela/api-client`, from server code. Two reads leave the API's routes: the current CV PDF's stored file for `/cv/pdf`, which the server fetches from the public address the API's media gives (the CDN in production), only over https or from the API's own origin (Modules, `profile`); and the stored image files directly below `WEB_MEDIA_BASE_URL`, which the server serves from the site's own `/media/<file>` for the image optimizer (Media and previews). Both are read through `WEB_MEDIA_READ_BASE_URL` when it is set (the website container in the Compose network). It never imports `@sebela/db` or `@sebela/services` (the import-boundaries lint rule enforces this) and never holds an API key: it reads public routes only.
- Every fact about the person — name, headline, bio, photo, email address, links — comes from the API. Components carry only UI copy: labels, headings and the site's own addresses (`src/modules/_shared/`). There are two exceptions. The first is the homepage's What I do (`src/modules/homepage/components/what-i-do.tsx`): three sentences of the site's own copy naming kinds of work, with no claims, because the API has no field for it. The second is the chat's prepared answers (`src/modules/chat/data/prepared-answers.ts`): fictional, generic mock copy for phase 3 that uses only the name from the API and states no facts about the person; their cards and sources are built only from the public profile's records the API returned, and the API replaces them in phase 7. No experience years, employer names or contact values are written into the app.
- Pages render on each request (`connection()`), so the build needs no API and no settings. Their API reads go through a process-local content cache that the API's signed invalidation notifications clear (Caching and invalidation); its fallback revalidation interval, `WEB_CONTENT_REVALIDATE_SECONDS` (60 seconds by default), refreshes content when a notification never arrives. Uploaded images go through Next's image optimizer, restricted to the media folder of `WEB_MEDIA_BASE_URL` (Media and previews). The chat (phase 3) answers from prepared fictional answers streamed in the browser through the shared chat contract; phase 7 connects it to the API (Modules, `chat`).
- Tokens, fonts and shared components come from `@sebela/ui` through its declared exports (`packages/ui/AGENTS.md`).

One created before the harness wrote `WEB_SITE_ORIGIN` (issue #54) falls back to the placeholder of `.env.example` (port 3000): add `WEB_SITE_ORIGIN=http://<its WEB_HOST>:<its WEB_PORT>` to its `.env.local`, or recreate the worktree.

## Container

`apps/web/Dockerfile` builds the website image from the repository root (the allowlist of `.dockerignore`: workspace manifests, `apps/`, `packages/`; never an environment file, `.context/`, test results or build output). The build needs no API, no setting and no secret: the build stage sets `WEB_BUILD_STANDALONE=1`, which switches `next.config.ts` to Next's self-contained output (`output: "standalone"`), and the runtime stage copies only the traced server and the static assets and runs as `node`. A build on the host keeps the normal output that `next start` serves. The container listens on `WEB_HOST` and `WEB_PORT` and refuses to start without them, as `scripts/next.mjs` does.

The `web` service of `compose.yaml` (profile `web`) starts after the API is healthy and reads every setting from the environment, as the API service does:

| Origin                                         | Host (`dev`, `start`, `test:e2e`)                       | Container (`compose.yaml`)                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Where the server reads the API                 | `WEB_API_BASE_URL`, the checkout's API origin           | `http://api:8080`, the API service inside the Compose network                                                                   |
| Where the website listens                      | `WEB_HOST`, `WEB_PORT`                                  | every interface on 8080 in the container, published on the host's `WEB_HOST` and `WEB_PORT` only                                |
| Canonical public origin                        | `WEB_SITE_ORIGIN`                                       | `WEB_SITE_ORIGIN`, the published address                                                                                        |
| Public media base (what the API names)         | `WEB_MEDIA_BASE_URL`                                    | `WEB_MEDIA_BASE_URL`, the API's published file route                                                                            |
| Where the server reads stored files            | the media base itself (`WEB_MEDIA_READ_BASE_URL` empty) | `WEB_MEDIA_READ_BASE_URL`, by default the API's file route inside the network with `STORAGE_ENVIRONMENT` and `STORAGE_WORKTREE` |
| Where the API sends invalidation notifications | `API_WEB_INVALIDATION_URL`, the checkout's website      | `http://web:8080/internal/invalidation` when `API_WEB_INVALIDATION_SECRET` is set, nothing otherwise                            |

Browsers see only the published website: pages name images by `/media/<file>`, never the internal API address, and the signing secret stays on the two servers (`pnpm test:web-stack` checks the pages and the logs for both). Health: the container is healthy once `/robots.txt` answers, a route that validates the configuration but reads no content, so a website whose API is down still runs and shows its unavailable pages; content readiness is the API's own health.

Commands (root, Docker, settings from `.env` or the environment): `pnpm stack:up` builds and starts Postgres, migration, API and website and waits until they are healthy (it refuses without `API_HOST`, `API_PORT`, `WEB_HOST` and `WEB_PORT`); `pnpm stack:seed` loads the demo seed; `pnpm stack:logs`; `pnpm stack:down` stops and removes the website, API and migration containers and keeps the shared Postgres and the media volume. `pnpm test:web-stack` (`scripts/checks/web-stack.e2e.mjs`, the `web-stack` CI job) starts two disposable complete Compose projects side by side, each with its own ports, database volume, media volume, storage folder, API key and signing secret, checks real pages, the CV PDF and stored images through the website, an authenticated edit the website shows, and that neither stack's key, files or signed invalidations reach the other, then runs `playwright.complete-stack.config.ts` against one of them (the hero's question to the mock Ask page at 360, 768 and 1280 px in light and dark mode, screenshots in `apps/web/test-results/complete-stack/`) and removes both projects with their volumes and images. Worktrees keep running the API and the website on the host (`dev`, `start`); the worktree harness is unchanged.

## Content states

`getHomepage()` reads `GET /v1/person`, `GET /v1/experiences` (with their projects), `GET /v1/technologies`, `GET /v1/current-focus`, `GET /v1/explorations` and `GET /v1/services` at the same time, then when the person has them the photo and the CV PDF through `GET /v1/media/{id}`, through the content cache (Caching and invalidation) and within 5 seconds each, once per request however many components ask. A failed read of any list makes the page unavailable, never a homepage with a section silently missing.

- **Ready.** The homepage renders the hero (name, headline, short bio as inline Markdown, photo, the chat entry (one input line with its submit, then the suggested questions: two below `sm`, three from it), the calls to action "Work with me" to `/services` for clients and "View my experience" to `/experience` for employers), What I do (three columns of the site's own copy: kinds of work, no claims), Selected work (the projects selected for the homepage as numbered rows, each linking to its exact case study or project on `/experience`; left out when none is selected), the Experience snapshot (whole years since `careerStartedOn` when set, the experiences without an end date as the current roles, the primary technologies as a core and an AI engineering focus line, "Full experience" and the CV actions), Now (Working on: each current focus with its topics and a link to its project on `/experience` or its own http(s) link; Exploring: the ongoing explorations — no end date — with their stored status, each linking to it on `/experience`; then "Independent R&D" to `/experience#independent-rd` when any exploration exists and "AI Roadmap" to the placeholder `/ai-roadmap`; each column left out when empty, the section when both are), Services (each service's name linking to `/services#service-<slug>` and its summary, then "All services"; left out without services), the contact block (`#contact`, the email address and the person's web links, or "No contact details are published yet." without either, so the header's Contact link never lands on a bare heading) and the footer (repository and CV). Until phase 4, Exploring comes from the profile's explorations; phase 4 replaces its source with the AI Roadmap. The homepage's links to dynamic pages are not prefetched (each prefetch would read the API).
- **Missing.** The API answers 404: no profile is published, and the page answers 404 (`not-found.tsx`).
- **Unavailable.** The API fails, is unreachable or too slow: `error.tsx` says the content is unavailable and offers "Try again" (HTTP 500). The website never shows an empty profile in its place.
- A photo that cannot be shown (not an image, no address, no dimensions, a failed read) leaves the profile without one: the portrait shows the initials instead. Links that are not `http` or `https` are left out; the short bio renders only paragraphs, emphasis, code and links, never raw HTML.

Without a PDF (none attached, not a PDF, no address, or its media cannot be read) only "Read the CV" to `/cv` and no date. Every page renders the site header (`SiteHeader`, `docs/design.md`, Navigation): the skip link, the name (or "Home" where no profile is read), the navigation with the current entry marked, "Ask AI" and the theme toggle; below `md`, a full-screen menu dialog. The root layout's inline `themeScript` applies a stored theme choice before paint (`docs/design.md`, Themes).

`/ask` (dynamic, not indexed): the chat. It reads the public profile the prepared answers rest on (`getAsk`: `GET /v1/person`, `GET /v1/experiences`, `GET /v1/services`, `GET /v1/explorations` and `GET /v1/technologies` at the same time) with the same missing and unavailable states as the other pages, reduces it on the server to plain evidence for the browser, and renders the assistant's introduction (an AI assistant over the public profile, never the person), the four suggested questions of an empty chat, the conversation, "New chat" and the composer. A conversation's address is `/ask?c=<random id>`; the question never enters the address. Conversations live in the tab only (`sessionStorage`, or memory where storage is refused); an unknown or invalid address opens an empty chat. An answer shows its text, then its block cards (experience, service, exploration with its stored status, contact; the roadmap card is rendered from a contract fixture only, with no records until phase 4), its sources (each the exact record on `/experience` or `/services`, built with the same anchor helper as the page, a case study opened inside its closed experience) and at most two related pages. Every block and source is shown only when the shared contract accepts it whole; an answer without evidence cites nothing, and the insufficient-evidence answer offers the contact card.

`/ai-roadmap` (static, not indexed): the AI Roadmap's placeholder until phase 4 — says it is not published yet, points to the independent R&D, and leads back to the homepage and to `/experience`. No roadmap data is read.

`/cv/pdf` (route handler, dynamic): `getCvPdfFile()` reads `GET /v1/cv`, then the named PDF's media and its file from the media's address (never cached, 15 seconds in all). The stored file is delivered as it is — `application/pdf`, `attachment; filename="<name-slug>-cv.pdf"`, `no-store` — only when it arrives whole, is served as a PDF and starts with `%PDF-`. Without a PDF the request is redirected (303) to `/cv`; when the file cannot be delivered, to `/cv/pdf/unavailable` (static, not indexed), which says nothing was downloaded and offers "Read the CV" and "Try the download again". The download links carry no `download` attribute, so a redirect opens as a page and is never saved as a file. Nothing generates a PDF.

## Media and previews

Uploaded images (the portrait, organization logos, testimonial author photos) are shown through `MediaImage` (`_shared`), Next's `<Image>` with the media's own alt text and dimensions and a `sizes` for the width it is rendered at, so the browser picks a source near its width: the portrait 160, 256 and 320 px wide at 360, 768 and 1280 px (320 on a 360 px phone with two device pixels per CSS pixel), a logo from its aspect ratio (at most 128 px below 640 px, 160 from it). The originals stay in the configured storage; the website's own optimizer (`/_next/image`) resizes them to WebP at one quality (75) and the widths of `src/media-source.ts`, never larger than the original. No CDN optimizer service is used.

- **Allowed sources.** A page names a stored image by the site's own path `/media/<file>.<png|jpg|webp>` (`mediaPath`), and the optimizer reads only that path (`imageSettings`: `localPatterns` for one file name, no query; no `remotePatterns`, no redirect followed, no local IP), so it never fetches another host and its settings depend on no environment. The route (`src/app/media/[file]/route.ts`, `getMediaFile`, `data/read-media-file.ts`) serves the file of that name directly below the read address (`WEB_MEDIA_READ_BASE_URL`, or `WEB_MEDIA_BASE_URL` when it is unset), read uncached, without credentials or redirects, limited to 15 seconds and 50 MB, and answers it with the type its extension names (the storage must agree), `public, max-age=300` (a replaced image gets a new name), `nosniff` and a policy that loads nothing. Any other name (traversal, another file type) is a 404 read from nowhere; a file the storage does not have is a 404; any other failure an empty 502. The media base must be an `http` or `https` address with a plain host name or IPv4 address and plain folder names (`parseMediaBase`). The profile module drops a media address outside the base before rendering (`mediaFileName`), so no page names one; a browser never sees the media base's host or the read address.
- **Fallbacks.** A missing, unusable or unreadable image is left out (`data/image.ts`): the portrait shows the initials, a logo or author photo leaves nothing in its place. When the original is gone after the page was rendered, the optimizer fails and `MediaImage` gives way to the same fallback, never a broken image. Images carry no focus and no motion. Technology logos stay static website assets; a technology whose key the website has no logo for is shown by its name alone (Modules, `experience`).
- **Observed sizes** (the `with-photo` fixture's 480 × 600 PNG portrait, 1673 B): WebP 120–147 B at 160 px, 196–208 B at 256 px, 241–288 B at 320 px; 480 and 750 px give the same 396–580 B, since nothing is enlarged. A 240 × 64 logo is fetched at 96 and 128 px rather than 128 and 160. The preview PNGs are about 45–48 KB. `e2e/media.spec.ts` records the portrait's sizes in `test-results/` (`portrait-sizes.json`).
- **Open Graph images.** Every indexed page names `/og/<page>` (`home`, `experience`, `services`, `cv`) on `WEB_SITE_ORIGIN` as its `og:image` (1200 × 630, PNG, the title as alt text) and a `summary_large_image` Twitter card. The route renders a card with `next/og` in the dark theme's tokens (`@sebela/ui/lib/tokens`): the site's host, the page's name, the person's name (at most 60 characters) and headline (at most 120), from `GET /v1/person` through `getHomepage()`. While the profile is missing or cannot be read it answers 200 with the site's own card (its host only) and `no-store`; the profile's card is sent with `no-cache`. Any other segment answers 404 (`X-Robots-Tag: noindex`). It is rendered per request; the build contacts no API. No photograph is drawn on the card.

Cache dependencies, for the signed invalidation slice ("Refresh rendered profile pages through signed API invalidation"):

| Cache                                    | Keyed by and kept                                                                                                                        | What makes it stale                                                                                                                                               |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Optimised images (`.next/cache/images/`) | the source address, width and quality; kept for the original's `Cache-Control` max-age or Next's `minimumCacheTTL`, whichever is longer  | nothing in normal use: a new upload gets a new key (a new UUID file name), so a changed photo or logo is a new address once the page that names it is re-rendered |
| Pages naming the images                  | rendered per request (`connection()`) from the content cache                                                                             | the media record a person, organization or testimonial author points at (`GET /v1/media/{id}`): a `media` notification, like every other, clears the whole cache  |
| `/og/<page>`                             | sent with `no-cache` (clients revalidate each use), the fallback with `no-store`; overrides `next/og`'s default one-year immutable cache | `GET /v1/person` (name, headline) through the content cache, cleared by every notification                                                                        |
| Shared previews in social networks       | their own crawlers' caches, outside the site                                                                                             | not refreshable by the site; the address stays the same                                                                                                           |

## Caching and invalidation

The `profile` module reads the API through a process-local content cache (`data/content-cache.ts`), passed to the generated client as its `fetch`: GET answers with status 200 are kept by address, at most 256 entries of at most 1 MiB each. An entry is fresh for the fallback revalidation interval (`WEB_CONTENT_REVALIDATE_SECONDS`, 60 seconds by default); after it the next request reads the API again, independent of notifications, so a dropped notification, a website without the receiver or another website instance (a notification clears only the instance it reaches) shows a write within one interval. A restarted website starts with an empty cache and reads current content at once. Nothing needs a rebuild.

Failed answers are never cached as content, and an outage never replaces good content:

- **Uncached failures pass through.** A read with no cached copy that fails (a network error, a timeout, any non-200 status) is returned unkept, so the page shows its unavailable or not-found state and "Try again" reads again.
- **Stale if unavailable.** When the API is unavailable while an expired copy exists — the read throws or times out, or answers 5xx, 408 or 429 — the expired copy is served instead, and a line `Content cache served a stale copy of <path>: <cause>` goes to standard error (the path and the status or error name only). The entry stays expired, so every request during the outage tries the API again and the first one after recovery shows current content. During a long outage the last good content is served for as long as it lasts; the log lines show it. While the API hangs rather than refusing, every request waits for each read's own timeout (5 seconds for the page reads) before the stale copy is served, and every stale read logs one line, so a page that reads several routes logs one line per route and request.
- **Definite answers win.** A 404 or other definite non-200 answer deletes the cached copy and is returned, so deleted content disappears. A fresh 200 answer too large to keep also deletes the older copy, so it never stands in for current content later. An invalidation clears every copy, so content a notification has replaced is never served stale, even during an outage.

The CV PDF's file read (`getCvPdfFile`) never goes through the cache. The cache lives on `globalThis`, so every route of the server process shares one; it is created on the first content request, and an invalidation before that has nothing to clear.

**Healthy notifications versus the fallback.** With the API and the receiver healthy a write shows within ten seconds (the notification's target, PRD "Cache invalidation guarantees"). The fallback interval is only the bound when notifications fail; it is not that target and is not meant to be lowered to meet it. Operator signals:

| Signal                                                                                    | Where                  | Meaning                                                                                                   |
| ----------------------------------------------------------------------------------------- | ---------------------- | --------------------------------------------------------------------------------------------------------- |
| `website invalidation <id> attempt <n> failed: <reason>`, then `gave up after 3 attempts` | API standard error     | a notification was not delivered; the website shows the write within one fallback interval                |
| `website invalidation <id> dropped: the queue is full`                                    | API standard error     | the same, under a burst of writes                                                                         |
| `error notifying <method> <path>: <error name>`                                           | API standard error     | the notifier itself failed; the write is still committed and answered as such                             |
| `Content cache served a stale copy of <path>: <cause>`                                    | website standard error | the API is unavailable and the website serves the last good content; repeated lines mean a lasting outage |
| pages answering 500 with "This page could not be loaded right now."                       | website                | the API is unavailable and the website has no copy of that content                                        |

The API sends a signed notification after each committed content write (`apps/api/AGENTS.md`, Website invalidation; contract in `packages/contracts/AGENTS.md`). `POST /internal/invalidation` (`modules/invalidation`) answers it:

- The body is read raw, bounded by `invalidationMaxBodyBytes` (4096): an announced or streamed longer body is refused with 413 at once, before parsing. The exact bytes and the `sebela-invalidation-timestamp` and `sebela-invalidation-signature` headers (absent ones as `null`) go to `verifyInvalidationNotification` with `WEB_INVALIDATION_SECRET`, which compares in constant time and refuses stale timestamps.
- Refusals invalidate nothing and are final for the sender: 401 for a missing, stale or wrong signature, 400 for a signed body that is no valid notification (unknown domain, a record that is no slug or identifier, extra fields such as addresses or cache keys), 413 for an oversized body. A missing or too short secret is a configuration error: 500, which the API retries. An accepted notification invalidates, then answers 204. Every answer is empty, `no-store` and `noindex`; log lines name the refusal only, never the secret, the body or the event.
- **Dependency map** (`modules/invalidation/data/dependencies.ts`). The website, never the caller, decides what a change invalidates: each content domain maps to cache scopes, typed over every domain of the contract so a new one does not compile until mapped. Every domain maps to the one scope `profile`, which clears the whole content cache. This is coarse on purpose and complete: every page, its metadata and structured data, `/sitemap.xml`, `/llms.txt` and `/og/<page>` are rendered from the profile reads (the table under Metadata and indexing), and a relation change or deletion also reaches the pages that showed the record before, without the website knowing them.
- **Ordering.** A notification means "refetch current data", so duplicates and out-of-order arrivals are harmless. A read that began before an invalidation is returned to its request but not kept, so a slow read of older data cannot outlive the invalidation. A lost notification leaves content stale for at most one fallback revalidation interval while the API is available.

## Metadata and indexing

The `seo` module builds every search and machine-readable output from the same public API reads as the pages, on `WEB_SITE_ORIGIN`. Nothing states a fact the profile does not hold: no owner fact is hard-coded, no achievement, skill list or date is derived, and the Open Graph image is a card of the name and headline (Media and previews).

- **Indexed pages** (`indexedPaths`): `/`, `/experience`, `/services` and `/cv`. Each has its title (`<name> — <headline>` on the homepage, `<Page> — <name>` otherwise), a description (its summary's first paragraph as plain text, at most 160 characters, else the headline), its canonical address, Open Graph basics (type, address, title, description, the name as the site's name, the preview image `/og/<page>` with its size and alt text) and a `summary_large_image` Twitter card with the same title, description and image.
- **Not indexed**: `/ask` and its conversations, `/ai-roadmap` (a placeholder; no roadmap detail route exists), `/cv/pdf/unavailable`, the missing state (404) and the unavailable state (`error.tsx`, HTTP 500, `<meta name="robots" content="noindex">`, no canonical and no structured data). `/cv/pdf` is a download, not a page, and is not listed. robots.txt disallows nothing, so crawlers can read each page's own `noindex`.
- **Structured data**: the homepage only, one `<script type="application/ld+json">` with a `WebSite`, a `ProfilePage` and a `Person` (name, headline as description, the homepage address, and the photo, email address and web links only when present). The JSON is escaped (`<`, `>`, `&`, U+2028, U+2029 as `\uXXXX`) so no profile text can close the script element.
- **`/sitemap.xml`**: the indexed pages on the origin, no `lastmod`. **`/llms.txt`**: the name, headline and short bio, then Pages (the CV PDF only when there is one), Experience, Services, Independent R&D and Contact with exact anchors on the origin, each section left out when empty; profile text is collapsed to one line and its brackets escaped, and only http(s) links are kept. Both answer 404 (`X-Robots-Tag: noindex`) without a published profile and 503 (`Retry-After: 60`, `no-store`, `noindex`) while the API cannot be read — never a successful empty document. **`/robots.txt`**: `Allow: /` and the sitemap's address; it reads no content and always answers 200.

What each output depends on, for the signed invalidation slice ("Refresh rendered profile pages through signed API invalidation") to refresh it completely. All are rendered per request from the content cache, which every accepted invalidation notification clears as a whole (Caching and invalidation), so each row is refreshed by any content change. A page's metadata comes from the page's own read (`getHomepage`, `getExperience`, `getServices`, `getCv`), so whatever makes that read missing or unavailable changes it as well; the table names the fields that appear in the output.
