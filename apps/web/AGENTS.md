# @sebela/web

The public website: a Next.js app (App Router) that renders its content from the API's public routes. Read the root `AGENTS.md` first; this file covers only what is specific to this app. Visual language: `docs/design.md` (binding).

## What it is

- The website reaches data only through the API over HTTP, with the generated `@sebela/api-client`, from server code. The one read outside the API's routes is the current CV PDF's stored file for `/cv/pdf`: the server fetches it from the public address the API's media gives (the CDN in production), only over https or from the API's own origin (Modules, `profile`). It never imports `@sebela/db` or `@sebela/services` (the import-boundaries lint rule enforces this) and never holds an API key: it reads public routes only.
- Every fact about the person — name, headline, bio, photo, email address, links — comes from the API. Components carry only UI copy: labels, headings and the site's own addresses (`src/modules/_shared/`). There are two exceptions. The first is the homepage's What I do (`src/modules/homepage/components/what-i-do.tsx`): three sentences of the site's own copy naming kinds of work, with no claims, because the API has no field for it. The second is the chat's prepared answers (`src/modules/chat/data/prepared-answers.ts`): fictional, generic mock copy for phase 3 that uses only the name from the API and states no facts about the person; their cards and sources are built only from the public profile's records the API returned, and the API replaces them in phase 7. No experience years, employer names or contact values are written into the app.
- Pages render on each request (`connection()`), so the build needs no API and no settings. Caching (#56, #57) and image optimisation (#55) belong to later issues. The chat (phase 3) answers from prepared fictional answers streamed in the browser through the shared chat contract; phase 7 connects it to the API (Modules, `chat`).
- Tokens, fonts and shared components come from `@sebela/ui` through its declared exports (`packages/ui/AGENTS.md`).

## Commands

| Task                                                | Command                                       |
| --------------------------------------------------- | --------------------------------------------- |
| Development server on this checkout's address       | `pnpm --filter @sebela/web dev`               |
| Build (no API or settings needed)                   | `pnpm --filter @sebela/web build`             |
| Serve the build                                     | `pnpm --filter @sebela/web start`             |
| Unit tests (Vitest)                                 | `pnpm --filter @sebela/web test`              |
| Browser tests against a real API (build first)      | `pnpm --filter @sebela/web test:e2e`          |
| Browser tests with every build they need (as in CI) | `pnpm test:e2e` (from the repository root)    |
| Lint, typecheck (`next typegen`, then `tsc`)        | `pnpm --filter @sebela/web lint`, `typecheck` |

`dev`, `start` and `test:e2e` read the process environment, then `.env.local`, `.env` and `.env.example` of the checkout (the earlier source wins). `dev` and `start` go through `scripts/next.mjs`, which passes `WEB_HOST` and `WEB_PORT` to Next and refuses to start without them. `dev` first builds the workspace packages the app depends on. For a browser read in development, run the API of the same checkout (`pnpm --filter @sebela/api dev`) and then `dev`.

## Configuration

| Variable           | Meaning                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WEB_HOST`         | Interface the website listens on (`dev`, `start`).                                                                                                                                                                                                                                                                                                                                                       |
| `WEB_PORT`         | Port the website listens on; the port scheme of `docs/repository-structure.md`.                                                                                                                                                                                                                                                                                                                          |
| `WEB_API_BASE_URL` | Base address of the API whose public routes the website reads: its origin, or an origin with a path prefix in front of `/v1`. Validated once per process by `readWebConfig` on the first content request: an `http` or `https` address without credentials, query or fragment; the error names the variable, never its value. Worktree setup writes the worktree's own API origin into its `.env.local`. |

The build reads none of them. A missing or invalid `WEB_API_BASE_URL` fails the first request that needs content, not the build. A worktree created before the harness wrote `WEB_API_BASE_URL` (commit `e2db9b4`) has no value for it: add `WEB_API_BASE_URL=http://<its API_HOST>:<its API_PORT>` to its `.env.local`, or recreate the worktree.

## Content states

`getHomepage()` reads `GET /v1/person`, `GET /v1/experiences` (with their projects), `GET /v1/technologies`, `GET /v1/current-focus`, `GET /v1/explorations` and `GET /v1/services` at the same time, then when the person has them the photo and the CV PDF through `GET /v1/media/{id}`, uncached (`no-store`) and within 5 seconds each, once per request however many components ask. A failed read of any list makes the page unavailable, never a homepage with a section silently missing.

- **Ready.** The homepage renders the hero (name, headline, short bio as inline Markdown, photo, the chat entry (one input line with its submit, then the suggested questions: two below `sm`, three from it), the calls to action "Work with me" to `/services` for clients and "View my experience" to `/experience` for employers), What I do (three columns of the site's own copy: kinds of work, no claims), Selected work (the projects selected for the homepage as numbered rows, each linking to its exact case study or project on `/experience`; left out when none is selected), the Experience snapshot (whole years since `careerStartedOn` when set, the experiences without an end date as the current roles, the primary technologies as a core and an AI engineering focus line, "Full experience" and the CV actions), Now (Working on: each current focus with its topics and a link to its project on `/experience` or its own http(s) link; Exploring: the ongoing explorations — no end date — with their stored status, each linking to it on `/experience`; then "Independent R&D" to `/experience#independent-rd` when any exploration exists and "AI Roadmap" to the placeholder `/ai-roadmap`; each column left out when empty, the section when both are), Services (each service's name linking to `/services#service-<slug>` and its summary, then "All services"; left out without services), the contact block (`#contact`, the email address and the person's web links) and the footer (repository and CV). Until phase 4, Exploring comes from the profile's explorations; phase 4 replaces its source with the AI Roadmap. The homepage's links to dynamic pages are not prefetched (each prefetch would read the API).
- **Missing.** The API answers 404: no profile is published, and the page answers 404 (`not-found.tsx`).
- **Unavailable.** The API fails, is unreachable or too slow: `error.tsx` says the content is unavailable and offers "Try again" (HTTP 500). The website never shows an empty profile in its place.
- A photo that cannot be shown (not an image, no address, no dimensions, a failed read) leaves the profile without one: the portrait shows the initials instead. Links that are not `http` or `https` are left out; the short bio renders only paragraphs, emphasis, code and links, never raw HTML.

`/experience`: `getExperience()` reads `GET /v1/person`, `GET /v1/experiences`, `GET /v1/explorations`, `GET /v1/technologies` and `GET /v1/education` the same way (uncached, 5 seconds each, once per request, at the same time), then each distinct organization logo and testimonial author photo once through `GET /v1/media/{id}`; a logo or photo that is missing, not an image, without a web address or dimensions, or whose read fails is left out without failing the page.

- **Ready.** The header (name, the headline as the summary, whole years since `careerStartedOn` when set, the CV actions) and the career timeline in the API's order: every experience its own row with the anchor `experience-<slug>`, the organization's logo when it has a usable one, period, kind label (`main_job` reads "Full-time job"), title and organization; current ones open, older ones closed (`docs/design.md`, Timeline). Each experience lists its own projects (anchor `project-<slug>`) with their evidence; a project's case study (anchor `case-study-<project slug>`) sits behind a disclosure. A link to any anchor opens the disclosures around it, scrolls to it and focuses it on load, hash change and back/forward; an unknown anchor opens nothing (`docs/design.md`, Timeline, Anchors). Testimonials appear only beside the experience they belong to, each with its author's photo beside the quote when it has a usable one and nothing in its place otherwise. Below the timeline, in this order: Independent R&D (anchor `independent-rd`; each exploration with the anchor `exploration-<slug>`, its stored status as visible text with its meaning, its sentence and concepts), Technologies (groups with the anchors `technology-group-core`, `technology-group-ai-engineering-focus` and `technology-group-secondary`; core with the website's static logos, the AI engineering focus as text, the secondary technologies behind a disclosure that a link opens) and Education (compact rows). Each is left out when it has nothing to show (`docs/design.md`, Experience sections).
- **Empty.** A published profile without experiences shows the header and "No experience is published yet."; the other sections still appear when they have content, and none appears empty or with a placeholder.
- **Missing** and **unavailable** behave as on the homepage (404, `error.tsx`); a failed read of experiences, explorations, technologies or education makes the page unavailable, never a page with a section silently missing.

`/services`: `getServices()` reads `GET /v1/person` and `GET /v1/services` the same way (uncached, 5 seconds each, once per request, at the same time).

- **Ready.** The header (name, "Services", the person's `servicesIntro` as Markdown when set), the services in the API's order as numbered rows, each at its anchor `service-<slug>` with who it is for, what the client gets and its evidence by kind: projects (to `project-<slug>` on `/experience`), independent R&D with its stored status (built and tested to `exploration-<slug>`; designed explorations only under "Planned, not built", never as evidence) and site links (kept exactly as stored when their path is one of the site's pages, `routes`; any other path is left out, never a dead link). Then the person's `servicesNote` (left out when null), the `collaborationSteps` under "How I work" (left out when empty), and "Get in touch" to the homepage's contact block (`/#contact`) (`docs/design.md`, Services page).
- **Empty.** A published profile without services shows the header and "No services are published yet."; the parts without content are left out and the closing action stays.
- **Missing** and **unavailable** behave as on the homepage; a failed read of the services makes the page unavailable, never a page without its services.

`/cv`: `getCv()` reads `GET /v1/cv` (uncached, 5 seconds, once per request). The API assembles the CV — which experiences it holds and in what order — and the website renders it as it comes, never selecting or reordering.

- **Ready.** One column, top to bottom: the name, the headline and the contacts (location, email address, web links; in print each link's address follows its label), the CV actions without the link to the page itself, then Summary (the short bio as Markdown), Experience (the experiences the API selected: period, kind label, title and organization, summary, responsibilities, technologies), Independent R&D (a short line per exploration with its stored status as visible text and its meaning — designed reads as an unimplemented design — period and summary; never among the experiences), Skills (each group's label and its technologies as one line) and Education (compact rows: title, institution, period, kind; no descriptions). Each section is left out when empty. In print the page is the same document dark on white whatever the theme, without the footer and the CV actions (`docs/design.md`, CV page).
- **Missing** and **unavailable** behave as on the homepage.

The CV actions (`CvActions`, in the homepage's experience snapshot, the Experience header and `/cv`): with a PDF, "Download CV" to `/cv/pdf` and "PDF updated <date>", the date being the day the PDF's media record was created (UTC) — never the person's or the media's `updatedAt`, so a profile edit never moves it. Without a PDF (none attached, not a PDF, no address, or its media cannot be read) only "Read the CV" to `/cv` and no date. The links to `/cv` are not prefetched: the page is dynamic, and a prefetch would render the CV and read the API on every view of a page that links to it.

Every page renders the site header (`SiteHeader`, `docs/design.md`, Navigation): the skip link, the name (or "Home" where no profile is read), the navigation with the current entry marked, "Ask AI" and the theme toggle; below `md`, a full-screen menu dialog. The root layout's inline `themeScript` applies a stored theme choice before paint (`docs/design.md`, Themes).

`/ask` (dynamic, not indexed): the chat. It reads the public profile the prepared answers rest on (`getAsk`: `GET /v1/person`, `GET /v1/experiences`, `GET /v1/services`, `GET /v1/explorations` and `GET /v1/technologies` at the same time) with the same missing and unavailable states as the other pages, reduces it on the server to plain evidence for the browser, and renders the assistant's introduction (an AI assistant over the public profile, never the person), the four suggested questions of an empty chat, the conversation, "New chat" and the composer. A conversation's address is `/ask?c=<random id>`; the question never enters the address. Conversations live in the tab only (`sessionStorage`, or memory where storage is refused); an unknown or invalid address opens an empty chat. An answer shows its text, then its block cards (experience, service, exploration with its stored status, contact; the roadmap card is rendered from a contract fixture only, with no records until phase 4), its sources (each the exact record on `/experience` or `/services`, built with the same anchor helper as the page, a case study opened inside its closed experience) and at most two related pages. Every block and source is shown only when the shared contract accepts it whole; an answer without evidence cites nothing, and the insufficient-evidence answer offers the contact card.

`/ai-roadmap` (static, not indexed): the AI Roadmap's placeholder until phase 4 — says it is not published yet, points to the independent R&D, and leads back to the homepage and to `/experience`. No roadmap data is read.

`/cv/pdf` (route handler, dynamic): `getCvPdfFile()` reads `GET /v1/cv`, then the named PDF's media and its file from the media's address (uncached, 15 seconds in all). The stored file is delivered as it is — `application/pdf`, `attachment; filename="<name-slug>-cv.pdf"`, `no-store` — only when it arrives whole, is served as a PDF and starts with `%PDF-`. Without a PDF the request is redirected (303) to `/cv`; when the file cannot be delivered, to `/cv/pdf/unavailable` (static, not indexed), which says nothing was downloaded and offers "Read the CV" and "Try the download again". The download links carry no `download` attribute, so a redirect opens as a page and is never saved as a file. Nothing generates a PDF.
