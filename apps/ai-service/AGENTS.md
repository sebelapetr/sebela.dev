# ai-service

The internal AI service: a FastAPI app (Python, a uv workspace member) that runs the portfolio chat agent (`packages/llm-agent`) for the API's guarded chat path, and serves bounded public read capabilities. Read the root `AGENTS.md` first; this file covers only what is specific to this app. The phase PRD is `.plan/07-ai-service/prd.md`.

## What it is

- **Internal, not public.** Only the API calls the generation route; the website never reaches this service. The service has no database access and no content-write key. It reads public content over the API's public read routes (through `llm_agent.ApiContentReader`) and reaches the API's two internal control routes with its own control bearer.
- **One operation per admitted question.** The API dispatches a question with a one-use grant; the service admits it or answers busy, claims the grant, runs the agent within the earlier deadline and the smaller allowance, and reports the one result back to the API. Nothing unapproved leaves the service: only what the Output Guard approved, mapped to the contract (`ChatGenerationResult` in `@sebela/contracts`).
- **Fictional model by default.** `AI_SERVICE_MODEL=fake` drives the real agent graph with a scripted model, no provider and no cost. The paid `anthropic` mode needs an explicit opt-in, a daily ceiling of its own and the provider key from the secret wrapper (`node harness/with-secrets.mjs -- <command>`).

| ---------------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /internal/v1/generations`                      | The API, with bearer                       | In order: the bearer (`AI_SERVICE_TOKEN`, constant time, before the body is read; 401), a 512 KiB body cap, strict validation (unknown fields refused; 422), the model, effort and pricing versions against this agent's (422 `version_mismatch`), admission (at most `AI_SERVICE_MAX_OPERATIONS` at once, a bounded wait; 503 `busy`), then 202 `{ "accepted": true }` while the operation runs on its own.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `POST /internal/v1/generations/{operationId}/cancel` | The API, with bearer                       | The API's Stop of one operation: the bearer first (401, also for a malformed identifier), a UUID identifier (422), then 202 `{ "accepted": true }` whether or not the operation runs here (no body; idempotent). A Stop before the dispatch or the claim prevents the claim; after the claim the generation's model and tool reads are cancelled, nothing more is scheduled and it reports `cancelled (stopped)` once, with the measured usage (uncertain while a model call was in flight). Other operations are untouched; the last 1024 Stops are remembered, so a late dispatch of a stopped operation is accepted and never claimed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `POST /internal/v1/compactions`                      | The API, with bearer                       | The API's dispatch of one compaction of a conversation's working context (#213): the same bearer, body cap, strict validation (a prior summary in the contract's shape, the working-context exchanges, no question), version check and admission as a generation, sharing its four slots and its Stop route, then 202 `{ "accepted": true }`. The claim must be a compaction's at the dispatched context revision, otherwise `failed (grant_mismatch)` without a model call. One summary call of the Main model without tools (at most one shared transient retry) folds the prior summary and the older complete exchanges and keeps the newest two; a context within them is `unchanged (nothing_to_compact)` without a model call. The one result goes to the compaction result route; a failure, timeout, Stop or over-budget result carries no summary, so the API keeps the prior working context.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `GET /v1/capabilities/<route>`                       | Read callers (the next phase's public MCP) | The fixed read capabilities, one literal route per read tool but the contact read, plus the technology catalogue: `profile`, `experiences`, `projects`, `project?slug=`, `services`, `explorations`, `education`, `current-focus`, `roadmap`, `roadmap-area?area=`, `learning-diary`, `learning-statistics`, `books`, `events` and `technologies` (the published catalogue: `slug`, `name`, `tier`, `group`, linked to the experience page's technology section; no model tool reads it, so what the model sees is unchanged). Each answers `CapabilityPage` (`capability`, `page`, `pageCount`, `records` of `kind`, `id`, `title`, canonical `href`, `data`), the same projections the model gets, 10 records a page. The query is the capability's own arguments (its input schema, in the OpenAPI document; none for the technologies) and `page` (1 to 30); an unknown or repeated parameter or a bad page is 422 `invalid_arguments` before any read, an unpublished record 404 `not_found`, any other path 404 and any other method 405. Shared bounds: at most 120 reads a sliding minute (429 `rate_limited` with `Retry-After`), 8 parallel reads never queued (503 `busy`), 5 s a read (503 `unavailable`, as for a failing read or an oversized result, never truncated). No bearer, no body; generation, compaction, conversations, the ledger, audit, credentials and stored originals are not reachable, and the bounds are separate from the generations'. |
| `GET /health`, `GET /ready`                          | The container, ops                         | Liveness, and readiness (503 `stopping` once a shutdown closed admission). Neither calls a model or the API.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

The service calls two API control routes with `AI_SERVICE_CONTROL_TOKEN` (the API's `API_AI_CONTROL_TOKEN`): `POST /v1/internal/chat/grants/claim` (one use; anything but a successful claim within the contract ends the operation without a model call and without a report) and `POST /v1/internal/chat/operations/{operationId}/result` (a generation's one result; a compaction's goes to `POST /v1/internal/chat/operations/{operationId}/compaction` under the same rules, retried on server and transport errors until a few seconds after the deadline; a redirect or a 4xx is final, whatever its body). Both go through the generated client `sebela_api_client` (`packages/api-client-python`) and its models `ChatGrantClaim`, `ChatGrantClaimed` and `ChatGenerationResult`, generated from the API document; no redirect is followed. The local `ResultReport` validates the result before it is sent and `tests/test_contract.py` ties it field by field to `ChatGenerationResult` in the API document, so a drift of the contract fails the tests.

With the trace export on, it also calls `POST /v1/internal/chat/operations/{operationId}/telemetry` (below, Trace export) through the same client and its models `ChatTelemetryRegistration` and `ChatTelemetryRegistered`.

The published interface is `openapi.json`, generated by `pnpm --filter @sebela/ai-service export:openapi` and kept in step by a test. The API generates its types of the generation request from it (`pnpm generate:ai-service-types`; `pnpm check:ai-service-types` fails on drift, in CI on every change). At run time the service serves no documentation and no OpenAPI route.

## Limits and shutdown

- The claim binds the operation to its terms: a claimed model, effort, pricing version or context revision that differs from the dispatched request's, or a claimed model, effort or pricing version that differs from this agent's (a claim without an effort included), ends it as `cancelled (grant_mismatch)` without a model call, with zero and certain usage; the API stores it as a failure (unavailable, retryable).
- The operation's deadline is the earlier of the request's and the claim's; its allowance is the smallest of the request's, the claim's and USD 0.02. An expired deadline is `limit_reached (deadline)` without a model call.
- Paid mode reserves the whole allowance against the service's daily ceiling (`AI_SERVICE_DAILY_CEILING_USD`, at most USD 0.25 per UTC day, per process) before the first model call; a refusal is `unavailable (daily_ceiling)` without a model call. Settling keeps the reported cost, or the whole reservation when the cost is uncertain or the run was interrupted.
- On shutdown the service stops admitting, waits up to `AI_SERVICE_SHUTDOWN_GRACE_S` for running operations, then interrupts them; they report `cancelled (interrupted)` with uncertain usage within a few seconds. Uvicorn's graceful shutdown timeout is the grace plus 10 s.

## Trace export

When `AI_SERVICE_LANGFUSE_BASE_URL`, `AI_SERVICE_LANGFUSE_PUBLIC_KEY` and `AI_SERVICE_LANGFUSE_SECRET_KEY` are all set, `runtime/telemetry.py` (`TraceExporter`) is the agent's `TelemetrySink`; with any of them empty nothing is registered or sent and every answer is unchanged. The deletion owner is the API: it stores each exported trace's reference and expiry and deletes it from Langfuse (`apps/api/AGENTS.md`, `chat-maintenance delete-telemetry`); this service keeps nothing.

1. After a successful claim, `Generations` binds the claimed grant to the operation; it is released when the operation ends. Each bound grant serves one record, and at most 64 are held.
2. The agent hands over its redacted `ExecutionRecord` before its result returns. `export` never blocks: it enqueues the record (16 at most) or drops it.
3. One worker task builds the body with `llm_agent.otlp_trace` in a single-thread executor (one masking job at a time, never on the event loop, at most 2 s), registers a fresh random trace identifier with the API's telemetry route (only `allowed` lets it go, so a conversation deleted meanwhile is never exported late), and posts it once to `{base}/api/public/otel/v1/traces` within the API's 10-minute export window, under Basic authentication with the project keys and `x-langfuse-ingestion-version: 4`, following no redirect.

The body is metadata only: nested spans for the stages, model attempts, tool calls and guard decisions with names, statuses, timing, models, token counts, cost, versions and outcome, and `degraded=no_detector`, because no local detector has passed the frozen corpus (`packages/llm-agent/AGENTS.md`, Trace pseudonymization). It never carries the question, the answer, a summary, tool data, the operation identifier, the grant, a token, a header value or an address; the API's own persistence stays authoritative. No Langfuse or OpenTelemetry SDK is installed (the anthropic SDK and FastAPI bring only the no-op `opentelemetry-api`), so no instrumentation or callback has another way out.

Every degraded path drops the trace, counts it (`TraceExporter.counts`), logs only the reason and never retries, spools or raises into the answer: no bound grant, no spans, a full queue, a failing or overrunning build, a refused or failed registration, an expired window, a 429, any other store failure, a record after shutdown and what shutdown leaves. Shutdown runs after the operations' own (`Generations.shutdown`) and gives queued traces at most 5 s.

`tests/test_telemetry.py` and `tests/test_trace_export_service.py` capture every outbound request whole, headers and body, through a fictional trace store and the fake API.

`scripts/measure_trace_export.py` is the repeatable workload measurement for S07 on the ARM64 server: `uv run python scripts/measure_trace_export.py [--detector <model-folder>] [--rounds N] [--json]` reports the masking version, the package and machine, cold and warm masking latency and throughput over the frozen local corpus, peak RSS before the detector loads and after the cold and warm passes, the CPU time, the exporter's throughput through a loopback store, and four concurrent fictional chats on one event loop without and with the export (wall time, loop-lag p95 and maximum). It uses no key, network or API, and its figures from a development machine are a fictional workload, not the production measurement.

**Real-cloud ingestion and deletion check (prepared for S07, not run here).** Every test above uses a fake trace store; only S07 checks the real Langfuse Cloud EU, without waiting 30 days:

1. Create a disposable Langfuse project for the check, with its own key pair; never the production project. Put its keys in the shell of a development stack with the demo seed only: `AI_SERVICE_LANGFUSE_*` for this service and `API_LANGFUSE_*` for the API, both pointing at the EU address.
2. Ask one fictional question in a fresh visitor conversation, so the API registers the trace and this service exports it. In the Langfuse project, confirm one trace with the nested stage, model and tool spans, `export_mode` `metadata` and `degraded` `no_detector`, and no question, answer, identifier, grant or key in it.
3. Clear the conversation (its clear reports `telemetryDeletion: pending`), wait out the 10-minute export horizon, run `pnpm --silent --filter @sebela/api chat-maintenance delete-telemetry`, and confirm the counts report the trace completed and that Langfuse no longer returns it. Ask again in that tab's new conversation and confirm the old trace does not come back.
4. Delete the disposable project and its keys. Record only counts, the mode and the outcome on the S07 issue, never a trace ID, key or screenshot of project data.

## Configuration

Every setting comes from the environment; nothing about the environment is hard-coded. Invalid or missing settings stop the start with a message that names the setting.

| Variable                          | Meaning                                                                                                                                                |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `AI_SERVICE_HOST`                 | The address to listen on. Required.                                                                                                                    |
| `LLM_AGENT_PORT`                  | The port to listen on (the ai-service row of the port scheme). Required.                                                                               |
| `AI_SERVICE_API_URL`              | The API base URL (`http` or `https`): public reads and the control routes. Required.                                                                   |
| `AI_SERVICE_TOKEN`                | The bearer the API presents on the generation route; at least 32 characters. Required.                                                                 |
| `AI_SERVICE_CONTROL_TOKEN`        | The bearer this service presents on the control routes; at least 32 characters, different from the above. Required.                                    |
| `AI_SERVICE_MODEL`                | `fake` (default) or `anthropic`.                                                                                                                       |
| `AI_SERVICE_FAKE_SCENARIO`        | The fictional model's behaviour: `answer` (default), `slow`, `refuse`, `fail`. Server configuration only.                                              |
| `AI_SERVICE_FAKE_CALLS_FILE`      | Tests only: an absolute file the fictional model appends each call to, so another process counts them. Fake mode only.                                 |
| `AI_SERVICE_FAKE_GATE_FILE`       | Tests only: an absolute file whose creation releases the `slow` scenario. Fake mode only.                                                              |

| `AI_SERVICE_LANGFUSE_BASE_URL`    | The Langfuse project's base address (`http` or `https`; the EU one is `https://cloud.langfuse.com`). All three Langfuse settings or the export is off. |
| `AI_SERVICE_LANGFUSE_PUBLIC_KEY`  | The project's public key.                                                                                                                              |
| `AI_SERVICE_LANGFUSE_SECRET_KEY`  | The project's secret key; only in the server's production environment file, never in a development checkout.                                           |
| `AI_SERVICE_LANGFUSE_ENVIRONMENT` | The trace environment: lowercase letters, digits, `-` or `_`, at most 40, not starting with `langfuse`; default `development`.                         |

## Container

`Dockerfile` builds from the repository root (`docker build --file apps/ai-service/Dockerfile .`): Python as `.python-version` and uv at the root `required-version` lower bound, both pinned by digest; `uv sync --locked --no-dev --no-editable --package ai-service`; a runtime stage with the virtual environment only, run as the unprivileged `app` user. The health check calls `/health` on `LLM_AGENT_PORT`; the command is `python -m ai_service`. The image holds no secret: every setting above comes from the container's environment.

In `compose.yaml` the service `ai-service` (profile `ai-service`) runs this image once the API is healthy, on the `chat` network it shares with the API only: it reaches the API by its service name (`AI_SERVICE_API_URL`) but not Postgres, MCP Admin or the website, and publishes no port. It receives only the settings above, its tokens from the API's `API_AI_SERVICE_TOKEN` and `API_AI_CONTROL_TOKEN`, and no database, storage, media or API key setting; its model defaults to the fictional one. The stop grace period is 75 s, the largest shutdown grace plus Uvicorn's 10 s and a margin. Start it in the main checkout with every chat setting given (`apps/api/AGENTS.md`, "Configuration"): `docker compose --profile api --profile web --profile ai-service up --build --detach --wait`; `pnpm stack:up` does not start it, so the chat stays off there. `pnpm test:api-stack` and `pnpm test:production-stack` check that it is healthy, unpublished and reaches the API but not Postgres. In production it stays behind its profile until the release pipeline publishes and deploys its image (`infra/README.md`).
