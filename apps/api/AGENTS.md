# @sebela/api

The Hono HTTP API, the only gateway to the data. Read the root `AGENTS.md` first; this file covers only what is specific to this app.

## What it is

The trust boundary of the repository. It may import `@sebela/services`, `@sebela/contracts` and `@sebela/config` (dependency table in `docs/repository-structure.md`), never `@sebela/db`; `@sebela/api-client` only in test files (`*.test.<ext>`), as a development dependency of its consumer contract tests; the import-boundaries rule rejects it anywhere else. Database settings, persistence and test databases reach it through `@sebela/services`. Routes stay thin; domain rules live in services and SQL in db.

`dev`, `start`, `api-keys`, `seed`, `clear-content`, `storage`, `media`, `knowledge` and `chat-maintenance` read the process environment, then `.env.local`, `.env` and `.env.example` of the checkout (the earlier source wins). Workspace packages resolve to their built `dist/`, so each command first builds what it runs from a fresh checkout: `dev` the workspace packages the API depends on (`--filter "@sebela/api^..."`), `start`, `api-keys`, `seed`, `clear-content`, `storage`, `media`, `knowledge` and `chat-maintenance` those and the API itself (`--filter "@sebela/api..."`). `api-keys` talks to the database through the services, so it needs no running server and no existing key. A new key is printed once; only its hash is stored, and `list` shows metadata only. `seed` loads the fictional demo seed, or the given seed folder, through the services in-process (format and rerun rules: `packages/db/seed/README.md`); it needs a migrated database and the media settings, but no running server and no API key, and prints counts and refusals by file and field, never content or the folder's path. `clear-content --confirm <database>` empties every table of the profile and the AI roadmap and deletes their stored media files through the services in-process, only when `<database>` is the configured `DATABASE_NAME` (exit code 0 cleared, 1 another name, 2 bad usage); API keys, the audit and the migrations stay. Take a backup first: in production `infra/scripts/clear-demo.sh` runs it in the API container after `backup.sh` succeeded (`infra/README.md`, Clearing the demo content). `seed --if-empty` loads only into a profile that holds nothing and otherwise prints that the seed was skipped; worktree setup uses it, so rerunning setup never overwrites edited content. `media upload <file> [--alt <text>]` uploads one PNG, JPEG, WebP or PDF file over the authenticated `POST /v1/media` like any other client, so a photo or CV PDF never passes through a model's tool call (`apps/mcp-admin/AGENTS.md`, File size and transport): it reads the owner's admin key from `SEBELA_ADMIN_API_KEY` in the process environment (the same key the owner's MCP client sends; it is in no settings file the command loads): either the variable is already set in the owner's shell, or the owner runs `node harness/with-secrets.mjs -- pnpm --silent --filter @sebela/api media upload <file>`, which gives it from the main checkout's `.env.secrets` (placeholder in `.env.secrets.example`) to that one process, sends to `http://API_HOST:API_PORT` (for a tunnel, set both in the shell; the process environment wins), resolves a relative path against where it was started, refuses locally what `checkMediaUpload` refuses under `MEDIA_MAX_BYTES` and `MEDIA_MAX_IMAGE_DIMENSION` (the API still decides), and prints the stored media ID as its last line. It prints the API's refusal code and message or the address it could not reach, never the key. `knowledge` builds like `seed` and works through the services in-process, so it needs a migrated database but no running server and no API key; every answer is one JSON document on stdout. `reindex` brings the retrieval index in step with the portfolio, embedding only sources whose content changed, and prints the report (sources, passages, tokens, cost); `candidates <file>` reads a JSON list of `{ id, query, kinds? }` (resolved like `seed`'s folder) and prints each question's candidate pool, best first, without the relevance floor, for the retrieval evals; `usage` prints the provider usage recorded this calendar month (UTC). The document commands take a fictional or owner-chosen supplemental document, UTF-8 Markdown (`.md`), plain text (`.txt`) or a PDF with a text layer (`.pdf`), through review and need the private storage settings (`PRIVATE_STORAGE_*`, below); the others never open it. `ingest <file> --slug <slug> --title <title>` (the options in either order, the file resolved like `seed`'s folder) checks the type, the size (1 MiB for text, 10 MiB for a PDF, before the file is read), a PDF's pages (100) and parser memory (256 MiB), the extracted size (500,000 characters) and the processing time (10 s), refuses a damaged, password-protected, scanned or image-only PDF and one whose text cannot be fully extracted, cleans the text (Unicode NFKC, line endings, whitespace, hyphenated line breaks), runs the local sensitivity checks (credential and secret formats, private keys, connection strings, e-mail addresses, telephone numbers, national identifiers, bank account numbers) and splits it into sections by heading and chunks by size with overlap, all without a provider call; it prints `{ created, version }`. A clean version is `pending` and its original is kept in private storage under a generated key; a version with findings is `blocked`, keeps no original and records each finding's kind and line in the original file (for a PDF, its page and the line on that page), never the detected value, and the command exits 1 asking for a sanitized revision. The same bytes ingested again are a no-op (`created: false`); changed bytes are a new version that needs its own approval. `--title` is the safe display title passages carry, and the slug makes the passages' `document:<slug>` identifier; the file name is never shown. `list` prints `{ documents }`, every version newest first; `show <hash>` the version's extracted text, sections, chunks and findings for the owner's preview; `approve <hash>` re-reads the original, checks it still has exactly that SHA-256 content hash, embeds it and makes it searchable, superseding the slug's earlier approved version and deleting that version's original, and holds back each chunk that conflicts with an API fact (a date, role title or technology that disagrees with the experience of the organization it names), recording the conflict on the version; `reject <hash>` rejects a pending or blocked version and deletes its original; `withdraw <hash>` takes an approved version out of search at once without a provider call and deletes its original (`withdrawn` is final); `delete <slug>` deletes every version of the document, its chunks and every original. `rebuild` rebuilds the whole index from the portfolio and the approved versions' retained originals, checking conflicts again against the current facts (so a corrected API fact takes effect at the next rebuild), and prints `{ portfolio, documents }`; an approved version whose original is gone, changed or now has findings is counted `missing`, named in `missingVersions` and left out of search while it stays approved, a document approved meanwhile stays published, and superseded or withdrawn originals still in storage are deleted. When private storage cannot delete an original, `withdraw` leaves the version withdrawn and out of search and `delete` removes nothing, both exit 1 and running the command again finishes it; `approve` and `rebuild` report the originals they could not delete in `originalsLeft`, and the next `rebuild` deletes them. Only approved versions are searched; pending, blocked, rejected, superseded and withdrawn ones never are, and no original is ever reachable through the media route, the API or a CDN. Exit code 0 done, 1 when the provider is unavailable, private storage could not delete an original, the month's budget is spent, the questions or document file is unreadable, or a document is refused (type, size, empty, invalid slug, unknown hash, findings, a state that cannot be approved, rejected or withdrawn, a slug without versions), 2 for bad usage; queries, settings and storage keys are never printed, and a document's text only by `show`. `storage prepare <worktree>` creates the worktree's storage folder `<environment>/<worktree>/` with an owner marker naming `<worktree>`, or reuses the folder that worktree already holds; `storage remove <worktree>` deletes the files of that folder only when the marker names the same worktree. Both refuse `production`, a missing `STORAGE_WORKTREE`, a folder of another owner and an unmarked folder that holds files, and print neither keys, paths nor credentials. `serve:e2e` is test support for the browser tests of the website (`apps/web/AGENTS.md`, Tests), not a server for content: it builds like `dev`, creates a temporary database (as the tests do, with the checkout's role), migrates it, loads the given seed folder into it with local storage in a temporary folder below the checkout's `.tmp/`, created when a clean checkout has none (environment `test`, its media addresses on its own `API_PORT`), serves the API from `src` on `API_HOST` and `API_PORT` (sending website invalidation notifications when `API_WEB_INVALIDATION_*` are set), and on `SIGTERM` or `SIGINT` drops the database and removes the folder. When `API_E2E_KEY_FILE` names a file, it also creates an API key on its temporary database and writes it to that file (mode 0600) for browser tests that write content through the private routes; `apps/web/e2e/invalidation.spec.ts` passes a file below `.tmp/` and removes it afterwards. When `API_E2E_KEYS_FILE` names a file, it creates one key per name in the comma-separated `API_E2E_KEY_NAMES` and writes `{ database, keys: [{ name, id, key }] }` there (mode 0600); `apps/mcp-admin/evals/fixture.js` uses it for the MCP Admin tests and evals, which revoke a key through `api-keys revoke` on that temporary database. It never touches the checkout's database, storage or the demo seed; it is excluded from the build. Its interface to the website's browser tests is the file itself: `apps/web/e2e/stack.ts` starts `node --import tsx src/cli/e2e-server.ts <folder>` in `apps/api`, without the script's build step, because `pnpm test:e2e` has built the dependencies once and the tests start several servers at the same time. Its storage folder is part of that interface too: it is `<checkout>/.tmp/e2e-storage-<random>/`, one per running server, with each file at its key below it (`test/...`). When `API_E2E_STORAGE_ROOT` names a folder, the server uses that folder instead and still removes it on shutdown; `apps/web/e2e/stack.ts` creates it for every server it starts, so a test knows which folder is its own server's while other test files run at the same time. `apps/web/e2e/cv.spec.ts`, `media.spec.ts` and `resilience.spec.ts` rename stored files there for a moment to test the website's failure states. When the chat settings are set, it serves the visitor chat too; when `API_E2E_CHAT_DAILY_SPEND_LIMIT_MICRO_USD` is also a whole number, the chat's daily spend limit is that many millionths of a US dollar instead of the policy's, so a test can exhaust the budget (`apps/ai-service/tests/integration/test_chat_stack.py`); anything else there refuses to start. Moving or renaming the file, changing its argument or the storage folder's place or prefix changes those callers in the same change. `chat-maintenance delete-expired` builds like `seed` and works through the services in-process, so it needs a migrated database and the chat settings but no running server and no API key: it deletes the visitor identities last seen longer ago than `API_CHAT_RETENTION_DAYS` (default 730) with their conversations, messages, operations and summaries, in at most `--max-batches` batches (default 100, at most 10,000) of at most `--batch-size` conversations (default 1,000, at most 10,000), keeps the spend accounting and a content-free count of each run, and prints one line with the number deleted, adding `; more may remain` when the last batch was full. Exit code 0 done, 1 when the chat is not configured or the database fails, 2 for bad usage. Run it on a schedule; nothing in the API process deletes expired conversations. `chat-maintenance delete-telemetry` builds and runs the same way: it first hands telemetry references whose 30 days (`chatTelemetryRetentionDays`) have passed to pending deletion, in at most `--max-requests` batches (default 10, at most 1,000) of at most `--batch-size` traces (default 1,000, at most 1,000, Langfuse's limit per request), then, when `API_LANGFUSE_BASE_URL`, `API_LANGFUSE_PUBLIC_KEY` and `API_LANGFUSE_SECRET_KEY` are all set (the EU address is `https://cloud.langfuse.com`), sends at most `--max-requests` `DELETE /api/public/traces` requests of due deletions, the longest due first. A deletion is never sent before its trace's export horizon (`chatTelemetryExportHorizonMs`, 10 minutes after registration) has passed, so a late export cannot recreate it; a visitor's clear makes its traces due right after that horizon. A failed request backs its batch off (15 minutes, doubling, at most 24 hours) and the run goes on; a 429 waits as `Retry-After` says (or backs off) and ends the run; a run that dies leaves its batch due again after a 15-minute lease. With the keys unset nothing is sent, the deletions stay pending and the run says so. It prints one line with the counts swept, sent, completed, failed and still pending, never a trace ID or key. Exit code 0 done (also when a request failed or was rate limited; the pending count says what remains), 1 when the chat is not configured, the Langfuse address is unusable or the database fails, 2 for bad usage. Langfuse's Hobby plan accepts 50 deletion requests a day, so schedule it at most about five times a day with the defaults; do not rely on the plan's 30-day read window. `openapi:export` builds like `start` and writes `describeApi()` as two-space JSON; it needs no database, configuration or secrets. Contributors normally run it through the root `pnpm generate:api-client`.

## Container stack

The main checkout can run the API in Docker: the profile `api` of the root `compose.yaml`, built from `Dockerfile` here (context: the repository root, allowlisted by the root `.dockerignore`). `pnpm stack:up` starts it together with the website container (profile `web`, `apps/web/AGENTS.md`, "Container"). Worktrees run the API on the host with the commands above. The image declares a `HEALTHCHECK` on `/health`, the same check `compose.yaml` declares, so the image is healthy also outside Compose; the production composition runs it from GHCR (`infra/README.md`). The AI service behind the visitor chat has its own profile `ai-service`, which `pnpm stack:up` does not start: it needs the chat settings (`API_CHAT_*`, `API_AI_*`, `API_TURNSTILE_*`), takes its two tokens from `API_AI_SERVICE_TOKEN` and `API_AI_CONTROL_TOKEN`, and starts with `docker compose --profile api --profile web --profile ai-service up --build --detach --wait` (`apps/ai-service/AGENTS.md`, Container). Without them the chat stays off and its routes answer 503.

| Task                                                           | Command (repository root)                                                                                                                      |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Build, migrate and start API and website; returns once healthy | `pnpm stack:up`                                                                                                                                |
| Load the demo seed                                             | `pnpm stack:seed`                                                                                                                              |
| Load a private seed folder outside the checkout                | `docker compose --profile api run --rm --volume <absolute folder>:/seed:ro api node dist/cli/seed.js /seed`                                    |
| Create, list or revoke an API key                              | `pnpm --silent stack:api-keys create <name>` / `list` / `revoke <id>`                                                                          |
| Logs                                                           | `pnpm stack:logs`                                                                                                                              |
| Stop and remove the API, website and AI service containers     | `pnpm stack:down` (Postgres keeps running for the worktrees)                                                                                   |
| Stop everything, keep data and media                           | `docker compose --profile api --profile web --profile ai-service down` (a plain `docker compose down` leaves the profiles' containers running) |
| Delete the data and the media as well                          | `docker compose --profile api --profile web --profile ai-service down --volumes`                                                               |

- **Order.** `migrate` (`node /app/packages/db/dist/cli/migrate.js`, the same image) starts once Postgres is healthy and applies the committed migrations; `api` starts only when it has exited with 0. A failed migration leaves the API down; the server itself never migrates. Running `stack:up` again re-runs `migrate`, which applies only new migrations.
- **Content.** Neither a start nor a restart seeds, resets or deletes content. The seed and the first key are separate, explicit one-off commands in a container of the `api` service; the key is printed once to the terminal, never to the service logs. The seed's rerun rules are those of `packages/db/seed/README.md`.
- **Configuration.** The containers get the same validated settings as the host API from the checkout's environment (`.env`), forwarded variable by variable in `compose.yaml`. None is required by Compose, so the Postgres-only commands of a checkout work without them: a missing one reaches the container empty, and `readApiConfig`, `readMediaConfig` or the migration's database settings stop it with its name. `pnpm stack:up` first refuses to start without `API_HOST` and `API_PORT`, the host address and port the API is published on; empty ones would publish it on every interface on a random port, so start the stack with `pnpm stack:up`, not a plain `docker compose --profile api up`. Four values are part of the declaration: inside the network the API reaches Postgres by its service name on the container port, and listens on every interface of its container on its own container port (`8080`). The database, role and password are the checkout's `DATABASE_*`.
- **Media.** `STORAGE_LOCAL_ROOT` is the folder of the named volume `api-media` (`/var/lib/sebela/media`), owned by the image's unprivileged `node` user; the key namespaces of `STORAGE_ENVIRONMENT` and `STORAGE_WORKTREE` apply below it. Uploads survive restarts and rebuilt containers and are deleted only with the volume. `STORAGE_PUBLIC_BASE_URL` stays the published address.
- **Website invalidation.** With `API_WEB_INVALIDATION_SECRET` set, `compose.yaml` points `API_WEB_INVALIDATION_URL` at the website container inside the Compose network (`http://web:8080/internal/invalidation`); without it the stack sends no notifications. The website container reads `WEB_INVALIDATION_SECRET`, which must be the same value.
- **Rate limits.** Requests from the host arrive through Docker's network, so every local caller shares one client address. Development only.
- **Image.** Production dependencies, the built `dist/` of the API and its workspace packages, the committed migrations and the fictional demo seed. No environment file, credentials or personal content; a private seed is mounted at run time. The runtime stage lists the manifest of every workspace package; add a new package's `package.json` there. The base image is pinned by tag and digest.
- **Smoke check.** `pnpm test:api-stack` (`scripts/checks/api-stack.e2e.mjs`, CI job `API stack smoke`) checks all of the above in a disposable Compose project; `pnpm test:web-stack` (`scripts/checks/web-stack.e2e.mjs`, CI job `Website stack smoke`) runs two complete stacks with the website side by side; see `docs/testing.md`, "CI".

## HTTP behaviour

- Versioned routes live under `/v1`. `GET /v1/person` is public; `POST`, `PATCH` and `DELETE /v1/person` are private. Besides the profile fields the person carries the Services page's prose: `servicesIntro` and `servicesNote` (Markdown or `null`) and the ordered `collaborationSteps` (title and Markdown description each); an update with `collaborationSteps` replaces the list, an omitted one keeps it. The catalogs `GET /v1/technologies`, `GET /v1/technologies/{slug}`, `GET /v1/topics` and `GET /v1/topics/{slug}` are public; `POST` on the collection and `PATCH`/`DELETE` on `{slug}` are private. The organizations follow the same pattern: `GET /v1/organizations` (ordered by name ignoring case, then slug) and `GET /v1/organizations/{slug}` are public, writes are private, and deleting an organization that other records still refer to answers 409 `conflict`. The experiences too: `GET /v1/experiences` (current roles first, then the latest start, the latest end and the slug) and `GET /v1/experiences/{slug}` are public and resolve the organization and the technologies in link order; writes are private and name the organization and technologies by slug. A create or update stores the experience and its links together or not at all; an update with `technologies` replaces every link, an omitted list keeps them. An unknown organization or technology, a repeated technology or an end before the start answers 400 `validation_failed` naming the field. Deleting an experience removes only its links; deleting a technology or an organization an experience still uses answers 409 `conflict`. The projects follow too: `GET /v1/projects` (grouped by owning experience in the experience order, then position, then slug) and `GET /v1/projects/{slug}` are public, name the owning experience by slug and resolve the technologies in link order; every experience response carries its projects, selected for the homepage or not, by position, then slug. Writes are private; a create requires an existing experience, and an update that sends `experience` moves the project to that experience, which is then its only owner. A missing or unknown experience, an invalid link, an unknown or repeated technology or an end before the start answers 400 `validation_failed` naming the field, with nothing written; a cover, case study or visibility flag is an unknown field. Deleting a project removes only its links; deleting an experience that owns a project, a technology a project uses, or a project that has a case study answers 409 `conflict`. Every project response, also inside an experience, carries its `caseStudy` (`null` without one). A project has at most one case study, addressed by the project's stable slug at `/v1/projects/{slug}/case-study`: `GET` is public, `POST`, `PATCH` and `DELETE` are private. `GET`, `PATCH` and `DELETE` answer 404 `not_found` for an unknown project or a project without a case study; `POST` answers 404 for an unknown project and 409 `conflict` when the project already has one, also for competing creates, and a create answers 201 with `Location: /v1/projects/<slug>/case-study`. The `role` (plain text, at most 500 characters) and the Markdown `body` (at most 50,000 characters, trimmed, otherwise stored as written, never rendered to HTML) are strict fields. Deleting the case study leaves its project. The explorations are outside the career timeline: `GET /v1/explorations` (by position, then slug) and `GET /v1/explorations/{slug}` are public, return the `built`/`tested`/`designed` status exactly as stored and resolve the technologies and topics in link order; writes are private and name the technologies and topics by slug. A create or update stores the exploration and its links together or not at all; a sent `concepts`, `technologies` or `topics` list replaces that list, an omitted one keeps it. An unknown status, an unknown or repeated technology or topic or an end before the start answers 400 `validation_failed` naming the field; an experience, project or visibility flag is an unknown field. Deleting an exploration removes only its links; deleting a technology or a topic an exploration still uses answers 409 `conflict`. The services follow too: `GET /v1/services` (position, then slug) and `GET /v1/services/{slug}` are public and return the name, summary, audience, deliverable and the evidence in its stored order, each piece typed by `kind`: `project` (slug, name, summary and owning experience), `exploration` (slug, name, summary and the status exactly as stored) or `link` (label and a path within the site). Writes are private and name projects and explorations by slug; a create or update stores the service and its evidence together or not at all, an update with `evidence` replaces all evidence in its order (an empty list removes it), an omitted list keeps it. An unknown or repeated project or exploration, an unsupported kind, or a link that is not a path within the site (a scheme, `//`, whitespace or a backslash) answers 400 `validation_failed` naming `evidence`, with the previous service and evidence intact. Deleting a service removes only its evidence; deleting a project or an exploration a service names answers 409 `conflict`. The education records follow too: `GET /v1/education` (position, then slug) and `GET /v1/education/{slug}` are public and return the kind (`school`, `course`, `certification` or `milestone`) exactly as stored, the title, institution, description and period; writes are private. A period needs at least one date: a start alone is ongoing learning, an end alone a completion on that day, and the end is never before the start, checked on the resulting record when an update sends only one date. An unknown kind, text out of bounds, a period without a date (naming `startedOn` and `endedOn`) or an end before the start (naming `endedOn`) answers 400 `validation_failed`. Nothing refers to an education record, so deleting one never conflicts. The testimonials follow too: `GET /v1/testimonials` (grouped by experience in the experience order, then position, then slug) and `GET /v1/testimonials/{slug}` are public, name the experience each belongs to by slug and carry the optional author photo as `authorPhotoId` (a media identifier or `null`); every experience response carries its testimonials by position, then slug, beside its organization and projects. Writes are private; a create requires an existing experience, and an update that sends `experience` moves the testimonial to that experience. A missing or unknown experience or a quote, author name or author role out of bounds answers 400 `validation_failed` naming the field, with nothing changed. Deleting a testimonial never conflicts and keeps its author photo; deleting an experience that has a testimonial answers 409 `conflict`. The current focus follows too: `GET /v1/current-focus` (by position, then slug) and `GET /v1/current-focus/{slug}` are public and resolve each entry's optional project (slug, name and experience, or `null`) and its topics in link order. Writes are private; `project` and `topics` name existing records by slug, an omitted link or project means none on create, and on update a slug replaces the project, `null` clears the project or the link, a sent `topics` list replaces every link and an omitted field keeps it. An unknown project, unknown or repeated topics, a link that is not `http` or `https`, or text out of bounds answers 400 `validation_failed` naming the field, with nothing changed. Deleting a focus entry never conflicts and keeps its project and topics; deleting a project or topic a focus entry links answers 409 `conflict`. The media are addressed by identifier: `GET /v1/media` (newest first, then identifier) and `GET /v1/media/{id}` are public and return the storage key, the type the content proved, the byte size, the image dimensions (`null` for a PDF), the alt text and a `url` computed from `STORAGE_PUBLIC_BASE_URL`, never stored; `url` is `null` for a record whose key the configured storage cannot address (stored under another environment or worktree prefix), which stays listed and readable while its file route answers 404. `POST /v1/media` is private and takes `multipart/form-data` with exactly one file part `file` and an optional `altText`; it accepts PNG, JPEG, WebP and PDF within `MEDIA_MAX_BYTES` and `MEDIA_MAX_IMAGE_DIMENSION`, answers 201 with `Location: /v1/media/<id>`, 415 for a body that is not a multipart form or a file whose content, declared type or extension disagree, 413 beyond the size limit and 400 `validation_failed` on `file` for a missing, repeated, empty, malformed or oversized image. The API generates the key; the file name never chooses it. `PATCH /v1/media/{id}` changes or clears the alt text only; `DELETE /v1/media/{id}` answers 409 `conflict` while the person, an organization, a project, a testimonial or a bookshelf book refers to the media, and otherwise removes the record and the file. `GET /v1/media/files/{key}` is public and serves a recorded local file inline with its proved type and `nosniff`; images carry `Content-Security-Policy: default-src 'none'; sandbox` and `Content-Disposition: inline`, a PDF carries `default-src 'none'` without `sandbox` (browser PDF viewers refuse sandboxed documents) and `Content-Disposition: inline; filename="<uuid>.pdf"`; a key with characters a generated key cannot contain, or one that names no recorded file, answers 404. Media are attached through the owning record's update: `photoId` and `cvPdfId` of the person, `logoId` of an organization, `coverId` of a project and `authorPhotoId` of a testimonial (also on its create) name media by identifier, and `null` clears them; unknown media or the wrong kind (a PDF as an image, an image as the CV) answers 400 `validation_failed` naming the field, with nothing written. The current CV PDF is uploaded as prepared; the API never generates it. Lists are plain JSON arrays in their documented order; a create answers 201 with `Location: /v1/<collection>/<slug>`; the slug cannot change. `GET /health`, `GET /openapi.json` and `GET /reference` are public and need no key. `GET /v1/authentication` is private and read-only: it answers 200 `{ "status": "authenticated" }` for a valid key and the usual 401 otherwise, through the same Bearer verification and budgets as every private route; it reads and changes no content. MCP Admin calls it with its caller's key before discovery and before every operation (`apps/mcp-admin/AGENTS.md`), so a revoked key fails on its next one.
- `GET /v1/cv` is public and read-only; no method writes to it (other methods answer 404). It returns the CV data assembled from the stored profile on every request: the person (contacts, links, summary), the experiences selected for the CV (`inCv`) in the experience order, the technology catalog grouped into `primary.core`, `primary.aiEngineeringFocus` and `secondary`, every education record, the explorations in a section of their own with their stored `built`/`tested`/`designed` status, and the current CV PDF (`cvPdf`, its `url` from the storage, `null` without a configured storage or when the storage cannot address the key). Absent sections are empty lists and an absent PDF is `null`; while there is no person it answers 404 `not_found` and creates nothing. It is CV data, not the CV page, and it never generates or updates the PDF.
- `GET /v1/roadmap` is public and read-only: every roadmap area, its modules and their resources in position order (then slug), each resource with its topics, plus the progress of each area and module and the roadmap's totals, derived on every request and never stored (decision 0019). `GET /v1/roadmap/tree/:area` and `GET /v1/roadmap/tree/:area/:module` are public and read one node of that tree at its nested address, from the same snapshot and with the same progress as the overview: `{ area }` with its modules and resources, or `{ area, module }` with the area without its modules and the module with its resources; a missing area or module, and a module that belongs to another area, answer 404 `not_found`, and an invalid slug 400 `validation_failed` naming `area` or `module`. `GET /v1/roadmap/current` is public: `{ areas }`, the areas whose derived status is `in-progress`, each with only its `in-progress` modules, in tree order, with their progress and without resources; nothing in progress is the valid empty list. `GET /v1/roadmap/{areas,modules,resources}/:slug` read one record; `POST /v1/roadmap/{areas,modules,resources}` (201 with `Location`), `PATCH` and `DELETE` on `:slug` (204) are private. A module names its area and a resource its module and topics by slug; a PATCH with `area` or `module` moves the record and `topics` replaces the links. Refusals: 404 `not_found`; 409 `conflict` for a taken slug or deleting an area with modules, a module with resources, a resource with time entries or a topic linked to a resource; 400 `validation_failed` naming `slug` (the reserved area slugs `diary`, `bookshelf`, `events`, `how-to-read-effectively`), `area`, `module`, `topics` (unknown or repeated) or `finishedAt` (before the start, including a stored start). Writes notify the content domains `roadmap-area`, `roadmap-module` and `roadmap-resource`.
- The learning diary (decision 0020): `GET /v1/roadmap/diary` is public, `{ days }`, every Europe/Prague calendar day with notes or time entries, newest first, each `{ date, notes, entries, totalSeconds, events }` with its entries in time order and their resource (slug, name, link, module, area) or event (slug, name, kind, dates, link), and the events whose inclusive dates cover the day; a day covered only by an event is listed without notes or time, and an event's dates add nothing to `totalSeconds`; an empty diary is `{ days: [] }`. `GET /v1/roadmap/diary/:date` is public and reads one day; a day without notes, entries and a covering event answers 404 `not_found`, an impossible date 400. Private: `PATCH /v1/roadmap/diary/:date` creates the day or replaces its Markdown notes (200 with the day, its time entries stay); `DELETE` on it clears the notes (204, 404 without notes); `POST /v1/roadmap/time-entries` logs a session `{ resource, startedAt, endedAt }` or attendance `{ event, startedAt, endedAt }` (exactly one target; 201 with `{ entries, dates }`); `POST /v1/roadmap/sessions` logs the same session or attendance with optional Markdown `notes` (`RoadmapSessionCreate`) and appends the notes after a blank line to the session's first diary day in the same transaction (201 with `{ entries, dates }`; a refused session writes neither, 409 on overlap); `PATCH /v1/roadmap/time-entries/:id` changes only the fields sent (200 with the written entries and every day touched, old and new); `DELETE` on it (204). Instants carry `Z` or an offset and whole seconds; a session is split at each Prague midnight into one entry per day without changing its elapsed time, all or nothing. Durations and totals are derived from the endpoints on every read, never stored. Refusals: 400 `validation_failed` naming `resource` or `event` (unknown; `event` also for both targets or neither), `startedAt`/`endedAt` (attendance outside the event's days), `endedAt` (not after the start) or `startedAt`/`endedAt` (no offset, fractions of a second); 409 `conflict` for an interval overlapping any logged interval on any resource or event, judged by the database so one of two concurrent overlapping writes loses (adjacent intervals are allowed); 404 `not_found` for an unknown entry. Writes notify the content domain `roadmap-diary` once per diary day they changed, the record being the date.
- The bookshelf (issue #112): `GET /v1/roadmap/books` is public, every book as an array by ascending `priority`, then slug (`[]` when empty), and `GET /v1/roadmap/books/:slug` reads one (404 `not_found`). Each book carries its cover media with its public `url`, the `status` derived from its dates, the resource of type `book` that links it and `readingSeconds`, the time logged on that resource, so it equals the diary's totals for it. Private: `POST /v1/roadmap/books` (201 with `Location`; 409 `conflict` for a taken slug), `PATCH /v1/roadmap/books/:slug` (only the fields sent, `null` clears) and `DELETE` on it (204; 409 `conflict` while a resource links it; its cover media stays). 400 `validation_failed` names `coverId` (unknown media or not an image) or `endedOn` (before the start, also against the stored start). A resource links a book with `book: "<slug>"` in its create or update body; 400 `validation_failed` on `book` for an unknown book, a book another resource links or a resource whose type is not `book`. Deleting media a book uses as cover is 409 `conflict`. Book writes notify the content domain `roadmap-book` with the book's slug; a resource's link change is a `roadmap-resource` change. Book time is logged only as time entries on the linking resource.
- The attended events (issue #113): `GET /v1/roadmap/events` is public, every event newest start first, then latest end and slug (`[]` when empty), and `GET /v1/roadmap/events/:slug` reads one (404 `not_found`). Each event carries its kind, organizer, inclusive Prague `startsOn`/`endsOn`, place, `online`, link, takeaways, topics and `attendanceSeconds`, the time logged on it alone. Private: `POST /v1/roadmap/events` (201 with `Location`; 409 `conflict` for a taken slug), `PATCH /v1/roadmap/events/:slug` (only the fields sent, `null` clears, `topics` replace the links; 409 `conflict` naming the days when new dates would leave logged attendance outside the event, with nothing changed) and `DELETE` on it (204; 409 `conflict` while it has attendance). 400 `validation_failed` names `endsOn` (before the start, also against the stored start) or `topics` (unknown or repeated). An event is not a resource: it is not part of the tree, its progress or the current learning. Attendance is logged through the time-entry routes with `event`. Event writes notify the content domain `roadmap-event` with the event's slug; the website's whole-profile clear refreshes the event listing and the old and new diary days of a moved event, and attendance notifies `roadmap-diary` with its days.
- The learning statistics (issue #114): `GET /v1/roadmap/statistics` is public and read-only (other methods 404) and takes no parameters. It returns `{ totals, days, weeks, months, areas, resources, events }`, every value whole seconds split into `resourceSeconds`, `bookSeconds` and `eventSeconds` with their `totalSeconds`. Each time entry counts once: an event entry as event time, a resource entry of type `book` as book time, any other as resource time. Days are the Europe/Prague days with time, oldest first, and equal the diary's `totalSeconds`; weeks (Monday start) and months run without gaps from the first to the last with time; an interval crossing a boundary adds only its elapsed part, and a daylight-saving day keeps its real length. `areas` and their `modules` carry only resource and book time, through each resource's current module; event time is never in an area. The sums run in PostgreSQL on every read; nothing is cached or stored. With no time logged, totals are zero and every list is empty. The read needs no notification of its own: the writes that change it already notify `roadmap-diary`, `roadmap-resource`, `roadmap-module`, `roadmap-area`, `roadmap-book` and `roadmap-event`.
- The supporting content (issue #115): `GET /v1/roadmap/project-ideas`, `GET /v1/roadmap/followed-sources` and `GET /v1/roadmap/glossary-terms` are public, each an array ordered by position, then slug (`[]` when empty), and `GET` on `/:slug` of each reads one (404 `not_found`). A project idea carries `title`, Markdown `whyItMatters`, optional Markdown `howToStart` and its `topics` in their order; a followed source `title`, optional Markdown `description`, optional `http`/`https` `link` and free-text `kind`; a glossary term `term` and Markdown `description`; each has `position` and timestamps. Private: `POST` on the list (201 with `Location`; 409 `conflict` for a taken slug), `PATCH` on the record (only the fields sent, `null` clears an optional one, given `topics` replace the links, the slug cannot change) and `DELETE` on it (204; nothing references these records, so only 404). 400 `validation_failed` names `topics` (unknown or repeated) or `link` (not `http`/`https`). Writes notify the content domains `roadmap-project-idea`, `roadmap-followed-source` and `roadmap-glossary-term` with the record's slug; the website maps them to its whole-profile clear. These lists, with the reads above, are also the data sources of the website's sitemap, `llms.txt`, structured data and Open Graph output; the API has no separate discovery route.
- Order of checks on every route: per-client rate budget, refusal of credentials in the query string, then on private routes bearer-key verification and the per-key budget, then on routes with path parameters their schema (400 `validation_failed` naming the parameter, so an unauthenticated caller learns nothing about the path), then on body routes the content type, the size and the Zod schema (on the upload route the multipart form, its file part and its other fields). Nothing reaches storage or the database before these checks pass, so a refused or unauthenticated upload leaves neither a file nor a record. A handler never runs for a request that failed an earlier check.
- Every failure is the common `ErrorResponse` of `@sebela/contracts` (`error.code`, `error.message`, optional `error.fields`). Statuses: 400 `malformed_json` / `validation_failed` / `credentials_in_url`, 401 `unauthorized` with `WWW-Authenticate: Bearer`, 404 `not_found`, 409 `conflict`, 413 `payload_too_large`, 415 `unsupported_media_type`, 429 `rate_limited` with `Retry-After`, 500 `internal_error` without details, 503 `unavailable` without details (readiness, and the visitor chat while it is off), the chat's 403 `forbidden` / `chat_challenge_failed`, 409 `chat_busy` / `chat_request_conflict` / `chat_not_retryable`, 429 `chat_quota_exceeded` and 503 `chat_budget_exhausted`, 503 `provider_unavailable` / `budget_exhausted` (an outside provider the route needs is not configured, failed or did not answer in time, or the month's spend on it reached its limit).
- Health (issue #232): `GET /health` is liveness only and never touches the database. `GET /health/ready` is public readiness: `{ status: "ready" }` when the database answers a trivial query within 2 seconds (`services.health.databaseReachable()`), otherwise 503 `unavailable` without any detail of the failure. Readiness answers with `Cache-Control: no-store`. Both share the `health` rate budget and are what the website's `/health` and uptime monitoring call.
- The visitor chat (issues #210 and #211; `docs/architecture.md`, Chat): `GET /v1/chat/conversation` (the caller's one conversation: a page of its newest messages, or those `before` a message, oldest first, with its active operation), `GET /v1/chat/usage` (#212: the caller's own usage and policy snapshot, read without consuming anything: the server time, the read-only model and effort, the rolling two-hour meter with its next capacity release and the UTC-day meter with its reset, the active operation, the restriction that would refuse a question now (the caller's own `minute`, `two_hours` or `day` limit, or `shared_network` or `service_budget`, which are not the caller's meter) with its retry time, and the last main call's context as measured or `unavailable`; never another visitor's use or the site-wide spend), `POST /v1/chat/conversation/messages` (ask one question; 202 with the operation, 200 with the existing one for a repeated request ID), `POST /v1/chat/conversation/compact` (#213: `{ requestId, challengeToken }`, the visitor's `/compact`: summarizes the working context, appends no message and changes no visible history; a context of fewer than three complete exchanges is a 200 local no-op before any challenge, quota or spend; otherwise the same challenge, quota (it counts as a question), spend and one-active-operation gates as a question, 202 with the `compaction` operation, 200 with it again for a repeated request ID, 409 `chat_request_conflict` for a request ID used by a question; only a valid summary reported against the conversation's current context revision is installed), `GET /v1/chat/operations/:operationId` and `GET /v1/chat/operations/:operationId/events` (server-sent `chat` events with IDs, resumable with `Last-Event-ID`, an ID-less `progress` event at least every five seconds while the operation runs, ending at the terminal event or with a retryable `timeout` after the deadline and a short grace), `POST /v1/chat/operations/:operationId/stop` (from any tab, without a body or a new challenge: an active operation ends as a retryable `cancelled` error, its reservation stays uncertain once its grant was claimed, and the supervisor tells the AI service to stop; an operation that already ended is returned as it is), `POST /v1/chat/operations/:operationId/retry` (`{ retryId, challengeToken }`: a new attempt of a failed request under its own retry ID; the same retry ID again, or an active or answered attempt of the request, is 200 with that operation before any challenge, quota or spend; otherwise 202 after the same gates as a question, and only the failed answer is replaced; 409 `chat_not_retryable` when the attempt is not a retryable failure of the latest question) and `DELETE /v1/chat/conversation` (`{ conversationId }` as the visitor confirmed it: cancels active work, deletes the messages, tombstones operations that may still report so a late result cannot recreate content, and starts a fresh empty conversation of the same identity; quotas, spend and redeemed challenges stay; another conversation ID clears nothing; `telemetryDeletion` is `none` when nothing was exported and `pending` while exported telemetry awaits deletion, never claimed complete). They are public and take no API key: the caller is the `sebela_chat` cookie (`HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` when `API_CHAT_COOKIE_SECURE=true`, Max-Age the retention), and a missing, unknown or forged cookie gets a fresh identity, so another visitor's operation is 404 `not_found`. Every answer is `Cache-Control: no-store`. Ask, compact, Stop, retry and clear are the named public visitor writes: a request without an allowed `Origin`, or one with a body without a JSON content type, is 403 `forbidden` before anything is read or stored (Stop has no body, so only its origin is checked). The ask and compact routes then check the challenge (403 `chat_challenge_failed`), the quotas (429 `chat_quota_exceeded` with `Retry-After`), a request ID reused for another question (409 `chat_request_conflict`), a question or compaction already in progress (409 `chat_busy`) and the spend budget (503 `chat_budget_exhausted`). While the chat is on, the nine visitor routes answer only the website's chat relay: a request without `x-sebela-chat-relay` equal to `API_CHAT_RELAY_TOKEN` (compared by digest in constant time, never logged) is 403 `forbidden` before anything is read or stored. The visitor address for the address quota and Siteverify's `remoteip` is the relay's `x-sebela-chat-client` header, believed only with a valid token and only when it is an IP literal; otherwise every such visitor shares one unknown-address quota and Siteverify gets no `remoteip`. `X-Forwarded-For` and `API_TRUSTED_PROXIES` play no part in the chat. The admitted operation is dispatched by the supervisor (`src/modules/chat`) to the AI service, detached from the request. The internal control routes `POST /v1/internal/chat/grants/claim`, `POST /v1/internal/chat/operations/:operationId/result` (an answer) and `POST /v1/internal/chat/operations/:operationId/compaction` (a compaction; the other kind's report is 403 `forbidden`) and `POST /v1/internal/chat/operations/:operationId/telemetry` (`ChatTelemetryRegistrationSchema`: the operation's grant and one trace ID the AI service means to export; 200 `ChatTelemetryRegisteredSchema` with `export` `allowed` or `refused` and the trace's `expiresAt`, refused when the conversation or operation was deleted or the trace is already owed a deletion; a repeat answers alike; 409 `conflict` for an unclaimed grant or a trace ID another operation registered, 403 `forbidden` for another operation's grant; the AI service exports only an allowed trace and only within the horizon) take only `API_AI_CONTROL_TOKEN` as a bearer token, compared in constant time (401 `unauthorized` otherwise; an API key is never accepted there and the control token nowhere else); a claimed or finished grant is 409 `conflict`, another operation's grant 403 `forbidden`. None of the chat routes is audited or announced to `onWrite`; their bodies, cookies, grants and tokens never reach a log. While the chat is off, every visitor route is 503 `unavailable` and the control routes 401. The visitor routes run the per-client public budget, the credentials-in-URL refusal, the off check, the relay check, the origin check, the body and the path parameters in that order. With a valid relay token the public budget counts the request against the visitor the relay names (relayed requests naming none share one bucket), never against the website's connection, so one visitor's flood refuses neither other visitors nor the website's own public reads; without it the request counts against its connection, like every other public route.
- Every response carries `X-Content-Type-Options: nosniff`; CORS is not enabled. Request and error logs are redacted: no bearer token or `sebela_` key reaches them.
- Media cleanup: an upload whose record cannot be written removes its file again; a deleted record whose file cannot be removed still answers 204. A removal that fails is logged by `logCleanupFailure` as one redacted line with the operation, the key and the error name and message (no stack, file contents or credentials); the file is then an orphan to remove by hand under that key. A successful response never names media whose file is missing.
- Content audit (issue #154, decision 0021): every write route that declares a `content` domain runs through `services.audit.write`, which commits the content change and its audit entries in one transaction, so an audit that cannot be stored rolls the content back. Each entry is stored in the private `audit` schema with the verified key (from authentication, never from the request), the `operationId`, method and route template, the optional caller-stated `sebela-provenance` header (`^[a-z][a-z0-9._:/-]*$`, at most 64 characters; anything else answers 400 `validation_failed` on `provenance` before the write runs), the entity and record, the action and the record's public read before and after. No credentials, other headers or file bytes are stored. A refused, invalid, conflicting or failed write stores nothing, and reads never do. The entity is the route's `content` domain and the records come from the slug, identifier or date path parameter or the created record's `slug`/`id`; a route overrides that with its `audit` (`RouteAudit`, whose `records(params, body)` also sees the validated body), as the time-entry routes do (entity `roadmap-time-entry`, records the written entries) and the session route does (entity `roadmap-diary`, records every Prague day the session's interval touches, from `sessionDiaryDates`). Audited writes run one at a time (a transaction advisory lock). Seed loads are not API writes and are not audited.
- `GET /v1/audit/changes` (private, `listRecentChanges`) returns `{ changes }`, the newest 20 (`recentChangesLimit`) audit entries, newest first, each with the key's name. A client that lost a write's response reads it before it retries. The provenance label is what the caller stated, never proof of who acted or that a human approved.
- `onWrite` in `createApp` is the attachment point for successful-write notifications. It runs only after the route's service has resolved, that is after the write committed; a refused, invalid, conflicting or failed write never reaches it, and reads never do. Each event carries the `change` the write made: the route's declared `content` domain, the record (the route's `records` hook when it declares one, one event per record — the diary's writes name every day they changed; else the `slug` or `id` path parameter, else the created record's; `null` for the person) and the action (`POST` created, `PATCH` updated, `DELETE` deleted). A write route without `content` stops `createApp`. The default is a no-op; a notifier that throws or rejects is logged as `error notifying <method> <path>: <error name>` (never its message) and never fails or rolls back the write, which still answers success. A write whose transaction fails answers its error and sends nothing.

## Website invalidation

When `API_WEB_INVALIDATION_URL` and `API_WEB_INVALIDATION_SECRET` are set, `src/server.ts` (and `src/cli/e2e-server.ts`) attach `createWebsiteInvalidation` from `src/modules/invalidation` as `onWrite`; otherwise nothing is sent. Every committed content write becomes one notification in the shape and signature of the website invalidation contract (`packages/contracts/AGENTS.md`, "Website invalidation contract"): a `POST` of `application/json` with `sebela-invalidation-timestamp` and `sebela-invalidation-signature` headers, signed over the exact body bytes with the dedicated secret. The destination and secret come only from the server environment, never from a query string, browser code or a log line.

- `notify` queues and returns at once, so the website's state never delays or fails a write. Deliveries run one at a time; at most 32 wait, and a change beyond that is dropped and logged.
- Each attempt has a 2-second timeout. A network error, timeout, 5xx or 429 is retried twice (after 250 ms and 1 s) with the same event identifier and body bytes and a fresh timestamp and signature; any other status, redirects included (never followed), ends delivery. The response body is never read. This budget (three attempts of at most 2 s each, 250 ms and 1 s apart, so about 7 s at worst) is the module's default, which `src/server.ts` and `src/cli/e2e-server.ts` use (tests pass their own); there is no persistent queue and no background worker, so a notification still queued when the process stops is lost. A lost notification leaves cached pages to the website's fallback revalidation interval (`apps/web/AGENTS.md`, Caching and invalidation, which also lists the operator signals).
- Log lines name the event identifier, the attempt and the status or error name only.
- Delivery is at least once and unordered across retries: the website treats a notification as "refetch current data", so duplicates and out-of-order arrivals are harmless.
- On `SIGTERM`/`SIGINT` the sender is closed: the delivery in flight is aborted and the queue dropped.

## Adding a route

1. Add or extend the contract schemas in `@sebela/contracts` and the service operation in `@sebela/services`, each test-first.
2. Add a `defineRoute` entry to the owning module (its `index.ts` or a private file it composes) with its access, path-parameter and body schemas, success and errors (a write route also its `content` domain, which makes it audited), and register the module in `app.ts`. OpenAPI, the route-registry property test and the audit coverage check in `src/audit.test.ts` pick it up from there; a write registered without a `content` domain fails the coverage check; a private route needs valid route parameters in the property test.
3. Regenerate the client with `pnpm generate:api-client` from the repository root and commit `packages/api-client/src/generated/`; CI's drift check fails otherwise.
4. Extend `src/client.test.ts` with the new or changed operation's success and documented errors, through the client.
5. Update this module map and the OpenAPI expectations.

## Tests

`pnpm --filter @sebela/api test`. Vitest against real Postgres: each test file creates its own temporary migrated database through `@sebela/services/testing` with small fictional fixtures. Rate-limit tests use a controlled clock. Media tests (`src/media.test.ts`) store files in a temporary local storage root per test file (`openTestBackend` in `src/test-support.ts`) with fictional sample files from `@sebela/services/testing`, and cover upload to attachment to download, alt-text updates, refused deletes, malformed and misleading files, excessive size and dimensions, unauthenticated uploads leaving nothing behind and traversal attempts in file names and keys. `src/invalidation.test.ts` drives the website invalidation sender through a recording fetch and a real local HTTP server on `API_HOST` (port 0), with a disposable fixture secret, and checks over a temporary database that committed writes, and only those, reach the website verified. `src/audit.test.ts` walks every registered Hono route: any route for a method other than `GET`, `HEAD` or `OPTIONS` that is not an audited content write fails it (the catch-all 404 and the global middleware are the reviewed exceptions), each audited write is refused without a key and on an invalid body without an audit entry, reads add none, every content write over HTTP stores its entry with the verified key and provenance, and an audit that cannot be stored rolls the content back. `src/server.test.ts` starts the real server process against an empty, unmigrated database and checks that it serves health and does not migrate. Tests need a running Postgres and `DATABASE_USER`/`DATABASE_PASSWORD`; see `packages/db/AGENTS.md`.
