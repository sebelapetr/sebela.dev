# @sebela/api

The Hono HTTP API, the only gateway to the data. Read the root `AGENTS.md` first; this file covers only what is specific to this app.

## What it is

The trust boundary of the repository. It may import `@sebela/services`, `@sebela/contracts` and `@sebela/config` (dependency table in `docs/repository-structure.md`), never `@sebela/db`; `@sebela/api-client` only in test files (`*.test.<ext>`), as a development dependency of its consumer contract tests; the import-boundaries rule rejects it anywhere else. Database settings, persistence and test databases reach it through `@sebela/services`. Routes stay thin; domain rules live in services and SQL in db.

## Commands

| Task                                   | Command                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------ |
| Migrate the database (never at start)  | `pnpm --filter @sebela/db db:migrate`                                                |
| Run in development (watch, from `src`) | `pnpm --filter @sebela/api dev`                                                      |
| Build, then run the built server       | `pnpm --filter @sebela/api start`                                                    |
| Create, list or revoke an API key      | `pnpm --silent --filter @sebela/api api-keys create <name>` / `list` / `revoke <id>` |
| Write the OpenAPI document to a file   | `pnpm --silent --filter @sebela/api openapi:export <file>` (relative to `apps/api`)  |

`dev`, `start` and `api-keys` read the process environment, then `.env.local`, `.env` and `.env.example` of the checkout (the earlier source wins). Workspace packages resolve to their built `dist/`, so each command first builds what it runs from a fresh checkout: `dev` the workspace packages the API depends on (`--filter "@sebela/api^..."`), `start` and `api-keys` those and the API itself (`--filter "@sebela/api..."`). `api-keys` talks to the database through the services, so it needs no running server and no existing key. A new key is printed once; only its hash is stored, and `list` shows metadata only. `openapi:export` builds like `start` and writes `describeApi()` as two-space JSON; it needs no database, configuration or secrets. Contributors normally run it through the root `pnpm generate:api-client`.

## Configuration

Validated once by `readApiConfig` in `src/config.ts` when the process starts; an invalid or missing variable stops it with the variable's name, never its value. No fallbacks. Placeholders and meanings are in `.env.example`.

| Variable                                                                                         | Meaning                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `API_HOST`, `API_PORT`                                                                           | Interface and port to listen on (`0` picks a free port).                                                                                                                                                 |
| `API_BODY_LIMIT_BYTES`                                                                           | Largest request body, enforced while it is received (413 beyond it).                                                                                                                                     |
| `API_TRUSTED_PROXIES`                                                                            | Comma-separated proxy addresses whose `X-Forwarded-For` is believed. Empty: forwarded headers are ignored. Exact match: a proxy reached over IPv4 on a dual-stack listener is listed as `::ffff:<ipv4>`. |
| `API_RATE_LIMIT_HEALTH`, `API_RATE_LIMIT_PUBLIC`, `API_RATE_LIMIT_PRIVATE`, `API_RATE_LIMIT_KEY` | `<max>/<seconds>` fixed-window budgets: health per client, public per client, private per client before the key is verified, and per verified key.                                                       |
| `API_RATE_LIMIT_MAX_TRACKED`                                                                     | Most callers tracked at once; the oldest window is evicted beyond it, so memory stays bounded.                                                                                                           |
| `POSTGRES_HOST`, `POSTGRES_PORT`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD`          | Database settings, validated by `readDatabaseConfig` from `@sebela/services`.                                                                                                                            |

## HTTP behaviour

- Versioned routes live under `/v1`. `GET /v1/person` is public; `POST`, `PATCH` and `DELETE /v1/person` are private. The catalogs `GET /v1/technologies`, `GET /v1/technologies/{slug}`, `GET /v1/topics` and `GET /v1/topics/{slug}` are public; `POST` on the collection and `PATCH`/`DELETE` on `{slug}` are private. The organizations follow the same pattern: `GET /v1/organizations` (ordered by name ignoring case, then slug) and `GET /v1/organizations/{slug}` are public, writes are private, and deleting an organization that other records still refer to answers 409 `conflict`. The experiences too: `GET /v1/experiences` (current roles first, then the latest start, the latest end and the slug) and `GET /v1/experiences/{slug}` are public and resolve the organization and the technologies in link order; writes are private and name the organization and technologies by slug. A create or update stores the experience and its links together or not at all; an update with `technologies` replaces every link, an omitted list keeps them. An unknown organization or technology, a repeated technology or an end before the start answers 400 `validation_failed` naming the field. Deleting an experience removes only its links; deleting a technology or an organization an experience still uses answers 409 `conflict`. The projects follow too: `GET /v1/projects` (grouped by owning experience in the experience order, then position, then slug) and `GET /v1/projects/{slug}` are public, name the owning experience by slug and resolve the technologies in link order; every experience response carries its projects, selected for the homepage or not, by position, then slug. Writes are private; a create requires an existing experience, and an update that sends `experience` moves the project to that experience, which is then its only owner. A missing or unknown experience, an invalid link, an unknown or repeated technology or an end before the start answers 400 `validation_failed` naming the field, with nothing written; a cover, case-study reference or visibility flag is an unknown field. Deleting a project removes only its links; deleting an experience that owns a project, or a technology a project uses, answers 409 `conflict`. Lists are plain JSON arrays in their documented order; a create answers 201 with `Location: /v1/<collection>/<slug>`; the slug cannot change. `GET /health`, `GET /openapi.json` and `GET /reference` are public and need no key.
- Order of checks on every route: per-client rate budget, refusal of credentials in the query string, then on private routes bearer-key verification and the per-key budget, then on routes with path parameters their schema (400 `validation_failed` naming the parameter, so an unauthenticated caller learns nothing about the path), then on body routes the content type, the size and the Zod schema. A handler never runs for a request that failed an earlier check.
- Every failure is the common `ErrorResponse` of `@sebela/contracts` (`error.code`, `error.message`, optional `error.fields`). Statuses: 400 `malformed_json` / `validation_failed` / `credentials_in_url`, 401 `unauthorized` with `WWW-Authenticate: Bearer`, 404 `not_found`, 409 `conflict`, 413 `payload_too_large`, 415 `unsupported_media_type`, 429 `rate_limited` with `Retry-After`, 500 `internal_error` without details.
- Every response carries `X-Content-Type-Options: nosniff`; CORS is not enabled. Request and error logs are redacted: no bearer token or `sebela_` key reaches them.
- `onWrite` in `createApp` is the attachment point for successful-write notifications. The default is a no-op; a failing notifier is logged and never fails the write.

## Adding a route

1. Add or extend the contract schemas in `@sebela/contracts` and the service operation in `@sebela/services`, each test-first.
2. Add a `defineRoute` entry to the owning module (its `index.ts` or a private file it composes) with its access, path-parameter and body schemas, success and errors, and register the module in `app.ts`. OpenAPI and the route-registry property test pick it up from there; a private route needs valid route parameters in the property test.
3. Regenerate the client with `pnpm generate:api-client` from the repository root and commit `packages/api-client/src/generated/`; CI's drift check fails otherwise.
4. Extend `src/client.test.ts` with the new or changed operation's success and documented errors, through the client.
5. Update this module map and the OpenAPI expectations.

## Tests

`pnpm --filter @sebela/api test`. Vitest against real Postgres: each test file creates its own temporary migrated database through `@sebela/services/testing` with small fictional fixtures. Rate-limit tests use a controlled clock. `src/server.test.ts` starts the real server process against an empty, unmigrated database and checks that it serves health and does not migrate. Tests need a running Postgres and `DATABASE_USER`/`DATABASE_PASSWORD`; see `packages/db/AGENTS.md`.
