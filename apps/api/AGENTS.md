# @sebela/api

The Hono HTTP API, the only gateway to the data. Read the root `AGENTS.md` first; this file covers only what is specific to this app.

## What it is

The trust boundary of the repository. It may import `@sebela/services`, `@sebela/contracts` and `@sebela/config` (dependency table in `docs/repository-structure.md`), never `@sebela/db`; `@sebela/api-client` only in test files (`*.test.<ext>`), as a development dependency of its consumer contract tests; the import-boundaries rule rejects it anywhere else. Database settings, persistence and test databases reach it through `@sebela/services`. Routes stay thin; domain rules live in services and SQL in db.

## Commands

| Task                                   | Command                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------- |
| Migrate the database (never at start)  | `pnpm --filter @sebela/db db:migrate`                                                 |
| Run in development (watch, from `src`) | `pnpm --filter @sebela/api dev`                                                       |
| Build, then run the built server       | `pnpm --filter @sebela/api start`                                                     |
| Create, list or revoke an API key      | `pnpm --silent --filter @sebela/api api-keys create <name>` / `list` / `revoke <id>`  |
| Write the OpenAPI document to a file   | `pnpm --silent --filter @sebela/api openapi:export <file>` (relative to `apps/api`)   |
| Load a seed folder (demo by default)   | `pnpm --silent --filter @sebela/api seed [folder]` (relative to where it is started)  |
| Seed only an empty profile             | `pnpm --silent --filter @sebela/api seed --if-empty [folder]`                         |
| Prepare or remove a worktree's storage | `pnpm --silent --filter @sebela/api storage prepare <worktree>` / `remove <worktree>` |
| Serve a seed folder for browser tests  | `pnpm --silent --filter @sebela/api serve:e2e <folder>` (test support; see below)     |

`dev`, `start`, `api-keys`, `seed` and `storage` read the process environment, then `.env.local`, `.env` and `.env.example` of the checkout (the earlier source wins). Workspace packages resolve to their built `dist/`, so each command first builds what it runs from a fresh checkout: `dev` the workspace packages the API depends on (`--filter "@sebela/api^..."`), `start`, `api-keys` and `seed` those and the API itself (`--filter "@sebela/api..."`). `api-keys` talks to the database through the services, so it needs no running server and no existing key. A new key is printed once; only its hash is stored, and `list` shows metadata only. `seed` loads the fictional demo seed, or the given seed folder, through the services in-process (format and rerun rules: `packages/db/seed/README.md`); it needs a migrated database and the media settings, but no running server and no API key, and prints counts and refusals by file and field, never content or the folder's path. `seed --if-empty` loads only into a profile that holds nothing and otherwise prints that the seed was skipped; worktree setup uses it, so rerunning setup never overwrites edited content. `storage prepare <worktree>` creates the worktree's storage folder `<environment>/<worktree>/` with an owner marker naming `<worktree>`, or reuses the folder that worktree already holds; `storage remove <worktree>` deletes the files of that folder only when the marker names the same worktree. Both refuse `production`, a missing `STORAGE_WORKTREE`, a folder of another owner and an unmarked folder that holds files, and print neither keys, paths nor credentials. `serve:e2e` is test support for the browser tests of the website (`apps/web/AGENTS.md`, Tests), not a server for content: it builds like `dev`, creates a temporary database (as the tests do, with the checkout's role), migrates it, loads the given seed folder into it with local storage in a temporary folder below the checkout's `.tmp/`, created when a clean checkout has none (environment `test`, its media addresses on its own `API_PORT`), serves the API from `src` on `API_HOST` and `API_PORT`, and on `SIGTERM` or `SIGINT` drops the database and removes the folder. It never touches the checkout's database, storage or the demo seed; it is excluded from the build. Its interface to the website's browser tests is the file itself: `apps/web/e2e/stack.ts` starts `node --import tsx src/cli/e2e-server.ts <folder>` in `apps/api`, without the script's build step, because `pnpm test:e2e` has built the dependencies once and the tests start several servers at the same time. Moving or renaming the file, or changing its argument, changes that caller in the same change. `openapi:export` builds like `start` and writes `describeApi()` as two-space JSON; it needs no database, configuration or secrets. Contributors normally run it through the root `pnpm generate:api-client`.

## Container stack

The main checkout can run the API in Docker: the profile `api` of the root `compose.yaml`, built from `Dockerfile` here (context: the repository root, allowlisted by the root `.dockerignore`). Worktrees run the API on the host with the commands above.

| Task                                            | Command (repository root)                                                                                   |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Build, migrate and start; returns once healthy  | `pnpm stack:up`                                                                                             |
| Load the demo seed                              | `pnpm stack:seed`                                                                                           |
| Load a private seed folder outside the checkout | `docker compose --profile api run --rm --volume <absolute folder>:/seed:ro api node dist/cli/seed.js /seed` |
| Create, list or revoke an API key               | `pnpm --silent stack:api-keys create <name>` / `list` / `revoke <id>`                                       |
| Logs                                            | `pnpm stack:logs`                                                                                           |
| Stop and remove the API containers              | `pnpm stack:down` (Postgres keeps running for the worktrees)                                                |
| Stop everything, keep data and media            | `docker compose --profile api down` (a plain `docker compose down` leaves the profile's containers running) |
| Delete the data and the media as well           | `docker compose --profile api down --volumes`                                                               |

- **Order.** `migrate` (`node /app/packages/db/dist/cli/migrate.js`, the same image) starts once Postgres is healthy and applies the committed migrations; `api` starts only when it has exited with 0. A failed migration leaves the API down; the server itself never migrates. Running `stack:up` again re-runs `migrate`, which applies only new migrations.
- **Content.** Neither a start nor a restart seeds, resets or deletes content. The seed and the first key are separate, explicit one-off commands in a container of the `api` service; the key is printed once to the terminal, never to the service logs. The seed's rerun rules are those of `packages/db/seed/README.md`.
- **Configuration.** The containers get the same validated settings as the host API from the checkout's environment (`.env`), forwarded variable by variable in `compose.yaml`. None is required by Compose, so the Postgres-only commands of a checkout work without them: a missing one reaches the container empty, and `readApiConfig`, `readMediaConfig` or the migration's database settings stop it with its name. `pnpm stack:up` first refuses to start without `API_HOST` and `API_PORT`, the host address and port the API is published on; empty ones would publish it on every interface on a random port, so start the stack with `pnpm stack:up`, not a plain `docker compose --profile api up`. Four values are part of the declaration: inside the network the API reaches Postgres by its service name on the container port, and listens on every interface of its container on its own container port (`8080`). The database, role and password are the checkout's `DATABASE_*`.
- **Media.** `STORAGE_LOCAL_ROOT` is the folder of the named volume `api-media` (`/var/lib/sebela/media`), owned by the image's unprivileged `node` user; the key namespaces of `STORAGE_ENVIRONMENT` and `STORAGE_WORKTREE` apply below it. Uploads survive restarts and rebuilt containers and are deleted only with the volume. `STORAGE_PUBLIC_BASE_URL` stays the published address.
- **Rate limits.** Requests from the host arrive through Docker's network, so every local caller shares one client address. Development only.
- **Image.** Production dependencies, the built `dist/` of the API and its workspace packages, the committed migrations and the fictional demo seed. No environment file, credentials or personal content; a private seed is mounted at run time. The runtime stage lists the manifest of every workspace package; add a new package's `package.json` there. The base image is pinned by tag and digest.
- **Smoke check.** `pnpm test:api-stack` (`scripts/checks/api-stack.e2e.mjs`, CI job `API stack smoke`) checks all of the above in a disposable Compose project; see `docs/testing.md`, "CI".

## HTTP behaviour

- Versioned routes live under `/v1`. `GET /v1/person` is public; `POST`, `PATCH` and `DELETE /v1/person` are private. The catalogs `GET /v1/technologies`, `GET /v1/technologies/{slug}`, `GET /v1/topics` and `GET /v1/topics/{slug}` are public; `POST` on the collection and `PATCH`/`DELETE` on `{slug}` are private. The organizations follow the same pattern: `GET /v1/organizations` (ordered by name ignoring case, then slug) and `GET /v1/organizations/{slug}` are public, writes are private, and deleting an organization that other records still refer to answers 409 `conflict`. The experiences too: `GET /v1/experiences` (current roles first, then the latest start, the latest end and the slug) and `GET /v1/experiences/{slug}` are public and resolve the organization and the technologies in link order; writes are private and name the organization and technologies by slug. A create or update stores the experience and its links together or not at all; an update with `technologies` replaces every link, an omitted list keeps them. An unknown organization or technology, a repeated technology or an end before the start answers 400 `validation_failed` naming the field. Deleting an experience removes only its links; deleting a technology or an organization an experience still uses answers 409 `conflict`. The projects follow too: `GET /v1/projects` (grouped by owning experience in the experience order, then position, then slug) and `GET /v1/projects/{slug}` are public, name the owning experience by slug and resolve the technologies in link order; every experience response carries its projects, selected for the homepage or not, by position, then slug. Writes are private; a create requires an existing experience, and an update that sends `experience` moves the project to that experience, which is then its only owner. A missing or unknown experience, an invalid link, an unknown or repeated technology or an end before the start answers 400 `validation_failed` naming the field, with nothing written; a cover, case study or visibility flag is an unknown field. Deleting a project removes only its links; deleting an experience that owns a project, a technology a project uses, or a project that has a case study answers 409 `conflict`. Every project response, also inside an experience, carries its `caseStudy` (`null` without one). A project has at most one case study, addressed by the project's stable slug at `/v1/projects/{slug}/case-study`: `GET` is public, `POST`, `PATCH` and `DELETE` are private. `GET`, `PATCH` and `DELETE` answer 404 `not_found` for an unknown project or a project without a case study; `POST` answers 404 for an unknown project and 409 `conflict` when the project already has one, also for competing creates, and a create answers 201 with `Location: /v1/projects/<slug>/case-study`. The `role` (plain text, at most 500 characters) and the Markdown `body` (at most 50,000 characters, trimmed, otherwise stored as written, never rendered to HTML) are strict fields. Deleting the case study leaves its project. The explorations are outside the career timeline: `GET /v1/explorations` (by position, then slug) and `GET /v1/explorations/{slug}` are public, return the `built`/`tested`/`designed` status exactly as stored and resolve the technologies and topics in link order; writes are private and name the technologies and topics by slug. A create or update stores the exploration and its links together or not at all; a sent `concepts`, `technologies` or `topics` list replaces that list, an omitted one keeps it. An unknown status, an unknown or repeated technology or topic or an end before the start answers 400 `validation_failed` naming the field; an experience, project or visibility flag is an unknown field. Deleting an exploration removes only its links; deleting a technology or a topic an exploration still uses answers 409 `conflict`. The services follow too: `GET /v1/services` (position, then slug) and `GET /v1/services/{slug}` are public and return the name, summary, audience, deliverable and the evidence in its stored order, each piece typed by `kind`: `project` (slug, name, summary and owning experience), `exploration` (slug, name, summary and the status exactly as stored) or `link` (label and a path within the site). Writes are private and name projects and explorations by slug; a create or update stores the service and its evidence together or not at all, an update with `evidence` replaces all evidence in its order (an empty list removes it), an omitted list keeps it. An unknown or repeated project or exploration, an unsupported kind, or a link that is not a path within the site (a scheme, `//`, whitespace or a backslash) answers 400 `validation_failed` naming `evidence`, with the previous service and evidence intact. Deleting a service removes only its evidence; deleting a project or an exploration a service names answers 409 `conflict`. The education records follow too: `GET /v1/education` (position, then slug) and `GET /v1/education/{slug}` are public and return the kind (`school`, `course`, `certification` or `milestone`) exactly as stored, the title, institution, description and period; writes are private. A period needs at least one date: a start alone is ongoing learning, an end alone a completion on that day, and the end is never before the start, checked on the resulting record when an update sends only one date. An unknown kind, text out of bounds, a period without a date (naming `startedOn` and `endedOn`) or an end before the start (naming `endedOn`) answers 400 `validation_failed`. Nothing refers to an education record, so deleting one never conflicts. The testimonials follow too: `GET /v1/testimonials` (grouped by experience in the experience order, then position, then slug) and `GET /v1/testimonials/{slug}` are public, name the experience each belongs to by slug and carry the optional author photo as `authorPhotoId` (a media identifier or `null`); every experience response carries its testimonials by position, then slug, beside its organization and projects. Writes are private; a create requires an existing experience, and an update that sends `experience` moves the testimonial to that experience. A missing or unknown experience or a quote, author name or author role out of bounds answers 400 `validation_failed` naming the field, with nothing changed. Deleting a testimonial never conflicts and keeps its author photo; deleting an experience that has a testimonial answers 409 `conflict`. The current focus follows too: `GET /v1/current-focus` (by position, then slug) and `GET /v1/current-focus/{slug}` are public and resolve each entry's optional project (slug, name and experience, or `null`) and its topics in link order. Writes are private; `project` and `topics` name existing records by slug, an omitted link or project means none on create, and on update a slug replaces the project, `null` clears the project or the link, a sent `topics` list replaces every link and an omitted field keeps it. An unknown project, unknown or repeated topics, a link that is not `http` or `https`, or text out of bounds answers 400 `validation_failed` naming the field, with nothing changed. Deleting a focus entry never conflicts and keeps its project and topics; deleting a project or topic a focus entry links answers 409 `conflict`. The media are addressed by identifier: `GET /v1/media` (newest first, then identifier) and `GET /v1/media/{id}` are public and return the storage key, the type the content proved, the byte size, the image dimensions (`null` for a PDF), the alt text and a `url` computed from `STORAGE_PUBLIC_BASE_URL`, never stored; `url` is `null` for a record whose key the configured storage cannot address (stored under another environment or worktree prefix), which stays listed and readable while its file route answers 404. `POST /v1/media` is private and takes `multipart/form-data` with exactly one file part `file` and an optional `altText`; it accepts PNG, JPEG, WebP and PDF within `MEDIA_MAX_BYTES` and `MEDIA_MAX_IMAGE_DIMENSION`, answers 201 with `Location: /v1/media/<id>`, 415 for a body that is not a multipart form or a file whose content, declared type or extension disagree, 413 beyond the size limit and 400 `validation_failed` on `file` for a missing, repeated, empty, malformed or oversized image. The API generates the key; the file name never chooses it. `PATCH /v1/media/{id}` changes or clears the alt text only; `DELETE /v1/media/{id}` answers 409 `conflict` while the person, an organization, a project or a testimonial refers to the media, and otherwise removes the record and the file. `GET /v1/media/files/{key}` is public and serves a recorded local file inline with its proved type and `nosniff`; images carry `Content-Security-Policy: default-src 'none'; sandbox` and `Content-Disposition: inline`, a PDF carries `default-src 'none'` without `sandbox` (browser PDF viewers refuse sandboxed documents) and `Content-Disposition: inline; filename="<uuid>.pdf"`; a key with characters a generated key cannot contain, or one that names no recorded file, answers 404. Media are attached through the owning record's update: `photoId` and `cvPdfId` of the person, `logoId` of an organization, `coverId` of a project and `authorPhotoId` of a testimonial (also on its create) name media by identifier, and `null` clears them; unknown media or the wrong kind (a PDF as an image, an image as the CV) answers 400 `validation_failed` naming the field, with nothing written. The current CV PDF is uploaded as prepared; the API never generates it. Lists are plain JSON arrays in their documented order; a create answers 201 with `Location: /v1/<collection>/<slug>`; the slug cannot change. `GET /health`, `GET /openapi.json` and `GET /reference` are public and need no key.
- `GET /v1/cv` is public and read-only; no method writes to it (other methods answer 404). It returns the CV data assembled from the stored profile on every request: the person (contacts, links, summary), the experiences selected for the CV (`inCv`) in the experience order, the technology catalog grouped into `primary.core`, `primary.aiEngineeringFocus` and `secondary`, every education record, the explorations in a section of their own with their stored `built`/`tested`/`designed` status, and the current CV PDF (`cvPdf`, its `url` from the storage, `null` without a configured storage or when the storage cannot address the key). Absent sections are empty lists and an absent PDF is `null`; while there is no person it answers 404 `not_found` and creates nothing. It is CV data, not the CV page, and it never generates or updates the PDF.
- Order of checks on every route: per-client rate budget, refusal of credentials in the query string, then on private routes bearer-key verification and the per-key budget, then on routes with path parameters their schema (400 `validation_failed` naming the parameter, so an unauthenticated caller learns nothing about the path), then on body routes the content type, the size and the Zod schema (on the upload route the multipart form, its file part and its other fields). Nothing reaches storage or the database before these checks pass, so a refused or unauthenticated upload leaves neither a file nor a record. A handler never runs for a request that failed an earlier check.
- Every failure is the common `ErrorResponse` of `@sebela/contracts` (`error.code`, `error.message`, optional `error.fields`). Statuses: 400 `malformed_json` / `validation_failed` / `credentials_in_url`, 401 `unauthorized` with `WWW-Authenticate: Bearer`, 404 `not_found`, 409 `conflict`, 413 `payload_too_large`, 415 `unsupported_media_type`, 429 `rate_limited` with `Retry-After`, 500 `internal_error` without details.
- Every response carries `X-Content-Type-Options: nosniff`; CORS is not enabled. Request and error logs are redacted: no bearer token or `sebela_` key reaches them.
- Media cleanup: an upload whose record cannot be written removes its file again; a deleted record whose file cannot be removed still answers 204. A removal that fails is logged by `logCleanupFailure` as one redacted line with the operation, the key and the error name and message (no stack, file contents or credentials); the file is then an orphan to remove by hand under that key. A successful response never names media whose file is missing.
- `onWrite` in `createApp` is the attachment point for successful-write notifications. The default is a no-op; a failing notifier is logged and never fails the write.

## Adding a route

1. Add or extend the contract schemas in `@sebela/contracts` and the service operation in `@sebela/services`, each test-first.
2. Add a `defineRoute` entry to the owning module (its `index.ts` or a private file it composes) with its access, path-parameter and body schemas, success and errors, and register the module in `app.ts`. OpenAPI and the route-registry property test pick it up from there; a private route needs valid route parameters in the property test.
3. Regenerate the client with `pnpm generate:api-client` from the repository root and commit `packages/api-client/src/generated/`; CI's drift check fails otherwise.
4. Extend `src/client.test.ts` with the new or changed operation's success and documented errors, through the client.
5. Update this module map and the OpenAPI expectations.

## Tests

`pnpm --filter @sebela/api test`. Vitest against real Postgres: each test file creates its own temporary migrated database through `@sebela/services/testing` with small fictional fixtures. Rate-limit tests use a controlled clock. Media tests (`src/media.test.ts`) store files in a temporary local storage root per test file (`openTestBackend` in `src/test-support.ts`) with fictional sample files from `@sebela/services/testing`, and cover upload to attachment to download, alt-text updates, refused deletes, malformed and misleading files, excessive size and dimensions, unauthenticated uploads leaving nothing behind and traversal attempts in file names and keys. `src/server.test.ts` starts the real server process against an empty, unmigrated database and checks that it serves health and does not migrate. Tests need a running Postgres and `DATABASE_USER`/`DATABASE_PASSWORD`; see `packages/db/AGENTS.md`.
