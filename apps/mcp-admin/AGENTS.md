# @sebela/mcp-admin

The private administrative MCP server: an owner's agent connects to it with an API key and reads and writes content through the content API. Read the root `AGENTS.md` first; this file covers only what is specific to this app. Phase PRD: `.plan/05-mcp-admin/prd.md`; security cases: `.plan/05-mcp-admin/security.md`; eval catalogue: `.plan/05-mcp-admin/evals.md`.

## What it is

- **Hono** supplies the HTTP surface and its protections; the **official MCP TypeScript SDK** supplies the protocol (`@modelcontextprotocol/server` 2.4.0 with `createMcpHandler`, `@modelcontextprotocol/hono` 2.0.2 for Origin validation, `hono` 4.13.18, `@hono/node-server` 2.1.8; the tests use `@modelcontextprotocol/client` 2.4.0). Versions are pinned exactly; upgrade them together. `hono` and `@hono/node-server` are shared with the API through the workspace catalog (`pnpm-workspace.yaml`), so both apps move together. There is no hand-written JSON-RPC and no REST route per tool: one endpoint, `/mcp`, serves the Streamable HTTP transport statelessly (a fresh MCP server per request, no sessions).
- It reaches data only through the content API over HTTP, with the generated `@sebela/api-client`. It never imports `@sebela/db` or `@sebela/services` (the import-boundaries lint rule enforces this) and has no database, migration or storage setting.
- **It stores no API key.** The caller sends `Authorization: Bearer <api-key>`; MCP Admin checks that key with the API's private `GET /v1/authentication` before anything else, on every request (discovery included, and every operation on an existing connection), and forgets it when the request ends. A revoked key fails on its next operation. Keys are created and revoked with the API's existing `api-keys` command (`apps/api/AGENTS.md`); there is no second key store, login, JWT or OAuth.
- Private first-party API calls (writes and the audit read) carry the caller's key and writes a provenance label; public reads carry neither. The API destination is configuration only (`MCP_ADMIN_API_URL`); no caller or tool argument chooses it. Redirects from the API are never followed.

## Tools

Thirteen tools: seven content tools over one fixed entity-to-operation registry (`src/modules/content/registry.ts`). The 23 entities are the content of phases 2 and 4, named as the API's audit names them: `person`, `technology`, `topic`, `organization`, `experience`, `project`, `case-study`, `testimonial`, `exploration`, `service`, `education`, `current-focus`, `roadmap-area`, `roadmap-module`, `roadmap-resource`, `roadmap-book`, `roadmap-event`, `roadmap-project-idea`, `roadmap-followed-source`, `roadmap-glossary-term`, `roadmap-diary`, `roadmap-time-entry` and `media`. Authentication, API keys, the audit store, conversations and knowledge staging are not entities and cannot be named.

| Tool             | Arguments                                               | Result                                                                                                                                                                  |
| ---------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `describe`       | `{ entity }`                                            | The entity's operations, how its records are identified, the JSON Schema of its create and update fields (from `@sebela/contracts`) and its relationships. No API call. |
| `list`           | `{ entity }`                                            | Every record through the public list route (for roadmap areas, modules and resources: the roadmap tree). No filter, query or limit.                                     |
| `get`            | `{ entity, id? }`                                       | One record through its public route, or `not_found`. The person has no `id`.                                                                                            |
| `save`           | `{ entity, action: "create" \| "update", id?, fields }` | Creates a record, or patches only the given fields of one; `{ entity, id, action, record }`.                                                                            |
| `delete`         | `{ entity, id }`                                        | Deletes exactly that one record; `{ entity, id, action: "deleted" }`.                                                                                                   |
| `recent_changes` | `{}`                                                    | `{ changes }`: the newest audited content changes, newest first, at most 20 (`GET /v1/audit/changes` with the caller's key).                                            |
| `upload`         | `{ fileName, contentBase64, altText? }`                 | Uploads the caller's file as new media (`POST /v1/media`, multipart); `{ entity: "media", id, action: "created", record }`. The `id` is what `save` then attaches.      |

What each entity supports is stated by `describe` and enforced before any call (`unsupported_operation`): the person has get, create and update (no list, no delete: it is the one record every page and the CV page are rendered from, so deleting it would take the whole profile off the site, and there is no undo; only a direct authenticated `DELETE /v1/person` can remove it); `case-study` is named by its project's slug, also on create, and has no list; `roadmap-diary` writes a day's notes with an upserting `update` (no create) and lists the days with their time entries; `roadmap-time-entry` has create, update and delete and is read through `roadmap-diary`; `media` has list, get, metadata update and delete, and new files arrive only through `upload`. The learning tasks are the tools below. There is no FAQ entity: the API has no FAQ route yet (the roadmap glossary is `roadmap-glossary-term`).

### Learning task tools

Six task tools over the learning module (`src/modules/learning`), for the diary-entry and add-event workflows. They read and write only through the content module, so its rules (strict arguments, one provenance-tagged write, reconciliation) apply to each write.

| Tool                  | Arguments                                                                                                      | Result                                                                                                                                                                                                                                                                                                                         |
| --------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `find_resource`       | `{ query }`                                                                                                    | `{ candidates, truncated }`: resources whose name or slug contains the query (case and diacritics ignored), or, for an `http(s)` query, whose stored link equals it (case and a trailing slash ignored); each with its type, status, link, book, module and area; at most 20. Reads the roadmap tree; never requests the link. |
| `add_resource`        | `{ module, name, type, link?, slug?, status?, estimatedMinutes? }`                                             | Creates the resource last in an existing module. An unknown module is `not_found`; the same stored link anywhere or the same name in the module is `conflict` with `candidates`; a taken or underivable slug is a `field` error on `slug`. Nothing is written in those cases.                                                  |
| `set_resource_status` | `{ resource, status, startedAt?, finishedAt? }`                                                                | Patches the canonical status (`planned`, `in-progress`, `completed`, `paused`, `skipped`; "started" is `in-progress`) and only the dates given, sent as UTC. No date is set for the owner.                                                                                                                                     |
| `log_session`         | `{ resource \| book \| event, startedAt, endedAt, notes? }`                                                    | One `POST /v1/roadmap/sessions` with provenance `mcp-admin/session/<nonce>`; `{ dates }`, or `{ dates, reconciled: true }` after a lost answer found in the audit. Exactly one target and an end after the start are checked first; a book is logged on its linked resource (`field` on `book` without one).                   |
| `save_event`          | `{ action, slug?, name?, kind?, organizer?, place?, online?, link?, takeaways?, startsOn?, endsOn?, topics? }` | `create` needs name, kind and the inclusive `startsOn`/`endsOn` (a `field` error names each missing one), derives the slug `<name>-<year>` and refuses the same name in the same year (`conflict`). `update` needs `slug` and sends only the given fields. The dates add no time.                                              |
| `save_book`           | `{ action, slug?, title?, author?, description?, pages?, year?, startedOn?, endedOn?, summary? }`              | `create` needs a title, derives the slug and refuses the same title (`conflict`); `update` needs `slug`. There is no `status`: a book's state comes from `startedOn` and `endedOn`.                                                                                                                                            |

When a task creates a record and a later task fails, the result is partial: the created record stays and both outcomes are reported; nothing is deleted or resent. `uncertain` from `log_session` means the session may be logged: read the diary day or `recent_changes` before anything else.

Rules the content module enforces:

- **Arguments are strict.** An unknown key, an entity outside the registry, a non-string or missing `id` and any path, query, filter, operator or credential are refused before any request. `id` is checked against the entity's contract (slug, UUID or `YYYY-MM-DD`), so a pattern, list or traversal is a `field` error on `id`; a new slug-named record takes its slug in `fields.slug`, never in `id`.
- **Fields are checked locally** with the entity's create or update contract before anything is sent: a protected or derived field (`createdAt`, `updatedAt`, `slug` on update, a nested record), an unknown field, a wrong type, a missing required field or an empty update is a `field` error naming each path, and nothing is written. Only the given `fields` are sent; there is no read-modify-write of other fields, so a concurrent edit of another field is kept.
- **Read before change.** An update or delete reads the record through its public route first and writes nothing when it is missing (`not_found`). The diary upsert and the time entry (no read route) skip this.
- **One write, never replayed.** Before writing, MCP Admin reads the audit's newest id; without it, it does not write (`unavailable`). The write carries `sebela-provenance: mcp-admin/save/<nonce>`, `mcp-admin/delete/<nonce>`, `mcp-admin/upload/<nonce>` or `mcp-admin/session/<nonce>` (12 random hex digits per write). When the answer is lost (network error, 5xx or an undocumented answer), it reads the audit again: an entry newer than that id with the same provenance and method is the write's own, reported as success with `reconciled: true`; otherwise the result is `uncertain`. A refusal of a save, delete or session (401, 403, 413, 415, 429) is `unavailable`: nothing changed. For `upload`, 413 and 415 are `field` errors on `file` instead (next rule); 401, 403 and 429 stay `unavailable`.
- **Upload only the caller's bytes.** `upload` takes the file's bytes as canonical, padded base64 in the call (a path, an address, unpadded or non-base64 text, or an empty file is a `field` error on `contentBase64`) and a plain file name (no `/`, `\\`, `:`, control character or leading dot, at most 255 characters; otherwise a `field` error on `fileName`), both before any request. It reads no path, fetches no address and never reaches storage. The bytes go once to the API's `POST /v1/media` as a multipart `file` with a generic declared type and the optional `altText`, with `sebela-provenance: mcp-admin/upload/<nonce>`; the API proves the type from the content and the name's extension, checks size and image dimensions, stores the file with its configured driver and audits it. Its refusals (400 malformed or empty, 413 too large, 415 unsupported or contradicting type) are `field` errors on `file`, and nothing is stored; 401, 403 and 429 are `unavailable`; a storage failure (500) or a lost answer is reconciled through the audit like any write, else `uncertain`, never retried. The result carries the media record, never the bytes. **The whole call is bounded by `MCP_ADMIN_BODY_LIMIT_BYTES`**: base64 grows a file by a third, so a body limit of 65536 bytes admits a file of roughly 48 KiB; larger files are refused with 413 before the tool runs.
- **Attach a returned media ID.** A media field that `describe` lists is set with `save` to the `id` a successful upload returned: the person's photo (`photoId`) or CV PDF (`cvPdfId`), or an organization's logo (`logoId`, with the organization's `id`). The API refuses an ID that names no media or media of the wrong kind (a PDF as the photo or logo, an image as the CV). A refused or uncertain upload attaches nothing, so the current reference stays. The CV PDF is a file the owner prepares; nothing here generates one.
- **Delete one record.** No bulk delete, delete by filter, cascading clean-up or undo. The API's dependency protection answers 409, reported as `conflict` with the API's reason.

Errors are `isError` results whose text is `{ "error": { "code", "message", "fields"?, "candidates"? } }`. Codes: `field` (with `fields: [{ path, message }]`, from the local check or the API's 400), `conflict`, `not_found` (`No person is stored yet.` for the person), `unavailable` (`The content API is unavailable; retry later.`), `uncertain` and `unsupported_operation`. Upstream text reaches a result only as the API's field and conflict messages, with key-shaped and bearer text redacted and the message cut at 500 characters; a key or a stack never does.

Annotations: `describe`, `list`, `get` and `recent_changes` are `readOnlyHint: true`; `find_resource` is `readOnlyHint: true`; `save` and the five learning writes are `readOnlyHint: false, destructiveHint: false, idempotentHint: false`; `delete` is `destructiveHint: true, idempotentHint: false`; `upload` is `readOnlyHint: false, destructiveHint: false, idempotentHint: false, openWorldHint: false`. **Annotations are hints to the client, not proof of human consent.** A custom client with a valid key can exercise every content permission of that key; the approval of writes and deletes is the supported client's configuration (below), and authorization is the API's. Each committed write reaches the website through the API's existing post-write invalidation; MCP Admin adds no cache or event path.

## Request order

Every request passes, in order: the log line (method, path with key-like segments redacted, status; never a header or body), `GET /health` (no key, no API call), the Host check (`MCP_ADMIN_ALLOWED_HOSTS`, else 403 `forbidden`), Origin validation (`MCP_ADMIN_ALLOWED_ORIGINS`; a request without Origin passes, a disallowed one is refused), the gate, the body limit (413 `payload_too_large`), then the MCP handler. The gate (`src/modules/gate`):

1. the pre-authentication budget per client address (429 `rate_limited` with `Retry-After`); `X-Forwarded-For` counts only from `MCP_ADMIN_TRUSTED_PROXIES`. Behind an SSH tunnel every caller arrives from the loopback address, so all tunnel callers share one pre-authentication budget;
2. credentials in the URL (400 `credentials_in_url`);
3. the Bearer key (401 `unauthorized` with `WWW-Authenticate: Bearer`, the same answer for a missing, malformed, unknown, revoked or foreign token);
4. the key check against the API within `MCP_ADMIN_TIMEOUT_MS` (401 for an invalid key; 503 `unavailable` for a timeout, an error, a redirect or a malformed answer: it fails closed);
5. the per-key budget, counted by the key's SHA-256 digest (429);
6. a concurrency slot (503 `busy` beyond `MCP_ADMIN_MAX_CONCURRENT`), held until the response body is fully sent, cancelled or the request is aborted or times out.

Rate limits are fixed windows in memory, per process, bounded by `MCP_ADMIN_RATE_LIMIT_MAX_TRACKED`. Each request's key check is a private API request from MCP Admin's own address, so it also counts against the API's `API_RATE_LIMIT_PRIVATE` budget for that address: keep `MCP_ADMIN_RATE_LIMIT_PREAUTH` within it.

## Configuration

Every setting is required and documented in `.env.example`; a missing or invalid one stops the process with its name, never its value. Worktree setup writes `MCP_ADMIN_PORT` and `MCP_ADMIN_API_URL` (the worktree's own API) into `.env.local`.

| Variable                                                   | Meaning                                                                               |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `MCP_ADMIN_HOST`, `MCP_ADMIN_PORT`                         | Interface and port it listens on. Keep the host on loopback.                          |
| `MCP_ADMIN_API_URL`                                        | The content API's base address, http or https without credentials, query or fragment. |
| `MCP_ADMIN_ALLOWED_HOSTS`                                  | Host names a request's `Host` may name.                                               |
| `MCP_ADMIN_ALLOWED_ORIGINS`                                | Host names a present `Origin` may name; empty refuses every browser request.          |
| `MCP_ADMIN_TRUSTED_PROXIES`                                | Proxies whose `X-Forwarded-For` is believed.                                          |
| `MCP_ADMIN_BODY_LIMIT_BYTES`                               | Largest request body.                                                                 |
| `MCP_ADMIN_TIMEOUT_MS`                                     | Longest a request may take, its API calls included.                                   |
| `MCP_ADMIN_MAX_CONCURRENT`                                 | Most requests in progress at once.                                                    |
| `MCP_ADMIN_RATE_LIMIT_PREAUTH`, `MCP_ADMIN_RATE_LIMIT_KEY` | `<requests>/<seconds>` per client address before the key check, and per verified key. |
| `MCP_ADMIN_RATE_LIMIT_MAX_TRACKED`                         | Most callers tracked across both budgets.                                             |

## Container

The profile `mcp-admin` of `compose.yaml` adds the service `mcp-admin`, built from `apps/mcp-admin/Dockerfile` (MCP Admin, the API client and the contracts only; unprivileged `node` user; no environment file). Start it with the API: `docker compose --profile api --profile mcp-admin up --detach --wait`. It listens on the container port 8080, reaches the API as `http://api:8080`, is published on `MCP_ADMIN_HOST`:`MCP_ADMIN_PORT` (loopback) and has a health check on `/health`, also declared as the image's `HEALTHCHECK`. The production composition (`infra/README.md`) publishes no MCP Admin port. Its environment holds only `MCP_ADMIN_*` settings.

Networks: `database` joins Postgres, the migration and the API; `content` joins the API and the website; `admin` joins the API and MCP Admin. MCP Admin has no route to Postgres or the website, the website has none to MCP Admin, and the website holds no API key. The repository check `scripts/checks/compose-policy.test.mjs` verifies this policy from `docker compose config` with the example settings, without building or starting an image (D22, D23); it runs with the root checks on every change, so a change to `compose.yaml`, `.dockerignore` or `.env.example` alone still runs it. The public edge (reverse proxy, TLS, which routes it exposes) is phase 10's; it must expose neither MCP Admin nor private API routes.

## Connecting a client

MCP Admin is never published on a public address. From another machine, open an SSH tunnel to the host's loopback port and connect to the local end:

```bash
ssh -N -L 127.0.0.1:<local-port>:127.0.0.1:<MCP_ADMIN_PORT> <user>@<host>
```

Create a key for the client with `pnpm --silent stack:api-keys create <name>` (or the API's `api-keys` command in a worktree) and keep it in the client's environment, never in a tracked file. Claude Code, project `.mcp.json` (HTTP transport; `${...}` is expanded from the client's environment):

```json
{
  "mcpServers": {
    "sebela-admin": {
      "type": "http",
      "url": "http://127.0.0.1:<local-port>/mcp",
      "headers": { "Authorization": "Bearer ${SEBELA_ADMIN_API_KEY}" }
    }
  }
}
```

Approval: allow the read tools and require a prompt for anything else, for example in the client's `settings.json` `"permissions": { "allow": ["mcp__sebela-admin__describe", "mcp__sebela-admin__list", "mcp__sebela-admin__get", "mcp__sebela-admin__recent_changes", "mcp__sebela-admin__find_resource"], "ask": ["mcp__sebela-admin__save", "mcp__sebela-admin__delete", "mcp__sebela-admin__upload", "mcp__sebela-admin__add_resource", "mcp__sebela-admin__set_resource_status", "mcp__sebela-admin__log_session", "mcp__sebela-admin__save_event", "mcp__sebela-admin__save_book"] }`. Every write tool, `upload` included, must stay on `ask`. The owner's agent workflows are the skills `.claude/skills/update-profile/SKILL.md` (content, and uploading and attaching a photo, an organization logo or the CV PDF), `.claude/skills/update-cv/SKILL.md` (changing facts the CV shows, with a reminder to review or replace the manually prepared CV PDF), `.claude/skills/diary-entry/SKILL.md` and `.claude/skills/add-event/SKILL.md`; the owner's global diary-entry skill of the old application stays untouched until launch.

Limitations: only clients that send a static `Authorization` header over Streamable HTTP are supported; there is no OAuth discovery, so clients that require OAuth for remote servers cannot connect. Sessions, resumable streams and server-sent notifications are not offered (stateless JSON responses). The protocol and authentication lifecycle are verified with the SDK client in `src/mcp.e2e.test.ts`; simulated approval and denial are in the evals. The owner's actual client, its version, the tunnel and the destructive-approval configuration are verified in S05.

### Open owner decisions and S05 verification: file size and transport

`upload` was built and tested with the SDK client and with base64 in the owner's message in the evals. These points are not settled and are left for the owner to decide and S05 to verify; nothing here changes them:

- **Size bound.** The example `MCP_ADMIN_BODY_LIMIT_BYTES` of 65536 admits a file of roughly 48 KiB, while the API accepts media up to `MEDIA_MAX_BYTES` (10 MiB in the example settings). A typical photo or CV PDF is larger than 48 KiB, so either the body limit is raised for uploads or the bound is accepted as it is; the owner decides which.
- **Transport.** Whether the owner's real client can pass a file's bytes to `upload` as base64 tool arguments, and up to what size, is unverified. The evals put the file into the owner's message as base64 text, which only simulates an attachment.
- **Model output.** The evals cap the model's answer at `max_tokens` 4096, and the model re-emits the whole base64 file in the `upload` call, which bounds the file an eval can carry; a real client and model have their own output limits.
- **Local files.** The skill forbids passing a path or address to `upload`. Whether the owner's client may read a local file the owner names and base64-encode it on the client side, before calling `upload` with the bytes, is for the owner to decide.
